Repartir los datos

Los pedidos de una tienda en línea no caben bien en una sola base. Vas a partirlos de dos maneras: por mes dentro de cada base, para borrar lo viejo sin dolor, y por cliente entre bases, para repartir la carga. Después vas a sumar un tercer shard con la tienda vendiendo, sin perder ni duplicar un pedido.

  • Pasar de dos a tres shards con carga, sin perder ni duplicar pedidos: doble escritura, backfill, verificación y limpieza.
  • Consultar todos los shards con un plazo, y conseguir que un shard congelado afecte solo a sus clientes.

La excusa

Una tienda en línea guarda sus pedidos en PostgreSQL. Empieza con dos bases y 10 000 clientes, y cada cliente vive entero en una de ellas: crear, listar y cancelar sus pedidos toca una sola base. La tienda crece y suma una tercera sin dejar de vender.

Son dos ideas que se parecen y resuelven problemas distintos. Dentro de cada base, la tabla se parte por mes: borrar un mes viejo es soltar una tabla, y una búsqueda por id va directo al mes que le toca. Entre bases, los clientes se reparten con un anillo de hashing consistente: cada base recibe un tercio de las escrituras, y sumar una cuarta mueve solo una parte de los clientes.

Tres bases iguales
Los tres shards salen del mismo bloque x-shard: misma imagen, mismo usuario y el mismo healthcheck. No se replican entre sí; cada uno tiene una parte distinta de los clientes.

s3 arranca con las tablas creadas, pero vacío: APP_RING dice que el anillo es s1,s2. La app conoce los tres desde el principio, para poder sumar s3 sin reiniciarse.

Un pool por shard
Cada shard tiene su URL y su pool-size. Tres shards con 10 conexiones son 30 por instancia de la app: con varias instancias, la cuenta tiene que caber en el max_connections de cada base, que es 100 por defecto. Documentado
Cortar a un shard congelado
socketTimeout=5, en la URL, corta una consulta que lleva 5 s sin respuesta. Sin él, el driver espera para siempre a un shard que aceptó la conexión y dejó de contestar.

import lab.pedidos.shard.Shards;

/** Llena los shards con pedidos repartidos en los últimos días, cada cliente en el shard que le toca. */
@RestController
public class SeedController {

    private final Shards shards;
    private final Topology topology;

    public SeedController(Shards shards, Topology topology) {
        this.shards = shards;
        this.topology = topology;
    }

    @PostMapping("/api/lab/seed")
    public Map<String, Integer> seed(@RequestParam(defaultValue = "10000") int customers,
                                     @RequestParam(defaultValue = "10") int ordersEach,
                                     @RequestParam(defaultValue = "80") int days) {
        State st = topology.state();
        Map<String, List<Long>> byShard = LongStream.rangeClosed(1, customers).boxed()
                .collect(Collectors.groupingBy(st::truth, TreeMap::new, Collectors.toList()));
        Map<String, Integer> inserted = new TreeMap<>();
        byShard.forEach((shard, ids) -> {
            int total = 0;
            for (int i = 0; i < ids.size(); i += 1000) {
                long[] chunk = ids.subList(i, Math.min(i + 1000, ids.size())).stream().mapToLong(Long::longValue).toArray();
                total += shards.jdbc(shard).sql("""
                        INSERT INTO orders (id, created_at, customer_id, total_cents, status, version)
                        SELECT g.id, uuid_extract_timestamp(g.id), g.customer_id, (random() * 20000)::bigint, 'NEW', 1
                          FROM (SELECT uuidv7(-(random() * make_interval(days => :days))) AS id, c AS customer_id
                                  FROM unnest(CAST(:customers AS bigint[])) AS c
                                 CROSS JOIN generate_series(1, :each)) AS g
                        """)
                        .param("customers", chunk)
                        .param("each", ordersEach)
                        .param("days", days)
                        .update();
            }
            inserted.put(shard, total);
        });
        return inserted;
    }
}

package lab.pedidos.partitions;

import java.time.Clock;
import java.time.YearMonth;
import java.util.List;

import lab.pedidos.shard.ShardProps;
import lab.pedidos.shard.Shards;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import org.springframework.beans.factory.InitializingBean;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

/**
 * Cada shard parte sus pedidos por mes. Al arrancar y cada madrugada: crea las particiones de los meses
 * que vienen y suelta las que pasaron la retención. Soltar una partición es instantáneo; borrar un mes fila por fila, no.
 */
@Component
public class PartitionMaintenance implements InitializingBean {

    private static final Logger log = LoggerFactory.getLogger(PartitionMaintenance.class);

    private final Shards shards;
    private final ShardProps.Partitions cfg;
    private final Clock clock = Clock.systemUTC();

    public PartitionMaintenance(Shards shards, ShardProps props) {
        this.shards = shards;
        this.cfg = props.partitions();
    }

    @Override
    public void afterPropertiesSet() {
        maintain();
    }

    @Scheduled(cron = "0 0 3 * * *", zone = "UTC")
    public void maintain() {
        YearMonth now = YearMonth.now(clock);
        for (String shard : shards.names()) {
            JdbcClient db = shards.jdbc(shard);
            for (int i = -cfg.monthsBack(); i <= cfg.monthsAhead(); i++) {
                create(db, now.plusMonths(i));
            }
            dropOlderThan(db, shard, now.minusMonths(cfg.retentionMonths()));
        }
    }

    public static String name(YearMonth month) {
        return "orders_%d_%02d".formatted(month.getYear(), month.getMonthValue());
    }

    private static void create(JdbcClient db, YearMonth month) {
        db.sql("CREATE TABLE IF NOT EXISTS %s PARTITION OF orders FOR VALUES FROM ('%s 00:00+00') TO ('%s 00:00+00')"
                .formatted(name(month), month.atDay(1), month.plusMonths(1).atDay(1))).update();
    }

    private static void dropOlderThan(JdbcClient db, String shard, YearMonth oldestToKeep) {
        List<String> partitions = db.sql("""
                SELECT c.relname FROM pg_inherits i JOIN pg_class c ON c.oid = i.inhrelid
                 WHERE i.inhparent = 'orders'::regclass
                 ORDER BY c.relname
                """).query(String.class).list();
        for (String partition : partitions) {
            YearMonth month = YearMonth.of(Integer.parseInt(partition.substring(7, 11)),
                    Integer.parseInt(partition.substring(12, 14)));
            if (month.isBefore(oldestToKeep)) {
                // CONCURRENTLY no bloquea las consultas que están leyendo orders mientras se suelta la partición.
                db.sql("ALTER TABLE orders DETACH PARTITION " + partition + " CONCURRENTLY").update();
                db.sql("DROP TABLE " + partition).update();
                log.info("Shard {}: partición {} eliminada", shard, partition);
            }
        }
    }
}
La decisión
Partir orders por rango de created_at, un mes por partición. La clave primaria de una tabla partida tiene que incluir la columna de partición, así que es (id, created_at). Documentado Como created_at sale del propio id con uuid_extract_timestamp, que la pareja sea única equivale a que el id lo sea, y una búsqueda por id puede decir en qué mes está el pedido. PartitionMaintenance crea los meses que vienen al arrancar y cada madrugada, y suelta los que pasaron la retención.
Lo que descartas
Una tabla sin partir y un DELETE por lotes cada noche para borrar lo viejo. Escribe en el WAL cada fila que borra, deja filas muertas para el vacuum y la tabla no se achica. Lo vas a medir. También descartas partir por hash del id: reparte parejo, pero un mes queda repartido entre todas las particiones, y ya no lo puedes soltar entero.
Qué puede salir mal
Que llegue un pedido de un mes sin partición: el INSERT falla. Si el mantenimiento deja de correr, los pedidos empiezan a fallar el día 1 del primer mes sin crear. Por eso crea tres meses hacia adelante, y conviene alertar si falta el siguiente. Una partición DEFAULT evita el error, pero después no puedes crear el mes que le falta mientras la DEFAULT tenga filas de ese rango. Documentado

/**
 * Anillo de hashing consistente. Cada shard pone "vnodes" puntos en el anillo; un cliente es del
 * primer punto que encuentra avanzando desde su propio hash.
 */
public final class Ring {

    private final List<String> nodes;
    private final NavigableMap<Long, String> points = new TreeMap<>();

    public Ring(List<String> nodes, int vnodes) {
        this.nodes = List.copyOf(nodes);
        for (String node : nodes) {
            for (int i = 0; i < vnodes; i++) {
                points.put(hash(node + "#" + i), node);
            }
        }
    }

    public String owner(long customerId) {
        Map.Entry<Long, String> point = points.ceilingEntry(hash(Long.toString(customerId)));
        return (point != null ? point : points.firstEntry()).getValue();
    }

    public List<String> nodes() {
        return nodes;
    }

    /** Los primeros 8 bytes del SHA-256: lento comparado con Murmur3, pero viene con el JDK. */
    public static long hash(String key) {
        try {
            byte[] digest = MessageDigest.getInstance("SHA-256").digest(key.getBytes(StandardCharsets.UTF_8));
            return ByteBuffer.wrap(digest).getLong();
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
La decisión
Cada shard pone 128 puntos en un anillo de números de 64 bits, en el hash de "s1#0", "s1#1"… Un cliente es del primer punto que encuentra avanzando desde el hash de su número: ceilingEntry, y si se pasa del último, el primero. El hash son los primeros 8 bytes del SHA-256, que da lo mismo en cualquier JVM y en cualquier lenguaje: anillo.py reproduce el anillo en Python.
Lo que descartas
hash(cliente) mod N. Reparte igual de bien, pero al pasar de dos a tres shards cambia de dueño dos de cada tres clientes, y con el anillo, uno de cada tres. Y una tabla que diga el shard de cada cliente: mueve exactamente lo que quieras, pero es otra base que consultar en cada request, y si se cae, se cae todo.
Qué puede salir mal
Cambiar la función de hash o el número de nodos virtuales es una migración: mueve todos los puntos del anillo. String.hashCode() tiene el mismo problema si algún día otro servicio, en otro lenguaje, tiene que calcular el dueño. Y con pocos nodos virtuales, la carga queda despareja: con uno por shard, el más cargado llevó en promedio un 85 % más de lo justo.

@Component
public class Shards implements DisposableBean {

    private final Map<String, HikariDataSource> pools = new TreeMap<>();
    private final Map<String, JdbcClient> clients = new TreeMap<>();
    private final Map<String, TransactionTemplate> transactions = new TreeMap<>();

    public Shards(ShardProps props) {
        props.shards().forEach((name, db) -> {
            HikariDataSource ds = new HikariDataSource();
            ds.setPoolName("shard-" + name);
            ds.setJdbcUrl(db.url());
            ds.setUsername(db.username());
            ds.setPassword(db.password());
            ds.setMaximumPoolSize(db.poolSize());
            // Si un shard no responde, mejor fallar en 1 s que dejar el hilo esperando 30.
            ds.setConnectionTimeout(1000);
            Flyway.configure().dataSource(ds).load().migrate();
            pools.put(name, ds);
            clients.put(name, JdbcClient.create(ds));
            transactions.put(name, new TransactionTemplate(new DataSourceTransactionManager(ds)));
        });
    }

    public Set<String> names() {
        return clients.keySet();
    }

    public JdbcClient jdbc(String shard) {
        JdbcClient client = clients.get(shard);
        if (client == null) {
            throw new IllegalArgumentException("No existe el shard " + shard);
        }
        return client;
    }

    public TransactionTemplate tx(String shard) {
        return transactions.get(shard);
    }

    @Override
    public void destroy() {
        pools.values().forEach(HikariDataSource::close);
    }
}

La decisión
Un HikariDataSource, un JdbcClient y un TransactionTemplate por shard, con Flyway corriendo en cada uno. @Component

    /** created_at sale del propio UUIDv7: con el id ya se sabe en qué partición está el pedido. */
    public Order insert(JdbcClient db, long customer, long totalCents) {
        return db.sql("""
                INSERT INTO orders (id, created_at, customer_id, total_cents, status, version)
                SELECT n.id, uuid_extract_timestamp(n.id), :customer, :total, 'NEW', 1
                  FROM (SELECT uuidv7() AS id) AS n
                RETURNING id, customer_id, total_cents, status, version, created_at
                """)
                .param("customer", customer)
                .param("total", totalCents)
                .query(Order.class)
                .single();
    }

    public Optional<Order> find(JdbcClient db, long customer, UUID id) {
        return db.sql("SELECT " + COLUMNS + """
                  FROM orders
                 WHERE id = :id AND created_at = uuid_extract_timestamp(:id) AND customer_id = :customer
                """)
                .param("id", id)
                .param("customer", customer)
                .query(Order.class)
                .optional();
    }

    public List<Order> byCustomer(JdbcClient db, long customer, int limit) {
        return db.sql("SELECT " + COLUMNS + """
                  FROM orders
                 WHERE customer_id = :customer
                 ORDER BY created_at DESC
                 LIMIT :limit
                """)
                .param("customer", customer)
                .param("limit", limit)
                .query(Order.class)
                .list();
    }

    public Optional<Order> cancel(JdbcClient db, long customer, UUID id) {
        return db.sql("""
                UPDATE orders SET status = 'CANCELLED', version = version + 1
                 WHERE id = :id AND created_at = uuid_extract_timestamp(:id)
                   AND customer_id = :customer AND status = 'NEW'
                RETURNING id, customer_id, total_cents, status, version, created_at
                """)
                .param("id", id)
                .param("customer", customer)
                .query(Order.class)
                .optional();
    }

    public List<Order> recent(JdbcClient db, int limit) {
        return db.sql("SELECT " + COLUMNS + " FROM orders ORDER BY created_at DESC, id DESC LIMIT :limit")
                .param("limit", limit)
                .query(Order.class)
                .list();
    }

    /** Recorre el shard por id (keyset) para el backfill, la verificación y la limpieza. */
    public List<Order> pageAfter(JdbcClient db, UUID after, int limit) {
        return db.sql("SELECT " + COLUMNS + " FROM orders WHERE id > :after ORDER BY id LIMIT :limit")
                .param("after", after)
                .param("limit", limit)
                .query(Order.class)
                .list();
    }

    /**
     * Copia filas enteras a otro shard. Con UPSERT, una fila que ya está solo se pisa si la copia es más nueva,
     * así que no importa en qué orden lleguen el backfill y la doble escritura.
     */
    public int copy(JdbcClient db, List<Order> rows, CopyMode mode) {
        String onConflict = mode == CopyMode.UPSERT
                ? "DO UPDATE SET status = excluded.status, version = excluded.version WHERE orders.version < excluded.version"
                : "DO NOTHING";
        return db.sql("""
                INSERT INTO orders (id, created_at, customer_id, total_cents, status, version)
                SELECT u.id, uuid_extract_timestamp(u.id), u.customer_id, u.total_cents, u.status, u.version
                  FROM unnest(CAST(:ids AS uuid[]), CAST(:customers AS bigint[]), CAST(:totals AS bigint[]),
                              CAST(:statuses AS text[]), CAST(:versions AS int[]))
                       AS u (id, customer_id, total_cents, status, version)
                ON CONFLICT (id, created_at)
                """ + onConflict)
                .param("ids", rows.stream().map(o -> o.id().toString()).toArray(String[]::new))
                .param("customers", rows.stream().mapToLong(Order::customerId).toArray())
                .param("totals", rows.stream().mapToLong(Order::totalCents).toArray())
                .param("statuses", rows.stream().map(Order::status).toArray(String[]::new))
                .param("versions", rows.stream().mapToInt(Order::version).toArray())
                .update();
    }

    /** La doble escritura ingenua: repetir el UPDATE en el otro shard. Si la fila todavía no llegó, no toca nada. */
    public void naiveUpdate(JdbcClient db, Order order) {
        db.sql("""
                UPDATE orders SET status = :status, version = :version
                 WHERE id = :id AND created_at = uuid_extract_timestamp(:id)
                """)
                .param("id", order.id())
                .param("status", order.status())
                .param("version", order.version())
                .update();
    }

    public Map<UUID, Integer> versions(JdbcClient db, Collection<UUID> ids) {
        Map<UUID, Integer> out = new HashMap<>();
        db.sql("SELECT id, version FROM orders WHERE id = ANY(CAST(:ids AS uuid[]))")
                .param("ids", ids.stream().map(UUID::toString).toArray(String[]::new))
                .query(rs -> {
                    out.put(rs.getObject("id", UUID.class), rs.getInt("version"));
                });
        return out;
    }

    public int delete(JdbcClient db, Collection<UUID> ids) {
        return db.sql("DELETE FROM orders WHERE id = ANY(CAST(:ids AS uuid[]))")
                .param("ids", ids.stream().map(UUID::toString).toArray(String[]::new))
                .update();
    }

    public long count(JdbcClient db) {
        return db.sql("SELECT count(*) FROM orders").query(Long.class).single();
    }

@Service
public class OrderService {

    private static final Comparator<Order> NEWEST_FIRST =
            Comparator.comparing(Order::createdAt).thenComparing(Order::id).reversed();

    private final Shards shards;
    private final Topology topology;
    private final OrderSql sql;
    private final Duration scatterTimeout;
    private final ExecutorService scatter = Executors.newVirtualThreadPerTaskExecutor();
    private final LongAdder mirrorFailures = new LongAdder();

    public OrderService(Shards shards, Topology topology, OrderSql sql, ShardProps props) {
        this.shards = shards;
        this.topology = topology;
        this.sql = sql;
        this.scatterTimeout = props.scatterTimeout();

    public Order create(long customer, long totalCents) {
        State st = topology.state();
        Order order = onShard(st.truth(customer), db -> sql.insert(db, customer, totalCents));
        mirror(st, order, false);
        return order;
    }

    public Order get(long customer, UUID id) {
        return onShard(topology.state().truth(customer), db -> sql.find(db, customer, id))
                .orElseThrow(() -> notFound(id));

        State st = topology.state();
        String shard = st.truth(customer);
        Order order = onShard(shard, db -> sql.cancel(db, customer, id)).orElseThrow(() ->
                onShard(shard, db -> sql.find(db, customer, id)).isPresent()

                        : notFound(id));
        mirror(st, order, true);
        return order;
    }

    /**
     * Scatter-gather: pregunta a todos los shards a la vez, espera como mucho scatterTimeout en total
     * y junta lo que llegó. Un shard lento no frena la respuesta: queda en missingShards.
     */
    public Recent recent(int limit) {
        State st = topology.state();
        Map<String, Future<List<Order>>> asked = new TreeMap<>();
        for (String shard : st.truthShards()) {
            asked.put(shard, scatter.submit(() -> sql.recent(shards.jdbc(shard), limit)));
        }
        long deadline = System.nanoTime() + scatterTimeout.toNanos();
        List<Order> merged = new ArrayList<>();
        List<String> missing = new ArrayList<>();
        for (Map.Entry<String, Future<List<Order>>> answer : asked.entrySet()) {
            try {
                long left = Math.max(0, deadline - System.nanoTime());
                for (Order order : answer.getValue().get(left, TimeUnit.NANOSECONDS)) {
                    // Durante una migración, un shard guarda copias de clientes que no son suyos: se descartan.
                    if (st.truth(order.customerId()).equals(answer.getKey())) {
                        merged.add(order);
                    }
                }
            } catch (TimeoutException | ExecutionException e) {
                answer.getValue().cancel(true);
                missing.add(answer.getKey());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                throw new IllegalStateException(e);
            }
        }
        merged.sort(NEWEST_FIRST);
        return new Recent(List.copyOf(merged.subList(0, Math.min(limit, merged.size()))), !missing.isEmpty(), missing);
    }

    public long mirrorFailures() {
        return mirrorFailures.sum();
    }

    /**
     * La segunda escritura de la migración. No hay transacción entre dos shards: si la copia falla, el pedido
     * ya existe en el shard que tiene la verdad, se anota y el backfill o la verificación lo arreglan.
     */
    private void mirror(State st, Order order, boolean isUpdate) {
        st.mirror(order.customerId()).ifPresent(other -> {
            try {
                JdbcClient db = shards.jdbc(other);
                if (st.copy() == CopyMode.NAIVE && isUpdate) {
                    sql.naiveUpdate(db, order);
                } else {
                    sql.copy(db, List.of(order), st.copy());
                }
            } catch (DataAccessException e) {
                mirrorFailures.increment();
                log.warn("No se pudo copiar el pedido {} al shard {}", order.id(), other, e);
            }
        });
    }

    private <T> T onShard(String shard, Function<JdbcClient, T> work) {
        try {
            return work.apply(shards.jdbc(shard));
        } catch (DataAccessResourceFailureException e) {
            throw new ShardUnavailable(shard, e);
        }
    }

    private static ResponseStatusException notFound(UUID id) {
        return new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe el pedido " + id);
    }

topology.state().truth(customer) dice qué shard tiene la verdad de ese cliente, y todo el trabajo va a ese shard. Buscar y cancelar filtran por id, por created_at = uuid_extract_timestamp(:id), para que el planificador vaya a un solo mes, y por cliente: un pedido pedido con otro cliente da 404.

package lab.pedidos.shard;

import java.util.List;
import java.util.Optional;
import java.util.concurrent.atomic.AtomicReference;

import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ResponseStatusException;

/**
 * Qué anillo manda y en qué fase va la migración. Vive en memoria, así que sirve para una sola
 * instancia: en producción iría en un almacén compartido (etcd, Consul o una tabla) con versión.
 */
@Component
public class Topology {

    public enum Phase { STABLE, DUAL_WRITE, READ_NEW }

    /** UPSERT copia la fila entera y gana la versión más alta. NAIVE repite la operación y puede perder cambios. */
    public enum CopyMode { UPSERT, NAIVE }

    public record State(Ring current, Ring target, Phase phase, CopyMode copy) {

        /** El shard que tiene la verdad de este cliente. */
        public String truth(long customer) {
            return phase == Phase.READ_NEW ? target.owner(customer) : current.owner(customer);
        }

        /** El otro shard que recibe una copia mientras dura la migración, si es distinto. */
        public Optional<String> mirror(long customer) {
            if (phase == Phase.STABLE) {
                return Optional.empty();
            }
            String other = phase == Phase.DUAL_WRITE ? target.owner(customer) : current.owner(customer);
            return other.equals(truth(customer)) ? Optional.empty() : Optional.of(other);
        }

        /** Los shards que tienen la verdad de algún cliente: los que consulta un scatter-gather. */
        public List<String> truthShards() {
            return phase == Phase.READ_NEW ? target.nodes() : current.nodes();
        }
    }

    private final AtomicReference<State> state;
    private final Shards shards;
    private final int vnodes;
    private volatile boolean finishedHere;

    public Topology(ShardProps props, Shards shards) {
        this.shards = shards;
        this.vnodes = props.vnodes();
        requireKnown(props.ring());
        this.state = new AtomicReference<>(new State(new Ring(props.ring(), vnodes), null, Phase.STABLE, CopyMode.UPSERT));
    }

    public State state() {
        return state.get();
    }

    public synchronized State start(List<String> target, CopyMode copy) {
        State now = state.get();
        if (now.phase() != Phase.STABLE) {
            throw conflict("Ya hay una migración en curso, en la fase " + now.phase());
        }
        requireKnown(target);
        return set(new State(now.current(), new Ring(target, vnodes), Phase.DUAL_WRITE, copy));
    }

    public synchronized State readNew() {
        State now = require(Phase.DUAL_WRITE);
        return set(new State(now.current(), now.target(), Phase.READ_NEW, now.copy()));
    }

    public synchronized State finish() {
        State now = require(Phase.READ_NEW);
        finishedHere = true;
        return set(new State(now.target(), null, Phase.STABLE, now.copy()));
    }

    /**
     * Borrar copias solo es seguro si esta instancia terminó la migración. Si la aplicación se reinició,
     * el anillo vuelve al de la configuración y "lo que no es mío" podría ser todo lo que se migró.
     */
    public boolean finishedHere() {
        return finishedHere && state.get().phase() == Phase.STABLE;
    }

    private State require(Phase phase) {
        State now = state.get();
        if (now.phase() != phase) {
            throw conflict("La migración está en " + now.phase() + " y este paso necesita " + phase);
        }
        return now;
    }

    private State set(State next) {
        state.set(next);
        return next;
    }

    private void requireKnown(List<String> ring) {
        if (ring.isEmpty() || !shards.names().containsAll(ring)) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST,
                    "El anillo " + ring + " usa shards que no existen: " + shards.names());
        }
    }

    private static ResponseStatusException conflict(String message) {
        return new ResponseStatusException(HttpStatus.CONFLICT, message);
    }
}

    public Backfill backfill() {
        State st = requireMigrating();
        long t0 = System.nanoTime();
        long scanned = 0;
        long copied = 0;
        for (String source : st.current().nodes()) {
            UUID after = FIRST;
            List<Order> page;
            while (!(page = sql.pageAfter(shards.jdbc(source), after, batch)).isEmpty()) {
                scanned += page.size();
                for (Map.Entry<String, List<Order>> dest : leaving(st, source, page).entrySet()) {
                    copied += sql.copy(shards.jdbc(dest.getKey()), dest.getValue(), st.copy());
                }
                after = page.getLast().id();
            }
        }
        return new Backfill(scanned, copied, (System.nanoTime() - t0) / 1_000_000);
    }

    /**
     * Compara cada fila que se muda con su copia. Una diferencia puede ser una doble escritura que todavía
     * no terminó, así que las diferencias se vuelven a mirar medio segundo después antes de contarlas.
     */
    public Verify verify() throws InterruptedException {
        State st = requireMigrating();
        long checked = 0;
        List<Moved> suspects = new ArrayList<>();
        for (String source : st.current().nodes()) {
            UUID after = FIRST;
            List<Order> page;
            while (!(page = sql.pageAfter(shards.jdbc(source), after, batch)).isEmpty()) {
                for (Map.Entry<String, List<Order>> dest : leaving(st, source, page).entrySet()) {
                    List<Order> rows = dest.getValue();
                    checked += rows.size();
                    Map<UUID, Integer> copies = sql.versions(shards.jdbc(dest.getKey()), ids(rows));
                    for (Order row : rows) {
                        if (!Integer.valueOf(row.version()).equals(copies.get(row.id()))) {
                            suspects.add(new Moved(source, dest.getKey(), row));
                        }
                    }
                }
                after = page.getLast().id();
            }
        }
        Thread.sleep(500);
        long missing = 0;
        long stale = 0;
        List<UUID> examples = new ArrayList<>();
        for (Moved m : suspects) {
            Integer truth = sql.versions(shards.jdbc(m.from()), List.of(m.row().id())).get(m.row().id());
            Integer copy = sql.versions(shards.jdbc(m.to()), List.of(m.row().id())).get(m.row().id());
            if (copy == null) {
                missing++;
            } else if (!copy.equals(truth)) {
                stale++;
            } else {
                continue;
            }
            if (examples.size() < 5) {
                examples.add(m.row().id());
            }
        }
        return new Verify(checked, missing, stale, examples);
    }

    /** Borra de cada shard las filas de clientes que ya no son suyos. Es lo único irreversible de la migración. */
    public Map<String, Integer> cleanup() {
        if (!topology.finishedHere()) {
            throw new ResponseStatusException(HttpStatus.CONFLICT,
                    "Solo se limpia después de terminar la migración en esta misma instancia");
        }
        State st = topology.state();
        Map<String, Integer> deleted = new TreeMap<>();
        for (String shard : shards.names()) {
            JdbcClient db = shards.jdbc(shard);
            int count = 0;
            UUID after = FIRST;
            List<Order> page;
            while (!(page = sql.pageAfter(db, after, batch)).isEmpty()) {
                List<UUID> notMine = page.stream()
                        .filter(o -> !st.current().owner(o.customerId()).equals(shard))
                        .map(Order::id)
                        .toList();
                if (!notMine.isEmpty()) {
                    count += sql.delete(db, notMine);
                }
                after = page.getLast().id();
            }
            deleted.put(shard, count);
        }
        return deleted;
    }

    private State requireMigrating() {
        State st = topology.state();
        if (st.phase() == Phase.STABLE) {
            throw new ResponseStatusException(HttpStatus.CONFLICT, "No hay ninguna migración en curso");
        }
        return st;
    }

    /** Las filas de esta página cuyo cliente cambia de shard en el anillo nuevo, agrupadas por destino. */
    private static Map<String, List<Order>> leaving(State st, String source, List<Order> page) {
        return page.stream()
                .filter(o -> !st.target().owner(o.customerId()).equals(source))
                .collect(Collectors.groupingBy(o -> st.target().owner(o.customerId()), HashMap::new, Collectors.toList()));
    }

    private static List<UUID> ids(List<Order> rows) {
        return rows.stream().map(Order::id).toList();
    }
}
La decisión
Primero, cada escritura va al dueño actual y se copia al dueño nuevo. Después, el backfill recorre cada shard por id, de a 1 000 filas, y copia lo que se muda. Las dos copias son la fila entera con su versión, y ON CONFLICT … WHERE orders.version < excluded.version hace que gane siempre la más nueva: no importa cuál llegue primero. verify compara versiones y vuelve a mirar las diferencias medio segundo después, por si eran una copia en camino. Recién entonces se lee del anillo nuevo, y solo al final se borra.
Lo que descartas
Parar las escrituras, copiar y cambiar de anillo: el corte dura lo que tarde la copia. Y la doble escritura ingenua, el modo NAIVE, que repite cada operación en el otro shard: si la cancelación llega antes que el backfill, el UPDATE no encuentra la fila, y el backfill después copia la versión vieja. Lo vas a provocar.
Qué puede salir mal
La topología vive en memoria: sirve para una sola instancia. Con dos, una puede estar en READ_NEW y la otra en DUAL_WRITE, y cada una cree que la verdad está en un lado distinto. En producción va en un lugar compartido, con versión. Si la app se reinicia a mitad, vuelve al anillo de la configuración, que todavía tiene la verdad, y la migración se empieza de nuevo. cleanup es lo único que no tiene vuelta atrás, y se niega si la migración no terminó en esta instancia.

# El mismo anillo que Ring.java, sin levantar nada: qué tan pareja queda la carga y cuántos clientes
# se mudan al sumar un shard. Uso: python scripts/anillo.py
import bisect
import hashlib
import statistics


def h(texto):
    # Los primeros 8 bytes del SHA-256, con signo, como ByteBuffer.getLong() en Java.
    return int.from_bytes(hashlib.sha256(texto.encode()).digest()[:8], "big", signed=True)


def anillo(nodos, vnodes):
    puntos = sorted((h(f"{n}#{i}"), n) for n in nodos for i in range(vnodes))
    claves = [p[0] for p in puntos]
    # bisect_left es el ceilingEntry de Java; el módulo, la vuelta al primer punto.
    return lambda cliente: puntos[bisect.bisect_left(claves, h(str(cliente))) % len(puntos)][1]

Cómo conectar

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A00, el laboratorio

    Los pedidos usan uuidv7(), los ids de A00, y aquí rinden el doble: además de no chocar entre shards, llevan la fecha que decide la partición. Si pones un PgBouncer de A00 delante de cada shard, haz la cuenta de nuevo: sin él, cada instancia de la app abre 10 conexiones a cada shard, y diez instancias son 100, el max_connections por defecto. Con él, la app puede abrir las que quiera y cada shard ve solo las del default_pool_size del PgBouncer. Flyway sigue yendo directo a cada base, como en A00.

  • Con A01, detrás de Nginx

    Las réplicas de la app no guardan pedidos, así que cualquiera puede atender a cualquier cliente. Lo que se rompe es la topología, que vive en memoria: con tres réplicas detrás de Nginx, una puede estar en READ_NEW y otra en DUAL_WRITE. Guárdala en un lugar compartido, con un número de versión, y que cada réplica rechace una escritura si su versión quedó vieja. Nginx tiene su propio anillo, hash $variable consistent, con el método ketama Documentado: sirve para que el mismo cliente caiga en la misma réplica, por ejemplo por su caché, no para repartir datos.

  • Con A02, una API que no se rompe

    Los recientes devuelven una sola página. Para paginarlos, usa el cursor de A02 con (created_at, id): cada shard sigue desde el cursor con su índice, y la app junta y corta. Con OFFSET, la página 50 le pide 50 páginas a cada shard. Y el 503 del shard caído ya es un ProblemDetail con su propio type, como los errores de A02; súmale un Retry-After para que el cliente sepa cuándo volver a intentar.

  • Con A03, caché que aguanta un pico

    Los nodos virtuales emparejan la cantidad de clientes, no la carga: si un cliente compra por mil, todo su tráfico cae en su shard igual. Una clave caliente se arregla con una caché delante, como la de A03, o partiendo a ese cliente, no con más nodos virtuales. Los recientes son un buen candidato para esa caché: cada request le pregunta a todos los shards, y con la carga única de A03 una sola por segundo haría el fan-out.

  • Con A04, primario y réplicas

    Cada shard puede tener sus réplicas, como en A04: si s2 se cae, su réplica se promueve y solo sus clientes ven el corte. Los recientes podrían leer de las réplicas, porque ya aceptan resultados incompletos. La verificación de la migración, no: con el lag de A04, una réplica todavía no tiene la última cancelación, y verify vería diferencias que no existen, o dejaría pasar las que sí.

  • Con A05, dos primarios

    La replicación lógica de A05 es otra forma de hacer el backfill: s3 se suscribe a s1 y a s2 y recibe cada cambio en orden, sin la carrera del modo NAIVE. El problema es elegir qué filas mandar. El filtro de filas de una publicación solo admite expresiones simples, sin funciones definidas por el usuario Documentado, y el anillo no es una: s3 recibiría todos los pedidos, y la limpieza tendría que borrar dos tercios.
