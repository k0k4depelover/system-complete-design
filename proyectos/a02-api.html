Una API que no se rompe

El catálogo de una librería con un millón de libros. La API tiene que paginar rápido en la última página, no pisar los cambios de otro, decir con claridad qué salió mal y seguir sirviendo a los clientes viejos mientras cambia.

Sin empezar

Al terminar podrás

  • Paginar un millón de filas con un cursor y medir con EXPLAIN ANALYZE cuánto cuesta OFFSET en cada página.
  • Responder 304 cuando el cliente ya tiene la versión actual, con un ETag que sale de la fila.
  • Rechazar con 412 la escritura de quien editó una versión vieja, y con 428 la de quien no dijo qué versión editaba.
  • Devolver cada error como Problem Details, con un type estable y el campo que falló.
  • Publicar una versión nueva de la API por cabecera, con la vieja marcada con Deprecation y Sunset.

La excusa

Una librería publica su catálogo: un millón de libros, que leen la web, la app y un par de socios que integraron su sistema hace años y no lo van a tocar pronto. Los editores corrigen fichas desde dos oficinas, a veces la misma ficha a la vez. Y el equipo quiere cambiar author, un texto, por authors, una lista, sin romper a los socios.

Ninguna de esas cosas es exótica. Son las que hacen que una API pública se vuelva difícil de cambiar, y casi todas se resuelven en el protocolo HTTP, no en el código.

Los endpoints

Sin la cabecera API-Version, el cliente recibe la 1.0, que es la que usan los socios. La 1.1 cambia author por authors y es la única que escribe.

Paso a paso

Paso 1. La tabla, con una versión por fila

CREATE TABLE books (
    id         uuid        PRIMARY KEY DEFAULT uuidv7(),
    title      text        NOT NULL,
    authors    text[]      NOT NULL,
    isbn       char(13)    UNIQUE,
    year       int         NOT NULL,
    version    int         NOT NULL DEFAULT 1,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);

-- El índice del cursor por título: mismo orden que el ORDER BY (title, id).
CREATE INDEX books_title_id ON books (title, id);
La decisión
Una columna version que sube en cada escritura. Es el ETag y es la condición de la escritura: el mismo número sirve para no mandar lo que el cliente ya tiene y para no pisar lo que cambió otro.
Lo que descartas
Usar updated_at como versión. Dos escrituras en el mismo milisegundo tienen la misma fecha, y un reloj que se atrasa en un servidor produce una versión que retrocede.
Qué puede salir mal
Un índice que no coincide con el orden. El cursor por título ordena por (title, id); si el índice fuera solo por title, PostgreSQL tendría que ordenar los empates en memoria y la comparación de la página siguiente no sería un rango del índice.

Paso 2. Paginar con un cursor

package lab.catalogo.books;

import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.UUID;

/**
 * La posición de la última fila que vio el cliente. Viaja opaco (base64url):
 * así puedes cambiar lo que guarda sin romper a nadie.
 */
public record Cursor(String title, UUID id) {

    public String encode() {
        String raw = (title == null ? "" : title) + "|" + id;
        return Base64.getUrlEncoder().withoutPadding().encodeToString(raw.getBytes(StandardCharsets.UTF_8));
    }

    public static Cursor decode(String token) {
        try {
            String raw = new String(Base64.getUrlDecoder().decode(token), StandardCharsets.UTF_8);
            int cut = raw.lastIndexOf('|');   // el UUID no tiene '|': el último separa los dos campos
            return new Cursor(raw.substring(0, cut), UUID.fromString(raw.substring(cut + 1)));
        } catch (RuntimeException e) {
            throw Problems.badCursor();
        }
    }
}
package lab.catalogo.books;

import java.sql.Array;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.Arrays;
import java.util.List;
import java.util.Optional;
import java.util.UUID;

import org.springframework.jdbc.core.RowMapper;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
public class BookRepository {

    private static final String COLUMNS = "id, title, authors, isbn, year, version";

    private static final RowMapper<Book> ROW = (ResultSet rs, int n) -> new Book(
            rs.getObject("id", UUID.class),
            rs.getString("title"),
            authors(rs.getArray("authors")),
            rs.getString("isbn"),
            rs.getInt("year"),
            rs.getInt("version"));

    private final JdbcClient jdbc;

    public BookRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    public Book insert(BookInput in) {
        return jdbc.sql("""
                INSERT INTO books (title, authors, isbn, year)
                VALUES (:title, :authors, :isbn, :year)
                RETURNING %s
                """.formatted(COLUMNS))
                .param("title", in.title())
                .param("authors", in.authors().toArray(String[]::new))
                .param("isbn", in.isbn())
                .param("year", in.year())
                .query(ROW)
                .single();
    }

    public Optional<Book> find(UUID id) {
        return jdbc.sql("SELECT " + COLUMNS + " FROM books WHERE id = :id")
                .param("id", id)
                .query(ROW)
                .optional();
    }

    /** Concurrencia optimista: solo actualiza si nadie cambió el libro desde la versión que vio el cliente. */
    public Optional<Book> update(UUID id, int expectedVersion, BookInput in) {
        return jdbc.sql("""
                UPDATE books
                   SET title = :title, authors = :authors, isbn = :isbn, year = :year,
                       version = version + 1, updated_at = now()
                 WHERE id = :id AND version = :expected
                RETURNING %s
                """.formatted(COLUMNS))
                .param("id", id)
                .param("expected", expectedVersion)
                .param("title", in.title())
                .param("authors", in.authors().toArray(String[]::new))
                .param("isbn", in.isbn())
                .param("year", in.year())
                .query(ROW)
                .optional();
    }

    public boolean delete(UUID id, int expectedVersion) {
        return jdbc.sql("DELETE FROM books WHERE id = :id AND version = :expected")
                .param("id", id)
                .param("expected", expectedVersion)
                .update() == 1;
    }

    /** Primera página, de los más nuevos a los más viejos (los UUIDv7 crecen con el tiempo). */
    public List<Book> newest(int limit) {
        return jdbc.sql("SELECT " + COLUMNS + " FROM books ORDER BY id DESC LIMIT :limit")
                .param("limit", limit)
                .query(ROW)
                .list();
    }

    public List<Book> newestBefore(UUID id, int limit) {
        return jdbc.sql("SELECT " + COLUMNS + " FROM books WHERE id < :id ORDER BY id DESC LIMIT :limit")
                .param("id", id)
                .param("limit", limit)
                .query(ROW)
                .list();
    }

    /** Por título. El id desempata títulos repetidos: sin él, el cursor salta o repite filas. */
    public List<Book> byTitle(int limit) {
        return jdbc.sql("SELECT " + COLUMNS + " FROM books ORDER BY title, id LIMIT :limit")
                .param("limit", limit)
                .query(ROW)
                .list();
    }

    public List<Book> byTitleAfter(Cursor after, int limit) {
        return jdbc.sql("""
                SELECT %s FROM books
                 WHERE (title, id) > (:title, :id)
                 ORDER BY title, id
                 LIMIT :limit
                """.formatted(COLUMNS))
                .param("title", after.title())
                .param("id", after.id())
                .param("limit", limit)
                .query(ROW)
                .list();
    }

    private static List<String> authors(Array array) throws SQLException {
        return Arrays.asList((String[]) array.getArray());
    }
}
package lab.catalogo.books;

import java.util.List;
import java.util.UUID;

import org.springframework.stereotype.Service;

@Service
public class BookService {

    private final BookRepository books;

    public BookService(BookRepository books) {
        this.books = books;
    }

    public Book create(BookInput in) {
        return books.insert(in);
    }

    public Book get(UUID id) {
        return books.find(id).orElseThrow(() -> Problems.notFound(id));
    }

    public Book replace(UUID id, int expectedVersion, BookInput in) {
        return books.update(id, expectedVersion, in).orElseThrow(() -> conflictOrMissing(id, expectedVersion));
    }

    public void delete(UUID id, int expectedVersion) {
        if (!books.delete(id, expectedVersion)) {
            throw conflictOrMissing(id, expectedVersion);
        }
    }

    /** sort = "recent" (por defecto) o "title". Pide una fila de más para saber si hay otra página. */
    public Page<Book> list(String sort, String after, int limit) {
        boolean byTitle = "title".equals(sort);
        Cursor cursor = after == null ? null : Cursor.decode(after);
        List<Book> rows;
        if (byTitle) {
            rows = cursor == null ? books.byTitle(limit + 1) : books.byTitleAfter(cursor, limit + 1);
        } else {
            rows = cursor == null ? books.newest(limit + 1) : books.newestBefore(cursor.id(), limit + 1);
        }
        if (rows.size() <= limit) {
            return new Page<>(rows, null);
        }
        Book last = rows.get(limit - 1);
        String next = new Cursor(byTitle ? last.title() : "", last.id()).encode();
        return new Page<>(rows.subList(0, limit), next);
    }

    private RuntimeException conflictOrMissing(UUID id, int expectedVersion) {
        // La escritura condicional no tocó ninguna fila: o el libro no existe o alguien lo cambió antes.
        return books.find(id)
                .<RuntimeException>map(current -> Problems.staleVersion(id, expectedVersion, current.version()))
                .orElseGet(() -> Problems.notFound(id));
    }
}

La decisión
Paginación keyset: la página siguiente empieza después de la última fila vista, WHERE (title, id) > (:title, :id). PostgreSQL compara la tupla completa, en el mismo orden del índice, y salta directo a esa posición. El servicio pide una fila de más para saber si hay otra página sin un COUNT.
Lo que descartas
OFFSET. La base tiene que leer y descartar todas las filas anteriores: la página 45 000 lee 900 000 filas para devolver 20. Y si alguien inserta un libro mientras paginas, todo se corre una posición y ves una fila dos veces.
Qué puede salir mal
Ordenar solo por título. Hay títulos repetidos, y con WHERE title > :title el cursor salta los libros con el mismo título que el último de la página. El id desempata. Y escribir la condición como title > :t OR (title = :t AND id > :id) da el mismo resultado pero no usa el índice como rango: lo vas a medir.

El cursor viaja en base64url, no como ?title=Libro%200899999&id=…. El cliente no tiene que entender qué hay adentro, y tú puedes cambiarlo mañana, por ejemplo para ordenar por año, sin romper a nadie. Un cursor que no se puede decodificar es un 400 cursor-invalido, no un 500.

Paso 3. ETag y 304

package lab.catalogo.books;

import java.util.UUID;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;

import io.swagger.v3.oas.annotations.Hidden;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestMethod;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.util.UriComponentsBuilder;

@RestController
@RequestMapping("/books")
public class BookController {

    private final BookService books;

    public BookController(BookService books) {
        this.books = books;
    }

    @GetMapping(version = "1.1")
    public Page<Book> list(@RequestParam(defaultValue = "recent") String sort,
                           @RequestParam(required = false) String after,
                           @RequestParam(defaultValue = "20") @Min(1) @Max(100) int limit) {
        return books.list(sort, after, limit);
    }

    @GetMapping(version = "1.0")
    public Page<BookV1> listV1(@RequestParam(defaultValue = "recent") String sort,
                               @RequestParam(required = false) String after,
                               @RequestParam(defaultValue = "20") @Min(1) @Max(100) int limit) {
        Page<Book> page = books.list(sort, after, limit);
        return new Page<>(page.items().stream().map(BookV1::of).toList(), page.next());
    }

    @GetMapping(path = "/{id}", version = "1.1")
    public ResponseEntity<Book> get(@PathVariable UUID id) {
        Book book = books.get(id);
        // Con ETag en la respuesta, Spring compara If-None-Match y contesta 304 sin body.
        return ResponseEntity.ok().eTag(etag(book)).body(book);
    }

    @GetMapping(path = "/{id}", version = "1.0")
    public ResponseEntity<BookV1> getV1(@PathVariable UUID id) {
        Book book = books.get(id);
        return ResponseEntity.ok().eTag(etag(book)).body(BookV1.of(book));
    }

    @PostMapping(version = "1.1")
    public ResponseEntity<Book> create(@Valid @RequestBody BookInput body, UriComponentsBuilder uri) {
        Book book = books.create(body);
        return ResponseEntity.created(uri.path("/books/{id}").build(book.id())).eTag(etag(book)).body(book);
    }

    @PutMapping(path = "/{id}", version = "1.1")
    public ResponseEntity<Book> replace(@PathVariable UUID id,
                                        @RequestHeader(name = "If-Match", required = false) String ifMatch,
                                        @Valid @RequestBody BookInput body) {
        Book book = books.replace(id, version(ifMatch), body);
        return ResponseEntity.ok().eTag(etag(book)).body(book);
    }

    @DeleteMapping(path = "/{id}", version = "1.1")
    public ResponseEntity<Void> delete(@PathVariable UUID id,
                                       @RequestHeader(name = "If-Match", required = false) String ifMatch) {
        books.delete(id, version(ifMatch));
        return ResponseEntity.noContent().build();
    }

    /** La 1.0 quedó de solo lectura. Sin este método, escribir con 1.0 da un 404 "No static resource". */
    @Hidden   // no es parte del contrato: springdoc no lo publica en /v3/api-docs
    @RequestMapping(path = {"", "/{id}"}, method = {RequestMethod.POST, RequestMethod.PUT, RequestMethod.DELETE},
            version = "1.0")
    public void writeV1() {
        throw Problems.readOnlyVersion();
    }

    private static String etag(Book book) {
        return "\"" + book.version() + "\"";
    }

    /** If-Match: "3" → 3. Sin la cabecera no se escribe: 428 Precondition Required. */
    private static int version(String ifMatch) {
        if (ifMatch == null || ifMatch.isBlank()) {
            throw Problems.ifMatchRequired();
        }
        try {
            return Integer.parseInt(ifMatch.replace("W/", "").replace("\"", "").trim());
        } catch (NumberFormatException e) {
            throw Problems.ifMatchRequired();
        }
    }
}
La decisión
Un ETag fuerte con la versión de la fila, "3". Con ResponseEntity.ok().eTag(…), Spring compara solo el If-None-Match de un GET y responde 304 sin body cuando coincide.
Lo que descartas
ShallowEtagHeaderFilter, que calcula un hash del body ya generado. Ahorra ancho de banda pero no trabajo: la consulta, el JSON y el hash se hacen igual en cada request. Con la versión, el ETag sale de una columna.
Qué puede salir mal
La 1.0 y la 1.1 del mismo libro tienen el mismo ETag con bodies distintos. Para el cliente no importa, porque compara contra lo que él guardó, pero una caché compartida delante de la API tiene que separar por versión: la respuesta debería llevar Vary: API-Version, o el ETag incluir la versión de la API.

Paso 4. If-Match: no pisar el cambio de otro

El UPDATE del repositorio lleva la condición WHERE id = :id AND version = :expected. Si otro editor escribió antes, la versión ya no coincide, el update no toca ninguna fila y el servicio averigua por qué: si el libro existe, es un 412 con la versión actual; si no, un 404.

La decisión
Concurrencia optimista en una sola sentencia: comprobar y escribir es atómico porque lo hace el UPDATE, no un SELECT antes. Sin If-Match no se escribe: 428 Precondition Required. Documentado
Lo que descartas
SELECT … FOR UPDATE mientras el editor tiene el formulario abierto. Un lock no puede durar lo que tarda una persona en escribir, y detrás de PgBouncer en modo transacción ni siquiera sobrevive entre dos requests. Descartas también que gane el último: es lo que pasa si no haces nada, y el primer editor pierde su cambio sin enterarse.
Qué puede salir mal
Leer el libro, ver que la versión coincide y después actualizar, en dos sentencias. Entre las dos cabe la escritura de otro: los dos editores pasan la comprobación y el segundo pisa al primero.

El 412 lleva currentVersion para que el cliente pueda volver a leer, mostrarle al editor qué cambió y dejarlo decidir. La API no mezcla cambios: decide quién llegó primero y le avisa al otro.

Paso 5. Errores que se entienden

package lab.catalogo.books;

import java.net.URI;
import java.util.UUID;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.ErrorResponseException;

/** Los errores del dominio como ProblemDetail (RFC 9457), cada uno con un type estable. */
final class Problems {

    private static final String BASE = "https://catalogo.example/problemas/";

    private Problems() {
    }

    static ErrorResponseException notFound(UUID id) {
        return problem(HttpStatus.NOT_FOUND, "libro-inexistente", "No existe el libro " + id);
    }

    static ErrorResponseException staleVersion(UUID id, int sent, int current) {
        ErrorResponseException e = problem(HttpStatus.PRECONDITION_FAILED, "version-vieja",
                "El libro " + id + " cambió: enviaste la versión " + sent + " y la actual es " + current);
        e.getBody().setProperty("currentVersion", current);
        return e;
    }

    static ErrorResponseException badCursor() {
        return problem(HttpStatus.BAD_REQUEST, "cursor-invalido", "El cursor no es uno que hayamos emitido");
    }

    static ErrorResponseException readOnlyVersion() {
        return problem(HttpStatus.BAD_REQUEST, "version-de-solo-lectura",
                "La versión 1.0 solo admite lecturas: manda API-Version: 1.1 para escribir");
    }

    static ErrorResponseException ifMatchRequired() {
        return problem(HttpStatus.PRECONDITION_REQUIRED, "falta-if-match",
                "Para modificar un libro manda If-Match con el ETag que leíste");
    }

    private static ErrorResponseException problem(HttpStatus status, String slug, String detail) {
        ProblemDetail body = ProblemDetail.forStatusAndDetail(status, detail);
        body.setType(URI.create(BASE + slug));
        return new ErrorResponseException(status, body, null);
    }
}
package lab.catalogo.web;

import java.net.URI;
import java.util.Map;
import java.util.stream.Collectors;

import org.springframework.dao.DuplicateKeyException;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

/** Un solo lugar para los errores: todos salen como application/problem+json. */
@RestControllerAdvice
public class ApiErrors extends ResponseEntityExceptionHandler {

    /** Validación: además del 400, qué campo falló y por qué. */
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors().stream()
                .collect(Collectors.toMap(FieldError::getField,
                        e -> e.getDefaultMessage() == null ? "inválido" : e.getDefaultMessage(),
                        (a, b) -> a));
        ProblemDetail body = ex.getBody();
        body.setDetail("El libro tiene campos inválidos");
        body.setProperty("errors", errors);
        return handleExceptionInternal(ex, body, headers, status, request);
    }

    /** Un ISBN repetido: decide la restricción UNIQUE de la base, no un SELECT previo que dos requests pasarían a la vez. */
    @ExceptionHandler(DuplicateKeyException.class)
    ProblemDetail duplicate(DuplicateKeyException ex) {
        ProblemDetail body = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Ya existe un libro con ese ISBN");
        body.setType(URI.create("https://catalogo.example/problemas/isbn-repetido"));
        return body;
    }
}
La decisión
Cada error del dominio con un type propio y estable, como …/problemas/version-vieja. El cliente decide por el type, no por el texto de detail, que puedes reescribir cuando quieras. La validación agrega un mapa errors con el campo y el motivo.
Lo que descartas
Revisar si el ISBN existe con un SELECT antes del INSERT. Dos requests con el mismo ISBN pasan la revisión a la vez; la restricción UNIQUE de la base no se equivoca, y su DuplicateKeyException se convierte en un 409.
Qué puede salir mal
Dejar errores esperables sin manejar. Spring Boot no muestra la traza por defecto, pero una excepción que nadie atrapa sale como un 500 con el JSON genérico de Boot, sin type, y el cliente no puede distinguir un ISBN repetido de una base caída.

Paso 6. Dos versiones a la vez

package lab.catalogo.web;

import java.net.URI;
import java.time.ZonedDateTime;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.accept.StandardApiVersionDeprecationHandler;
import org.springframework.web.servlet.config.annotation.ApiVersionConfigurer;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

/** La versión llega en la cabecera API-Version; sin ella, el cliente recibe la 1.0. */
@Configuration
public class ApiVersioning implements WebMvcConfigurer {

    @Override
    public void configureApiVersioning(ApiVersionConfigurer configurer) {
        StandardApiVersionDeprecationHandler deprecations = new StandardApiVersionDeprecationHandler();
        deprecations.configureVersion("1.0")
                .setDeprecationDate(ZonedDateTime.parse("2026-10-01T00:00:00Z"))
                .setSunsetDate(ZonedDateTime.parse("2027-04-01T00:00:00Z"))
                .setSunsetLink(URI.create("https://catalogo.example/docs/migrar-a-1.1"));

        configurer.useRequestHeader("API-Version")
                .addSupportedVersions("1.0", "1.1")
                .setDefaultVersion("1.0")
                .setDeprecationHandler(deprecations);
    }
}
La decisión
La versión va en la cabecera API-Version, y cada método del controlador dice para qué versión es. La 1.0 sigue respondiendo lecturas con author como texto, avisa con Deprecation y Sunset cuándo se retira y no acepta escrituras.
Lo que descartas
/v1/books y /v2/books. Funciona y es lo más común, pero la versión pasa a ser parte de la identidad del recurso: el mismo libro tiene dos URLs, y los enlaces guardados apuntan a una versión para siempre.
Qué puede salir mal
La versión por defecto. Con setDefaultVersion("1.0"), un cliente nuevo que olvida la cabecera recibe la forma vieja y no se entera; con la 1.1 por defecto, los socios se rompen el día del despliegue. Se elige la vieja y se mide cuántas requests llegan sin cabecera antes del Sunset.

Sin el método writeV1, un POST con la 1.0 no encuentra ningún controlador y Spring responde un 404 "No static resource books.", que no explica nada. Con él, es un 400 que dice qué cabecera mandar. La anotación @Hidden lo deja fuera de /v3/api-docs: es una ayuda para los clientes perdidos, no parte del contrato.

Las cabeceras, a mano

curl -si -X POST localhost:8080/books -H 'API-Version: 1.1' -H 'Content-Type: application/json' \
  -d '{"title": "Dune", "authors": ["Frank Herbert"], "isbn": "9780441013593", "year": 1965}'
# HTTP/1.1 201, ETag: "1"

curl -si localhost:8080/books/$ID                      # sin API-Version: la 1.0
# Deprecation: @1790812800
# Sunset: Thu, 1 Apr 2027 00:00:00 GMT
# Link: <https://catalogo.example/docs/migrar-a-1.1>; rel="sunset"; type="text/html"
# {"id": "…", "title": "Dune", "author": "Frank Herbert", …}

curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/books/$ID -H 'If-None-Match: "1"'   # 304
curl -s localhost:8080/books -H 'API-Version: 3.0'     # 400: "Invalid API version: '3.0.0'."

@1790812800 es el formato de RFC 9745: los segundos desde 1970 del 1 de octubre de 2026, el día en que la 1.0 pasó a deprecada. Documentado El Sunset, de RFC 8594, dice cuándo deja de responder, y el Link con rel="sunset", dónde leer cómo migrar.

OFFSET contra el cursor, con un millón de filas

# Una sola vez: el ISBN es único.
# En Git Bash pon MSYS_NO_PATHCONV=1 delante, o convierte /scripts en una ruta de Windows.
docker compose exec postgres psql -U app -d app -f /scripts/un-millon.sql     # unos 15 s
docker compose exec postgres psql -U app -d app -c \
  "EXPLAIN (ANALYZE, BUFFERS) SELECT id, title FROM books ORDER BY title, id LIMIT 20 OFFSET 900000"
docker compose exec postgres psql -U app -d app -c \
  "EXPLAIN (ANALYZE, BUFFERS) SELECT id, title FROM books
   WHERE (title, id) > ('Libro 0899999', '<id de esa fila>') ORDER BY title, id LIMIT 20"

Los bloques son páginas de 8 KB que PostgreSQL leyó, de la caché o del disco. OFFSET 900 000 lee 20 938, unos 170 MB, para devolver 20 filas; el cursor lee 6, los mismos que la primera página. La forma con OR lee tantos bloques como el peor OFFSET porque PostgreSQL no la convierte en un rango del índice: recorre el índice desde el principio y filtra.

Trade-off

Con un cursor no hay "ir a la página 300", y el total de páginas cuesta un COUNT(*) sobre todo lo que filtra la búsqueda. Para un catálogo que se recorre hacia adelante, como un scroll infinito o una exportación, no importa. Para un panel de administración con saltos de página y pocas filas, OFFSET está bien.

Cómo conectar

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A00, el laboratorio

    La API de notas lista con ORDER BY id DESC LIMIT y no tiene página siguiente. Agrégale el cursor de este proyecto: como los ids son UUIDv7, el cursor es solo el id, WHERE id < :id, y vuelve a correr NotasSimulation pidiendo páginas profundas. Y si la llevas a producción detrás de PgBouncer, recuerda que la concurrencia optimista de este proyecto no necesita ningún lock que sobreviva a la transacción, justo lo que A00 mostró que no funciona.

  • Con A01, detrás de Nginx

    Pon el catálogo detrás del Nginx de A01. Si activas gzip para application/json, Nginx convierte los ETag fuertes en débiles al comprimir, W/"3". Documentado El 304 sigue funcionando, porque If-None-Match compara en forma débil, pero If-Match exige comparación fuerte según RFC 9110, y este proyecto acepta W/ por comodidad: decide si lo rechazas o si el ETag lo calcula Nginx después de comprimir. Y el límite de tasa de A01 protege las escrituras, que son las que cuestan.
