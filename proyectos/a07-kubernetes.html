Un servicio de cuentas no se puede cortar cada vez que lo despliegas. Vas a montar un clúster de Kubernetes de tres nodos en tu máquina, desplegar el servicio sin perder un request, verlo escalar solo con la carga y matarle el primario a la base para medir cuánto dura el corte.

La excusa

Un servicio de cuentas: registrarse, iniciar sesión y preguntar quién eres con el token. Todas las demás partes de un producto lo llaman, así que no se puede cortar para desplegar una versión nueva, ni cuando un nodo entra en mantenimiento, ni cuando se cae el primario de su base.

Tiene además una carga particular: cada inicio de sesión compara la contraseña con bcrypt, que gasta CPU a propósito. Con más usuarios hacen falta más pods, y es la CPU, no la base, la que dice cuántos. Kubernetes se encarga de las tres cosas si se lo pides bien: reemplazar pods sin cortar, sumar pods con la carga y, con un operador, promover la réplica de la base.

Tres nodos de verdad
Cada contenedor corre el mismo binario de k3s que instalarías en una máquina: server es el control plane y también acepta pods, y los dos agent se unen con K3S_TOKEN. Con tres nodos tiene sentido repartir pods, drenar uno y poner el primario y la réplica en nodos distintos.
Privilegiado
k3s arranca su propio containerd y maneja cgroups y redes dentro del contenedor, así que necesita privileged. Es un laboratorio: no lo hagas con contenedores que no controlas.
El kubeconfig, en tu carpeta
K3S_KUBECONFIG_OUTPUT lo escribe en cluster/kube/kubeconfig.yaml, apuntando a https://127.0.0.1:6443. --tls-san=127.0.0.1 mete esa dirección en el certificado del API.
Puertos
6443, el API de Kubernetes. 8080, el puerto 80 de Traefik: es la entrada de todos los requests. 5000, el registro de imágenes.
Versión fija
rancher/k3s:v1.36.5-k3s1 era la del canal estable de k3s al escribir esta guía, con Traefik en el chart 40.1.0.

/** El mismo 401 para "no existe ese correo" y "la contraseña no coincide": no le dice a nadie qué correos hay. */
public class Unauthorized extends ErrorResponseException {

    public Unauthorized() {
        super(HttpStatus.UNAUTHORIZED, problem(), null);
        getHeaders().set(HttpHeaders.WWW_AUTHENTICATE, "Bearer");
    }

    private static ProblemDetail problem() {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED,
                "Credenciales inválidas o sesión vencida");
        problem.setType(URI.create("https://cuentas.example/problemas/no-autorizado"));
        return problem;
    }
}
package lab.cuentas.accounts;

import java.time.OffsetDateTime;
import java.util.Optional;

import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
public class AccountRepository {

    public record Credentials(long id, String passwordHash) {
    }

    private final JdbcClient jdbc;

    public AccountRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    /** Vacío si el correo ya existe, sin importar mayúsculas: lo decide el índice único sobre lower(email). */
    public Optional<Account> insert(String email, String passwordHash) {
        return jdbc.sql("""
                INSERT INTO accounts (email, password_hash) VALUES (:email, :hash)
                ON CONFLICT ((lower(email))) DO NOTHING
                RETURNING id, email, created_at
                """)
                .param("email", email)
                .param("hash", passwordHash)
                .query(Account.class)
                .optional();
    }

    public Optional<Credentials> credentials(String email) {
        return jdbc.sql("SELECT id, password_hash FROM accounts WHERE lower(email) = lower(:email)")
                .param("email", email)
                .query(Credentials.class)
                .optional();
    }

    public void insertSession(byte[] tokenHash, long accountId, OffsetDateTime expiresAt) {
        jdbc.sql("INSERT INTO sessions (token_hash, account_id, expires_at) VALUES (:hash, :account, :expires)")
                .param("hash", tokenHash)
                .param("account", accountId)
                .param("expires", expiresAt)
                .update();
    }

    public Optional<Account> bySession(byte[] tokenHash) {
        return jdbc.sql("""
                SELECT a.id, a.email, a.created_at
                  FROM sessions s JOIN accounts a ON a.id = s.account_id
                 WHERE s.token_hash = :hash AND s.expires_at > now()
                """)
                .param("hash", tokenHash)
                .query(Account.class)
                .optional();
    }
}
package lab.cuentas.accounts;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.time.Duration;
import java.time.OffsetDateTime;
import java.time.ZoneOffset;
import java.util.Base64;

import lab.cuentas.AppProps;

import org.springframework.http.HttpStatus;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.web.server.ResponseStatusException;

@Service
public class AccountService {

    private final AccountRepository repo;
    private final BCryptPasswordEncoder encoder;
    private final Duration sessionTtl;
    private final SecureRandom random = new SecureRandom();
    /** Se compara contra este hash cuando el correo no existe, para que las dos respuestas tarden lo mismo. */
    private final String dummyHash;

    public AccountService(AccountRepository repo, AppProps props) {
        this.repo = repo;
        this.encoder = new BCryptPasswordEncoder(props.bcryptCost());
        this.sessionTtl = props.sessionTtl();
        this.dummyHash = encoder.encode("una contraseña que nadie tiene");
    }

    public Account register(String email, String password) {
        if (!fitsBcrypt(password)) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "La contraseña no puede pasar de 72 bytes");
        }
        // bcrypt cuesta CPU a propósito: con costo 10, su parte más cara da 2^10 = 1024 vueltas. Es lo que hace escalar este servicio.
        String hash = encoder.encode(password);
        return repo.insert(email, hash).orElseThrow(() ->
                new ResponseStatusException(HttpStatus.CONFLICT, "Ya existe una cuenta con ese correo"));
    }

    public Session login(String email, String password) {
        var credentials = repo.credentials(email);
        String hash = credentials.map(AccountRepository.Credentials::passwordHash).orElse(dummyHash);
        // Nadie se registró con más de 72 bytes: esa contraseña no coincide con ninguna, y el encoder ni la ve.
        boolean matches = fitsBcrypt(password) && encoder.matches(password, hash);
        if (credentials.isEmpty() || !matches) {
            throw new Unauthorized();
        }
        byte[] raw = new byte[32];
        random.nextBytes(raw);
        String token = Base64.getUrlEncoder().withoutPadding().encodeToString(raw);
        OffsetDateTime expiresAt = OffsetDateTime.now(ZoneOffset.UTC).plus(sessionTtl);
        // En la base solo queda el SHA-256 del token: quien lea la tabla no puede usar las sesiones.
        repo.insertSession(sha256(token), credentials.get().id(), expiresAt);
        return new Session(token, expiresAt);
    }

    public Account me(String authorization) {
        if (authorization == null || !authorization.startsWith("Bearer ")) {
            throw new Unauthorized();
        }
        return repo.bySession(sha256(authorization.substring(7))).orElseThrow(Unauthorized::new);
    }

    /** bcrypt solo usa los primeros 72 bytes, y en UTF-8 una ñ son dos: @Size cuenta caracteres, aquí se cuentan bytes. */
    static boolean fitsBcrypt(String password) {
        return password.getBytes(StandardCharsets.UTF_8).length <= 72;
    }

    static byte[] sha256(String token) {
        try {
            return MessageDigest.getInstance("SHA-256").digest(token.getBytes(StandardCharsets.UTF_8));
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
package lab.cuentas.accounts;

import java.net.URI;
import java.util.Map;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class AccountController {

    // bcrypt solo mira los primeros 72 bytes: una contraseña más larga se rechaza en vez de recortarse en silencio.
    // @Size cuenta caracteres; los bytes los revisa AccountService.fitsBcrypt.
    public record NewAccount(@NotBlank @Email String email, @NotBlank @Size(min = 8, max = 72) String password) {
    }

    public record Login(@NotBlank String email, @NotBlank String password) {
    }

    private final AccountService accounts;

    public AccountController(AccountService accounts) {
        this.accounts = accounts;
    }

    @PostMapping("/api/accounts")
    public ResponseEntity<Account> register(@Valid @RequestBody NewAccount body) {
        Account account = accounts.register(body.email(), body.password());
        return ResponseEntity.created(URI.create("/api/accounts/" + account.id())).body(account);
    }

    @PostMapping("/api/sessions")
    @ResponseStatus(HttpStatus.CREATED)
    public Session login(@Valid @RequestBody Login body) {
        return accounts.login(body.email(), body.password());
    }

    @GetMapping("/api/me")
    public Map<String, Object> me(@RequestHeader(name = HttpHeaders.AUTHORIZATION, required = false) String authorization) {
        Account account = accounts.me(authorization);
        return Map.of("id", account.id(), "email", account.email());
    }
}

/** Cada respuesta dice qué pod la atendió y con qué versión: así se ve el rolling update desde afuera. */
@Component
public class PodHeaders extends OncePerRequestFilter {

    private final String pod;
    private final String version;

    public PodHeaders(@Value("${POD_NAME:${HOSTNAME:local}}") String pod, AppProps props) {
        this.pod = pod;
        this.version = props.version();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        response.setHeader("X-Pod", pod);
        response.setHeader("X-Version", version);
        chain.doFilter(request, response);

La decisión
Reemplazar pods sin que nadie lo note. maxSurge: 1 y maxUnavailable: 0: primero arranca un pod nuevo, y solo cuando pasa la readiness se baja uno viejo. Al bajarlo, Kubernetes lo saca de los Endpoints y le corre el preStop a la vez; los 5 s de sleep le dan tiempo a Traefik para enterarse antes de que llegue el SIGTERM. Es la acción sleep del propio Kubernetes, así que la imagen no necesita traer el comando. Documentado Después, el apagado ordenado termina lo que estaba en curso. terminationGracePeriodSeconds: 30 cubre los 5 más los 20, con margen.
Lo que descartas
Poner la base en las probes. Si la liveness preguntara por la base, una caída del primario reiniciaría todos los pods a la vez, y tendrían que arrancar de nuevo justo cuando la base vuelve. Si la readiness preguntara por la base, el Gateway se quedaría sin pods y respondería 503 sin decir nada; así, cada pod responde un error claro a los 5 s de Hikari. También descartas replicas en el Deployment: lo decide el HPA, y cada kubectl apply lo volvería a fijar. Y, por ahora, blue-green y canary. Blue-green tiene dos Deployments completos y cambia la ruta de golpe; canary manda un porcentaje del tráfico a la versión nueva, con pesos en el HTTPRoute. Documentado Sirven para volver atrás en segundos o probar con poco tráfico, a cambio del doble de pods o de alguien que mueva los pesos.
Qué puede salir mal
Quitar el preStop porque "ya hay apagado ordenado". Sacar el pod de los Endpoints y mandarle el SIGTERM pasan al mismo tiempo, y Traefik tarda un momento en enterarse: sin la espera, algunos requests llegan a un pod que ya cerró el puerto, y Traefik responde 502. Lo vas a medir. Y requests.cpu sin limits.cpu deja que un pod use más CPU que la que pidió si el nodo la tiene libre, cosa que bcrypt aprovecha; la memoria sí tiene límite, y con -XX:MaxRAMPercentage=75 el heap puede crecer hasta 384 MiB de los 512. El resto queda para lo que la JVM usa fuera del heap, como los hilos y el metaspace.

    Iterator<Map<String, Object>> usuarios = Stream.generate(() ->
            Map.<String, Object>of("i", ThreadLocalRandom.current().nextInt(ACCOUNTS))).iterator();

            .feed(usuarios)
            .exec(http("POST sesión").post("/api/sessions")

# Registra una cuenta cada 100 ms y anota en qué segundo falla cada intento.
import json, sys, time, uuid, urllib.request, urllib.error
secs, out = float(sys.argv[1]), sys.argv[2]
t0 = time.time(); fails = []; ok = 0
while time.time() - t0 < secs:
    t = time.time() - t0
    body = json.dumps({"email": "w-%s@example.com" % uuid.uuid4().hex[:12], "password": "clave-larga-1"}).encode()
    req = urllib.request.Request("http://localhost:8080/api/accounts", data=body, headers={"content-type": "application/json"}, method="POST")
    try:
        urllib.request.urlopen(req, timeout=float(sys.argv[3]) if len(sys.argv) > 3 else 10).read(); ok += 1
    except urllib.error.HTTPError as e:
        fails.append((round(t, 1), e.code))
    except Exception as e:
        fails.append((round(t, 1), type(e).__name__))
    time.sleep(max(0, 0.1 - (time.time() - t0 - t)))
first, last = (fails[0][0], fails[-1][0]) if fails else (None, None)
summary = {"ok": ok, "fallas": len(fails), "primera": first, "última": last,
           "códigos": sorted({str(c) for _, c in fails})}
json.dump({"resumen": summary, "fallas": fails}, open(out, "w"))
print(json.dumps(summary, ensure_ascii=False))
La decisión
Dos mediciones distintas. Gatling mide lo que ve un usuario: registra 200 cuentas una vez y después inicia sesión y pregunta quién es, a un ritmo fijo o en rampa. escrituras.py mide cuándo se puede escribir en la base: un registro cada 100 ms, con un timeout corto, para ver el segundo exacto en que empieza y termina un corte. Cada corrida de Gatling deja su reporte en target/gatling/cuentassimulation-<fecha>/index.html, con los requests, los KO y los percentiles de cada request: las tablas de esta guía muestran esos números.
Lo que descartas
Medir el corte solo con Gatling. Sus inicios de sesión también escriben, pero un request que espera 30 s por una conexión aparece en el reporte como una latencia alta, no como un hueco con principio y fin.
Qué puede salir mal
Medir con la JVM fría: los primeros inicios de sesión tardan el doble. Antes de cada medición, deja pasar unos segundos de carga.

La segunda parte es tuya. El script corre en su propio reloj: el kill fue cerca de su segundo 10, así que la promoción cayó cerca del 30 en la primera corrida y del 29 en la segunda. Con los valores por defecto, las escrituras siguieron fallando hasta el 43.6, unos 14 s después de promover, cerca de los 15 s del server_connect_timeout, el plazo con que PgBouncer abandona un intento de conexión. Con los de esta guía, la última falla fue en el 31.3, unos 2 s después. El corte, de la primera a la última escritura fallida, bajó de 31.5 a 19.2 s. La medición no separa a PgBouncer de Hikari, porque cambiaron los dos juntos: si quieres saber cuánto pone cada uno, cambia uno por vez.

Después del failover, el operador vuelve a crear el primario viejo como réplica del nuevo, con pg_rewind si hace falta. Documentado Es lo que evita el split brain: un primario que vuelve no vuelve como primario. Espera a que el clúster esté Ready antes de repetir la prueba.

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A00, el laboratorio

    Es la misma división que en A00: la app pasa por PgBouncer en modo transaction, y Flyway va directo al primario por cuentas-db-rw, porque el SET de una migración y el ALTER TABLE que le sigue pueden caer en conexiones distintas del servidor. Y el workflow de A00 puede construir la imagen y empujarla a un registro con la etiqueta del commit, en vez de un número a mano.

  • Con A01, detrás de Nginx

    Traefik hace aquí lo que hacía Nginx en A01, con una diferencia: Nginx descubría una réplica caída por sus errores, con max_fails, y Traefik se entera por la readiness, antes de mandarle tráfico. El límite de tasa de A01 tiene su equivalente en un middleware RateLimit de Traefik, que el HTTPRoute usa con un filtro ExtensionRef. Documentado En el registro y el inicio de sesión tiene más sentido que en cualquier otra ruta: cada intento cuesta un bcrypt.

  • Con A02, una API que no se rompe

    Durante un rollout responden dos versiones a la vez, y lo mismo pasa con la base: Flyway corre la migración cuando arranca el primer pod nuevo, mientras los viejos siguen atendiendo. Cada migración tiene que funcionar con el código anterior, como la API vieja de A02 convive con la nueva hasta su Sunset: primero agregar, después usar y al final quitar. El 401 ya es un ProblemDetail con su type, como los errores de A02.

  • Con A03, caché que aguanta un pico

    /api/me es la lectura más caliente del servicio, y cada una va a la base. Una caché como la de A03, con la sesión por el hash del token y un TTL corto, la saca de ahí. Cerrar sesión pasa a ser una invalidación: si una réplica de la app no se entera, el token sigue sirviendo hasta que venza la entrada.

  • Con A04, primario y réplicas

    CloudNativePG hace los pasos del failover manual de A04: cerrarle el paso al primario viejo, promover la réplica, mover el tráfico, que aquí es mover el Service cuentas-db-rw, y volver a sumar el viejo como réplica. También crea cuentas-db-ro para leer de las réplicas. Si /api/me leyera de ahí, el problema de A04 vuelve: un usuario que acaba de iniciar sesión puede no encontrar su sesión en la réplica.

  • Con A05, dos primarios

    Cada sucursal de A05 sería un Cluster propio. CloudNativePG maneja la replicación lógica entre ellos con los recursos Publication y Subscription Documentado, en vez de los comandos de conectar.sh. Los conflictos de A05 siguen siendo tuyos: el operador sabe mover un primario, no decidir qué venta vale.

  • Con A06, repartir los datos

    Cada shard de A06 sería un Cluster con su Pooler, y un drain afectaría solo al shard de ese nodo. Pero la topología de A06 vive en memoria, y aquí el HPA corre entre 2 y 8 pods: cada uno tendría su propia idea de en qué fase va la migración. Antes de llevarla a Kubernetes, guárdala en un lugar compartido, con versión.
