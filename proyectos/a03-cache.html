Caché que aguanta un pico

Una tienda en su día de ofertas: diez productos se llevan ocho de cada diez visitas, y la ficha de cada uno cuesta 50 ms de base. Vas a escribir la caché a mano, en dos niveles, y a medir qué pasa cuando vence una clave caliente, cuando cambia un precio y cuando la app se cae a mitad de pasar las visitas a la base.

Al terminar podrás

  • Leer en tres escalones, la memoria de la réplica, Redis y PostgreSQL, y contar de dónde salió cada lectura.
  • Contener un cache stampede con un lock en Redis y sirviendo lo vencido, y medir cuántas veces llega a la base.
  • Repartir el vencimiento de las claves con jitter y avisar a las otras réplicas con Pub/Sub cuando cambia un precio.
  • Evitar que un lector lento deje en la caché un precio más viejo que el que se acaba de guardar.
  • Pasar un contador a la base en lotes con write-behind, sin perder ni duplicar visitas aunque la réplica muera a mitad.

La excusa

Una tienda en línea tiene mil productos y un día de ofertas: diez productos rebajados se llevan ocho de cada diez visitas. Armar la ficha de un producto cuesta 50 ms de base, porque junta reseñas, stock por bodega y opciones de envío. A 300 fichas por segundo, sin caché, serían 15 conexiones ocupadas todo el tiempo, de las 20 que hay, sin margen para el pico.

Hay dos datos más con reglas distintas. El precio cambia pocas veces, pero cuando cambia nadie debería ver el viejo por mucho tiempo. Las visitas de cada producto cambian todo el tiempo, y a nadie le importa si la base las ve unos segundos tarde.

package lab.ofertas.products;

import java.util.Optional;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
public class ProductRepository {

    private final JdbcClient jdbc;
    private final double delaySeconds;

    public ProductRepository(JdbcClient jdbc, @Value("${app.db-delay-ms}") long delayMs) {
        this.jdbc = jdbc;
        this.delaySeconds = delayMs / 1000.0;
    }

    /** La ficha. pg_sleep hace de la consulta cara de verdad: reseñas, stock por bodega y envíos. */
    public Optional<Product> find(long id) {
        return jdbc.sql("""
                SELECT id, name, price_cents, views, version
                  FROM products CROSS JOIN pg_sleep(:delay)
                 WHERE id = :id
                """)
                .param("id", id)
                .param("delay", delaySeconds)
                .query(Product.class)
                .optional();
    }

    public Optional<Product> updatePrice(long id, long priceCents) {
        return jdbc.sql("""
                UPDATE products SET price_cents = :price, version = version + 1
                 WHERE id = :id
                RETURNING id, name, price_cents, views, version
                """)
                .param("id", id)
                .param("price", priceCents)
                .query(Product.class)
                .optional();
    }
}
La decisión
Simular la consulta cara con pg_sleep dentro del mismo SELECT: la conexión queda ocupada 50 ms en la base, como con una consulta real, y el pool se llena igual.
Lo que descartas
Un Thread.sleep en Java. La request tardaría lo mismo, pero la conexión no estaría ocupada y no verías lo que importa: 20 conexiones para todas las cargas a la vez.
Qué puede salir mal
Creer que pg_sleep es una base cargada. Duerme sin gastar CPU ni disco. Una consulta real de 50 ms, repetida 200 veces a la vez, sí los gasta, y entonces todas tardan más. Por eso, en la estampida, mira cuántas veces se llega a la base y no solo la latencia.

Paso 2. Redis: fresco, vencido y versionado

package lab.ofertas.products;

import java.time.Duration;
import java.util.List;
import java.util.Optional;
import java.util.UUID;
import java.util.concurrent.ThreadLocalRandom;

import lab.ofertas.CacheProps;
import tools.jackson.databind.json.JsonMapper;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.RedisScript;
import org.springframework.stereotype.Component;

/** La caché compartida: un hash por producto con el JSON, la versión y hasta cuándo está fresco. */
@Component
public class RedisProducts {

    public record Entry(Product product, boolean fresh) {
    }

    // Escribe solo si lo guardado no es más nuevo. Así un lector lento no pisa el precio que se acaba de cambiar.
    private static final RedisScript<Long> PUT_IF_NOT_OLDER = RedisScript.of("""
            local current = redis.call('HGET', KEYS[1], 'version')
            if current and tonumber(current) > tonumber(ARGV[1]) then
              return 0
            end
            redis.call('HSET', KEYS[1], 'version', ARGV[1], 'json', ARGV[2], 'freshUntil', ARGV[3])
            redis.call('PEXPIRE', KEYS[1], ARGV[4])
            return 1
            """, Long.class);

    // Borra el lock solo si sigue siendo nuestro: si venció y lo tomó otro, no se lo quitamos.
    private static final RedisScript<Long> UNLOCK = RedisScript.of("""
            if redis.call('GET', KEYS[1]) == ARGV[1] then
              return redis.call('DEL', KEYS[1])
            end
            return 0
            """, Long.class);

    private static final Duration LOCK_TTL = Duration.ofSeconds(3);

    private final StringRedisTemplate redis;
    private final JsonMapper json;
    private final CacheProps props;

    public RedisProducts(StringRedisTemplate redis, JsonMapper json, CacheProps props) {
        this.redis = redis;
        this.json = json;
        this.props = props;
    }

    public Optional<Entry> get(long id) {
        List<Object> fields = redis.opsForHash().multiGet(key(id), List.of("json", "freshUntil"));
        if (fields.get(0) == null) {
            return Optional.empty();
        }
        Product product = json.readValue((String) fields.get(0), Product.class);
        boolean fresh = System.currentTimeMillis() < Long.parseLong((String) fields.get(1));
        return Optional.of(new Entry(product, fresh));
    }

    public boolean putIfNotOlder(Product product) {
        long ttl = jittered(props.ttl()).toMillis();
        long freshUntil = System.currentTimeMillis() + ttl;
        long keepFor = ttl + props.stale().toMillis();
        Long written = redis.execute(PUT_IF_NOT_OLDER, List.of(key(product.id())),
                Integer.toString(product.version()), json.writeValueAsString(product),
                Long.toString(freshUntil), Long.toString(keepFor));
        return Long.valueOf(1).equals(written);
    }

    /** Con jitter de 0.1, un ttl de 60 s queda entre 54 y 66 s: las claves cargadas juntas no vencen juntas. */
    Duration jittered(Duration ttl) {
        if (props.jitter() <= 0) {
            return ttl;
        }
        double factor = 1 + ThreadLocalRandom.current().nextDouble(-props.jitter(), props.jitter());
        return Duration.ofMillis(Math.round(ttl.toMillis() * factor));
    }

    public Optional<String> tryLock(long id) {
        String token = UUID.randomUUID().toString();
        Boolean acquired = redis.opsForValue().setIfAbsent(lockKey(id), token, LOCK_TTL);
        return Boolean.TRUE.equals(acquired) ? Optional.of(token) : Optional.empty();
    }

    public void unlock(long id, String token) {
        redis.execute(UNLOCK, List.of(lockKey(id)), token);
    }

    static String key(long id) {
        return "product:" + id;
    }

    private static String lockKey(long id) {
        return "lock:product:" + id;
    }
}

La decisión
Dos vencimientos. freshUntil, dentro del hash, dice hasta cuándo la ficha vale fresca: 60 s, más o menos un 10 % de jitter. PEXPIRE borra la clave 5 minutos después. Entre los dos, la ficha está vencida pero sigue ahí, para servirla mientras alguien la recarga.
Lo que descartas
Un solo TTL de Redis. Cuando vence, la clave desaparece, y todas las requests que llegan en ese instante encuentran el vacío a la vez. Con lo vencido a mano, solo una tiene que ir a la base.
Qué puede salir mal
Un lector lento pisa un precio nuevo. Lee la versión 4 de la base, se demora, y mientras tanto alguien guarda la versión 5 en la base y en Redis. Cuando el lector escribe su versión 4, la caché queda con el precio viejo durante un minuto. El script PUT_IF_NOT_OLDER compara versiones dentro de Redis, que ejecuta cada script de Lua sin intercalar otros comandos Documentado, y descarta la escritura vieja.

El jitter importa cuando muchas claves se cargan juntas, como al arrancar o después de vaciar Redis. Sin jitter, vencen juntas 60 s después, y la base recibe todas las recargas en el mismo segundo. Lo vas a medir.

Paso 3. Una sola carga en el pico

package lab.ofertas.products;

import java.util.Optional;

import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import lab.ofertas.CacheProps;
import lab.ofertas.lab.CacheStats;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.web.server.ResponseStatusException;

/** Lecturas en tres escalones: memoria de la réplica, Redis y PostgreSQL. */
@Service
public class ProductService {

    public static final String INVALIDATIONS = "products:invalidate";

    private final ProductRepository db;
    private final RedisProducts shared;
    private final StringRedisTemplate redis;
    private final CacheProps props;
    private final CacheStats stats;
    private final Cache<Long, Product> local;

    public ProductService(ProductRepository db, RedisProducts shared, StringRedisTemplate redis,
                          CacheProps props, CacheStats stats) {
        this.db = db;
        this.shared = shared;
        this.redis = redis;
        this.props = props;
        this.stats = stats;
        this.local = Caffeine.newBuilder().maximumSize(10_000).expireAfterWrite(props.localTtl()).build();
    }

    public Product get(long id) {
        Product inMemory = local.getIfPresent(id);
        if (inMemory != null) {
            stats.localHits.increment();
            return inMemory;
        }

        Optional<RedisProducts.Entry> cached = shared.get(id);
        if (cached.isPresent() && cached.get().fresh()) {
            stats.redisHits.increment();
            return remember(cached.get().product());
        }
        if (!props.stampedeProtection()) {
            return load(id);
        }

        Optional<String> lock = shared.tryLock(id);
        if (lock.isPresent()) {
            try {
                // Mira otra vez: quien tenía el lock pudo dejarla en Redis entre tu lectura y tu lock.
                Optional<RedisProducts.Entry> again = shared.get(id);
                if (again.isPresent() && again.get().fresh()) {
                    stats.redisHits.increment();
                    return remember(again.get().product());
                }
                return load(id);
            } finally {
                shared.unlock(id, lock.get());
            }
        }
        if (cached.isPresent()) {
            // Vencida, pero otra request ya la está recargando: servimos la vieja en lugar de esperar.
            stats.staleServed.increment();
            return remember(cached.get().product());
        }
        return waitForTheOneLoading(id);
    }

    /** Nada en Redis y otro tiene el lock: esperamos hasta medio segundo a que la deje ahí. */
    private Product waitForTheOneLoading(long id) {
        stats.waits.increment();
        for (int i = 0; i < 25; i++) {
            sleep(20);
            Optional<RedisProducts.Entry> cached = shared.get(id);
            if (cached.isPresent()) {
                return remember(cached.get().product());
            }
        }
        return load(id);   // el que cargaba tardó demasiado: mejor ir a la base que fallar
    }

    private Product load(long id) {
        stats.dbLoads.increment();
        Product product = db.find(id).orElseThrow(() ->
                new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe el producto " + id));
        shared.putIfNotOlder(product);
        return remember(product);
    }

    /** Write-through: la base y Redis quedan con el precio nuevo; las otras réplicas se enteran por Pub/Sub. */
    public Product updatePrice(long id, long priceCents) {
        Product updated = db.updatePrice(id, priceCents).orElseThrow(() ->
                new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe el producto " + id));
        shared.putIfNotOlder(updated);
        local.invalidate(id);
        if (props.pubsub()) {
            redis.convertAndSend(INVALIDATIONS, Long.toString(id));
        }
        return updated;
    }

    public void evictLocal(long id) {
        local.invalidate(id);
    }

    public void evictAllLocal() {
        local.invalidateAll();
    }

    private Product remember(Product product) {
        local.put(product.id(), product);
        return product;
    }

    private static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
La decisión
Cuando la ficha no está fresca, la request intenta tomar lock:product:{id} con SET NX y 3 s de vida. La que lo consigue mira otra vez Redis y, si sigue sin estar, carga de la base. Las demás sirven la ficha vencida si la hay, y si no, esperan hasta medio segundo a que aparezca.
Lo que descartas
Un lock en la memoria de cada réplica, como un ConcurrentHashMap de futuros. Funciona dentro de una réplica, y Caffeine lo hace solo con get(key, loader), pero con dos réplicas cargan dos, y con cuarenta, cuarenta. El lock en Redis lo comparten todas.
Qué puede salir mal
Dos cosas. Si la carga tarda más de 3 s, el lock vence, otra request lo toma y la primera, al terminar, no puede borrar un lock que ya no es suyo: por eso UNLOCK compara el token antes de borrar. Y si la carga tarda más de medio segundo, las que esperaban se cansan y van a la base, todas juntas. La espera tiene que ser mayor que la carga más lenta que aceptes.

La segunda mirada a Redis, dentro del lock, no es redundante. Entre que una request vio la ficha vencida y consiguió el lock, otra pudo cargarla y soltar el lock. Sin esa mirada, cada request que llega justo después de una carga haría otra.

package lab.ofertas.views;

import java.util.List;
import java.util.Map;
import java.util.UUID;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.data.redis.core.Cursor;
import org.springframework.data.redis.core.ScanOptions;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.RedisScript;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

/**
 * Write-behind: cada visita es un HINCRBY en Redis y un proceso las pasa a PostgreSQL en lotes.
 * Un lote se aparta con RENAME, se aplica en una transacción y recién después se borra.
 */
@Component
public class ViewCounter {

    private static final Logger log = LoggerFactory.getLogger(ViewCounter.class);

    static final String PENDING = "views:pending";
    static final String FLUSHING = "views:flushing:";

    private static final RedisScript<Long> RENAME_IF_EXISTS = RedisScript.of("""
            if redis.call('EXISTS', KEYS[1]) == 1 then
              redis.call('RENAME', KEYS[1], KEYS[2])
              return 1
            end
            return 0
            """, Long.class);

    private final StringRedisTemplate redis;
    private final ViewStore store;
    private final String haltAt;

    public ViewCounter(StringRedisTemplate redis, ViewStore store, @Value("${app.views.halt-at}") String haltAt) {
        this.redis = redis;
        this.store = store;
        this.haltAt = haltAt;
    }

    public void increment(long productId) {
        redis.opsForHash().increment(PENDING, Long.toString(productId), 1);
    }

    @Scheduled(fixedDelayString = "${app.views.flush-every-ms}")
    public void flush() {
        // Primero, los lotes que alguien apartó y no terminó: una réplica que se cayó a mitad de camino.
        try (Cursor<String> leftovers = redis.scan(ScanOptions.scanOptions().match(FLUSHING + "*").count(100).build())) {
            leftovers.forEachRemaining(this::flushBatch);
        }
        // Después, lo acumulado. Las visitas que lleguen desde ahora van a un views:pending nuevo.
        String batch = FLUSHING + UUID.randomUUID();
        if (Long.valueOf(1).equals(redis.execute(RENAME_IF_EXISTS, List.of(PENDING, batch)))) {
            haltIf("rename");
            flushBatch(batch);
        }
    }

    void flushBatch(String batch) {
        Map<Object, Object> counts = redis.opsForHash().entries(batch);
        if (!counts.isEmpty()) {
            long[] ids = new long[counts.size()];
            long[] views = new long[counts.size()];
            int i = 0;
            for (Map.Entry<Object, Object> e : counts.entrySet()) {
                ids[i] = Long.parseLong((String) e.getKey());
                views[i] = Long.parseLong((String) e.getValue());
                i++;
            }
            boolean applied = store.apply(batch.substring(FLUSHING.length()), ids, views);
            haltIf("commit");
            log.info("Lote {}: {} productos, {}", batch, ids.length, applied ? "aplicado" : "ya estaba aplicado");
        }
        redis.delete(batch);
    }

    /** Falla inyectada para el laboratorio: la réplica muere en seco en ese punto. */
    private void haltIf(String point) {
        if (point.equals(haltAt)) {
            log.warn("Falla inyectada: la réplica se detiene después de {}", point);
            Runtime.getRuntime().halt(1);
        }
    }
}
package lab.ofertas.views;

import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Transactional;

@Repository
public class ViewStore {

    private final JdbcClient jdbc;

    public ViewStore(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    /**
     * Aplica un lote una sola vez. Si la réplica se cae después del COMMIT y antes de borrar el lote
     * de Redis, el reintento encuentra el batch_id y no vuelve a sumar.
     */
    @Transactional
    public boolean apply(String batchId, long[] productIds, long[] counts) {
        int first = jdbc.sql("INSERT INTO view_flushes (batch_id) VALUES (:batch) ON CONFLICT DO NOTHING")
                .param("batch", batchId)
                .update();
        if (first == 0) {
            return false;
        }
        jdbc.sql("""
                UPDATE products p
                   SET views = p.views + v.n
                  FROM unnest(CAST(:ids AS bigint[]), CAST(:counts AS bigint[])) AS v(id, n)
                 WHERE p.id = v.id
                """)
                .param("ids", productIds)
                .param("counts", counts)
                .update();
        return true;
    }

    public long views(long productId) {
        return jdbc.sql("SELECT views FROM products WHERE id = :id").param("id", productId).query(Long.class).single();
    }
}
La decisión
Write-behind. Cada visita es un HINCRBY en views:pending, y cada 2 s la réplica aparta el hash con RENAME a un nombre único, lo aplica en la base en una transacción y recién entonces lo borra. Las visitas que llegan durante el lote van a un views:pending nuevo.
Lo que descartas
Un UPDATE products SET views = views + 1 por visita. A 300 visitas por segundo, 240 caen en los mismos diez productos, y cada UPDATE toma el lock de su fila: las visitas se forman en fila detrás del lock. En lote, son diez UPDATE cada 2 s.
Qué puede salir mal
La réplica muere entre el COMMIT y el borrado del lote. Al volver, encuentra el lote con SCAN y lo aplicaría de nuevo: el doble de visitas. La tabla view_flushes lo evita: el id del lote se guarda en la misma transacción que las visitas, y un lote que ya está ahí no se vuelve a sumar.

Las dos réplicas pasan lotes a la vez, y la una puede encontrar con SCAN el lote que la otra está aplicando en ese momento. No pasa nada: el segundo INSERT en view_flushes espera a que el primero confirme, no inserta nada, y ese lote no se suma dos veces. La idempotencia sirve para las caídas y para la concurrencia, con el mismo código.

Trade-off

En la laptop, la latencia de la estampida con y sin lock se parece: los pg_sleep no compiten por CPU, y 209 cargas de 50 ms en 20 conexiones son medio segundo. En una base real, esas 209 consultas compiten con todas las demás y la tienda entera se pone lenta. El lock cuesta la espera de unas pocas requests; la estampida, la base de todos.

El precio en la otra réplica

PUBSUB=false LOCAL_TTL=30s docker compose up -d app1 app2
curl -s localhost:8082/api/products/500 > /dev/null                 # app2 lo guarda en memoria
curl -s -X PUT localhost:8081/api/products/500/price \
  -H 'Content-Type: application/json' -d '{"priceCents": 20776}'      # app1 cambia el precio
for i in $(seq 1 35); do curl -s localhost:8082/api/products/500 | grep -o '"priceCents":[0-9]*'; sleep 1; done

Con un TTL local de 30 s, para que se note: sin Pub/Sub, app2 mostró el precio viejo durante 29 s, hasta que venció su memoria. Con Pub/Sub, la primera lectura de app2 después del cambio ya trajo el precio nuevo.

El jitter

TTL_JITTER=0 docker compose up -d app1 app2
docker compose exec redis redis-cli FLUSHALL
# Las mil fichas, 20 a la vez en cada réplica, con un solo curl por réplica
curl -sZ --parallel-max 20 "localhost:8081/api/products/[1-500]" > /dev/null &
curl -sZ --parallel-max 20 "localhost:8082/api/products/[501-1000]" > /dev/null; wait
docker compose exec -T redis redis-cli EVAL "local out = {} for _, k in ipairs(redis.call('KEYS', 'product:*')) \
  do table.insert(out, redis.call('HGET', k, 'freshUntil')) end return out" 0 \
  | awk '{ n[int($1 / 1000)]++ } END { for (s in n) if (n[s] > m) m = n[s]; print length(n), "segundos, pico de", m }'

Las mil fichas se cargaron en unos 3 s. Sin jitter, sus vencimientos cayeron en 4 segundos distintos, con un pico de unas 390 claves en el mismo segundo. Con el jitter de 0.1, en 15 o 16 segundos, con un pico de unas 100. Son las cifras de tres corridas en una laptop, y se repiten: sin jitter, el minuto siguiente trae el mismo pico que la carga inicial; con jitter, el pico baja a la cuarta parte.

Un curl por réplica con -Z manda las requests en paralelo desde un solo proceso. Con un curl por request, en Windows, solo arrancar los procesos tarda más de 20 s, y la carga se reparte sola en el tiempo: el jitter no se nota.

Falla: la réplica muere a mitad de un lote

docker compose stop app2                       # que solo app1 pase lotes
HALT_AT=commit docker compose up -d app1       # muere después del COMMIT, antes de borrar el lote
sleep 20                                       # que termine de arrancar
for i in $(seq 1 400); do                      # hasta que la réplica deje de responder
  curl -s -o /dev/null -w "%{http_code}\n" -X POST localhost:8081/api/products/777/views || break
done | grep -c 202                             # cuántas visitas aceptó antes de morir
docker compose exec redis redis-cli KEYS 'views:*'
docker compose up -d app1                      # sin HALT_AT: vuelve y encuentra el lote
docker compose logs app1 | grep Lote
docker compose exec postgres psql -U app -d app -c "SELECT views FROM products WHERE id = 777"

En el primer caso lo aplicó; en el segundo, el log dijo "ya estaba aplicado" y solo lo borró. La base terminó con las visitas aceptadas, ni una más ni una menos.

Cómo conectar

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A00, el laboratorio

    El paso de lotes no necesita un lock para correr en dos réplicas: RENAME es atómico y la tabla view_flushes descarta lo repetido. Compáralo con el advisory lock de sesión que A00 mostró filtrándose por PgBouncer. Si un día necesitas que un trabajo corra en una sola réplica, ya sabes que el lock va dentro de la transacción. Y las 984 cargas pasan por el mismo pool: dos réplicas con 10 conexiones de Hikari cada una, para las 20 reales de PgBouncer.

  • Con A01, detrás de Nginx

    Pon las dos réplicas detrás del Nginx de A01 y Gatling apuntando a https://localhost. Nginx puede agregar un escalón más, antes de la memoria de la réplica: proxy_cache guarda la respuesta entera unos segundos, y proxy_cache_lock on deja pasar una sola request por clave mientras se llena, que es la misma protección contra la estampida de este proyecto. Documentado El precio, en cambio, ya no se invalida con Pub/Sub en ese escalón: su TTL es el máximo que alguien puede ver el viejo.

  • Con A02, una API que no se rompe

    Cada ficha ya tiene version, la misma que usa PUT_IF_NOT_OLDER. Úsala como ETag, como en A02: un If-None-Match que coincide con la versión de la memoria de la réplica se responde con un 304 sin tocar Redis ni la base. Y el cambio de precio puede exigir If-Match, para que dos personas rebajando el mismo producto no se pisen.
