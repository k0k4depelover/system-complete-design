Detrás de Nginx

Un acortador de enlaces con tres réplicas, una de ellas lenta a propósito, detrás de un Nginx que termina TLS. Vas a medir cuánto cambia el algoritmo de balanceo, qué detecta Nginx solo y qué no detecta nunca.

Al terminar podrás

  • Poner Nginx delante de varias réplicas con TLS, HTTP/2 y conexiones keepalive hacia el upstream.
  • Hacer que la aplicación arme sus URLs con el esquema y el host que vio el cliente, y no con los del proxy.
  • Medir round robin contra least_conn con una réplica lenta y explicar por qué el p99 casi no cambia.
  • Ver cómo Nginx deja de mandar tráfico a una réplica que no responde, y por qué sin zone pagan el timeout tres veces más requests.
  • Cortar una ráfaga de escrituras con limit_req y un 429.

La excusa

Un acortador de enlaces: le das una URL larga, te devuelve una de siete caracteres, y quien abre la corta recibe un 302 hacia la larga. Casi todo el tráfico son redirecciones, que son lecturas baratas, así que el servicio escala agregando réplicas. Lo interesante no está en el código del acortador, que es corto, sino en lo que pasa entre el navegador y las réplicas.

Hay tres réplicas iguales salvo por un detalle: la tercera tarda 200 ms más en cada request, como una máquina con un disco que se está muriendo o un vecino ruidoso. Así es un día normal en producción: nada está caído, pero algo está lento.

Códigos de respuesta

  • 201Creado; Location es la URL corta.
  • 400La URL no empieza con http:// o https://, o es demasiado larga.
  • 429Lo responde Nginx: más de 10 escrituras por segundo desde tu IP, con una ráfaga de 20.
  • 502Ninguna réplica aceptó la conexión, ni siquiera en el reintento.
  • 504La réplica no respondió en 5 s. Un POST no se reintenta en otra.

Sin puertos en las réplicas
Las réplicas no publican el 8080: solo Nginx las alcanza, por la red interna de Compose, con los nombres app1, app2 y app3. Si las publicaras, alguien podría saltarse el límite de tasa y las cabeceras del proxy.
Flyway tres veces
Las tres réplicas corren Flyway al arrancar contra el mismo PostgreSQL. No se pisan: Flyway toma un lock en la base antes de migrar, y las otras dos esperan y encuentran la migración hecha.
La imagen
Un JRE de Java 25 y el jar. Construyes el jar con ./mvnw -DskipTests package antes de docker compose up --build.

El certificado es autofirmado, para localhost. Lo generas una vez con OpenSSL dentro de un contenedor, así no lo tienes que instalar:

mkdir -p nginx/certs
docker run --rm -v "$PWD/nginx/certs:/certs" alpine/openssl req -x509 -newkey rsa:2048 -nodes \
  -days 365 -keyout /certs/localhost.key -out /certs/localhost.crt \
  -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
# En Git Bash de Windows: MSYS_NO_PATHCONV=1 delante y "$(pwd -W)" en lugar de "$PWD".

Sin MSYS_NO_PATHCONV=1, Git Bash convierte /certs/localhost.key en una ruta de Windows antes de pasársela a Docker, y OpenSSL escribe en un lugar que no existe. Agrega nginx/certs/ al .gitignore: una clave privada no va al repositorio, ni siquiera una de prueba.

Paso 1. Códigos cortos que no chocan

CREATE TABLE links (
    code       varchar(7)  PRIMARY KEY,
    url        text        NOT NULL CHECK (length(url) <= 2048),
    created_at timestamptz NOT NULL DEFAULT now()

package lab.acortador.links;

import java.security.SecureRandom;

import org.springframework.stereotype.Component;

/** Códigos de 7 caracteres en base 62: 62^7 ≈ 3.5 billones de combinaciones. */
@Component
public class CodeGenerator {

    private static final String ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";
    private static final int LENGTH = 7;

    private final SecureRandom random = new SecureRandom();

    public String next() {
        StringBuilder code = new StringBuilder(LENGTH);
        for (int i = 0; i < LENGTH; i++) {
            code.append(ALPHABET.charAt(random.nextInt(ALPHABET.length())));
        }
        return code.toString();
    }
}
package lab.acortador.links;

import java.util.Optional;

import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
public class LinkRepository {

    private final JdbcClient jdbc;

    public LinkRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    /** Vacío si el código ya existía: ON CONFLICT evita la excepción y el rollback. */
    public Optional<Link> insert(String code, String url) {
        return jdbc.sql("""
                INSERT INTO links (code, url) VALUES (:code, :url)
                ON CONFLICT (code) DO NOTHING
                RETURNING code, url, created_at
                """)
                .param("code", code)
                .param("url", url)
                .query(Link.class)
                .optional();
    }

    public Optional<Link> find(String code) {
        return jdbc.sql("SELECT code, url, created_at FROM links WHERE code = :code")
                .param("code", code)
                .query(Link.class)
                .optional();
    }
}
package lab.acortador.links;

import java.util.Optional;

import org.springframework.stereotype.Service;

@Service
public class LinkService {

    private static final int MAX_ATTEMPTS = 5;

    private final LinkRepository links;
    private final CodeGenerator codes;

    public LinkService(LinkRepository links, CodeGenerator codes) {
        this.links = links;
        this.codes = codes;
    }

    public Link create(String url) {
        // Con un millón de enlaces, la chance de chocar es de 1 en 3.5 millones por intento.
        for (int attempt = 0; attempt < MAX_ATTEMPTS; attempt++) {
            Optional<Link> created = links.insert(codes.next(), url);
            if (created.isPresent()) {
                return created.get();
            }
        }
        throw new IllegalStateException("No se encontró un código libre en " + MAX_ATTEMPTS + " intentos");
    }

    public Optional<Link> find(String code) {
        return links.find(code);
    }
}
La decisión
Siete caracteres al azar en base 62, con SecureRandom, y INSERT … ON CONFLICT (code) DO NOTHING. Si el código ya existe, el insert no devuelve fila y el servicio prueba otro. 627 son unos 3.5 billones de códigos; con un millón de enlaces, un intento choca una vez en 3.5 millones.
Lo que descartas
Un id secuencial codificado en base 62. No choca nunca, pero los códigos se pueden recorrer: quien conoce aaaaab prueba aaaaac y lee los enlaces de otros. Descartas también capturar la excepción de clave duplicada: en PostgreSQL un error aborta la transacción, y ON CONFLICT lo evita.
Qué puede salir mal
Un bucle de reintentos sin tope. Si un día la tabla se llena o el generador se rompe y devuelve siempre lo mismo, el bucle no termina. Con 5 intentos, el servicio falla con un error claro.

Paso 2. La redirección y la URL corta

package lab.acortador.links;

import java.net.URI;

import jakarta.validation.Valid;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;
import org.springframework.web.servlet.support.ServletUriComponentsBuilder;

@RestController
public class LinkController {

    private final LinkService links;

    public LinkController(LinkService links) {
        this.links = links;
    }

    @PostMapping("/api/links")
    public ResponseEntity<LinkView> create(@Valid @RequestBody NewLink body) {
        LinkView view = view(links.create(body.url()));
        return ResponseEntity.created(URI.create(view.shortUrl())).body(view);
    }

    @GetMapping("/api/links/{code}")
    public LinkView get(@PathVariable String code) {
        return view(find(code));
    }

    /** La redirección. 302 y no 301: un 301 lo guarda el navegador y ya no vuelve a pasar por aquí. */
    @GetMapping("/{code:[0-9A-Za-z]{7}}")
    public ResponseEntity<Void> redirect(@PathVariable String code) {
        return ResponseEntity.status(HttpStatus.FOUND).location(URI.create(find(code).url())).build();
    }

    private Link find(String code) {
        return links.find(code).orElseThrow(() ->
                new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe el enlace " + code));
    }

    private static LinkView view(Link link) {
        // fromCurrentContextPath usa el esquema y el host que llegaron en X-Forwarded-Proto y X-Forwarded-Host.
        String shortUrl = ServletUriComponentsBuilder.fromCurrentContextPath()
                .path("/{code}").buildAndExpand(link.code()).toUriString();
        return new LinkView(link.code(), link.url(), shortUrl, link.createdAt());
    }
}

La decisión
302 Found. El navegador vuelve a pasar por el acortador cada vez, y puedes contar visitas, cambiar el destino o borrar un enlace abusivo.
Lo que descartas
301 Moved Permanently. Es más rápido para quien repite, porque el navegador lo guarda en su caché y no vuelve a preguntar, pero por eso mismo un 301 publicado no se puede deshacer. El 301 se queda para lo que de verdad es permanente, como pasar de HTTP a HTTPS.
Qué puede salir mal
Armar shortUrl con lo que la réplica cree que es su dirección: http://app1:8080/WOpCtYw. El cliente no conoce app1, y no llegó por HTTP. El paso 4 lo arregla.

Paso 3. Tres réplicas, una lenta

package lab.acortador.web;

import java.io.IOException;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

/** Marca cada respuesta con la réplica que la atendió y, si se pide, la hace lenta a propósito. */
@Component
public class InstanceFilter extends OncePerRequestFilter {

    private final String instance;
    private final long slowMs;

    public InstanceFilter(@Value("${app.instance}") String instance, @Value("${app.slow-ms}") long slowMs) {
        this.instance = instance;
        this.slowMs = slowMs;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        response.setHeader("X-Instance", instance);
        if (slowMs > 0 && !request.getRequestURI().startsWith("/actuator")) {
            try {
                Thread.sleep(slowMs);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
        chain.doFilter(request, response);
    }
}
La decisión
Un filtro que marca cada respuesta con X-Instance y que, si SLOW_MS es mayor que 0, duerme antes de atender. La lentitud es de la réplica entera, no de un endpoint, y no toca a /actuator, como pasa con una máquina degradada que sigue respondiendo su health check.
Lo que descartas
Apagar la réplica para simular una falla. Una réplica caída es el caso fácil: la conexión se rechaza y Nginx la saca enseguida. La réplica lenta es la que engaña a los balanceadores.
Qué puede salir mal
Olvidar el filtro en producción. X-Instance le dice a cualquiera cuántas réplicas tienes y cómo se llaman; en un servicio real, el id de la réplica va en los logs y en las trazas, no en la respuesta.

Paso 4. Nginx: TLS, keepalive y cabeceras

worker_processes auto;

events {
    worker_connections 1024;
}

http {
    # Una línea por request: a qué réplica fue y cuánto tardó cada tramo.
    log_format upstream '$remote_addr "$request" $status up=$upstream_addr '
                        'up_t=$upstream_response_time t=$request_time rid=$request_id';
    access_log /var/log/nginx/access.log upstream;

    # Límite de tasa por IP: 10 requests por segundo, con ráfagas de hasta 20.
    limit_req_zone $binary_remote_addr zone=por_ip:10m rate=10r/s;
    limit_req_status 429;

    upstream acortador {
        zone acortador 64k;                           # fallas y conexiones compartidas entre workers
        least_conn;                                   # bórrala para volver a round robin
        server app1:8080 max_fails=3 fail_timeout=10s;
        server app2:8080 max_fails=3 fail_timeout=10s;
        server app3:8080 max_fails=3 fail_timeout=10s;
        keepalive 32;                                 # conexiones abiertas hacia las réplicas
    }

    server {
        listen 80;
        server_name localhost;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl;
        http2 on;
        server_name localhost;

        ssl_certificate     /etc/nginx/certs/localhost.crt;
        ssl_certificate_key /etc/nginx/certs/localhost.key;
        ssl_protocols       TLSv1.2 TLSv1.3;

        # Se heredan en los dos location: keepalive real hacia upstream y las cabeceras X-Forwarded-*.
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Request-ID $request_id;

        proxy_connect_timeout 1s;
        proxy_read_timeout 5s;
        proxy_next_upstream error timeout http_502 http_503;
        proxy_next_upstream_tries 2;

        location /api/ {
            limit_req zone=por_ip burst=20 nodelay;
            proxy_pass http://acortador;
        }

        location / {
            proxy_pass http://acortador;
        }
    }
}

La decisión
Nginx termina TLS y habla HTTP/1.1 con keepalive hacia las réplicas: keepalive 32 en el upstream, más proxy_http_version 1.1 y Connection "". Las réplicas confían en X-Forwarded-* con server.forward-headers-strategy: native, y la URL corta sale con https://localhost.
Lo que descartas
TLS hasta cada réplica. Dentro de una red privada de Docker no protege de nada que importe en el laboratorio, y obliga a manejar certificados en cada réplica. En producción, con redes compartidas o requisitos de cumplimiento, se cifra también ese tramo, como explica M10.
Qué puede salir mal
Por defecto, Nginx habla HTTP/1.0 con el upstream y manda Connection: close: abre y cierra una conexión TCP por request, aunque escribas keepalive 32. Sin las dos líneas de proxy_*, el keepalive no hace nada y no lo vas a notar hasta que se acaben los puertos efímeros.

Tomcat solo acepta X-Forwarded-* cuando la request llega desde una IP privada, como la de Nginx en la red de Docker. Documentado Si el cliente manda X-Forwarded-For directo a una réplica desde internet, Tomcat lo ignora. Y Nginx no reemplaza lo que el cliente mandó: $proxy_add_x_forwarded_for lo agrega al final, así que la IP en la que puedes confiar es la última, la que puso tu proxy.

proxy_next_upstream error timeout http_502 http_503 reintenta en otra réplica cuando una falla o no responde en 5 s, como mucho una vez más (proxy_next_upstream_tries 2). No reintenta un POST que ya llegó al upstream: Nginx no reintenta métodos no idempotentes salvo que agregues non_idempotent. Documentado Sin esa regla, un timeout en la creación podría crear dos enlaces.

Paso 5. Un límite de tasa para las escrituras

En el mismo nginx.conf, limit_req_zone define una zona de 10 MB con un contador por IP, a 10 requests por segundo, y limit_req … burst=20 nodelay la aplica solo a /api/.

La decisión
Limitar solo las escrituras y la API, por IP, con una ráfaga de 20 que pasa sin esperar (nodelay) y un 429 para lo demás. Las redirecciones no tienen límite: son el producto.
Lo que descartas
Limitar en la aplicación. Cada réplica contaría por su lado, y con tres réplicas el límite real sería el triple. Nginx lo cuenta en una zona compartida entre sus workers; con varios Nginx necesitarías un contador central, por ejemplo en Redis.
Qué puede salir mal
Limitar por IP detrás de otro proxy o de una CDN. Todas las requests llegan con la IP de la CDN, y el límite se lo comen todos tus usuarios juntos. Ahí la IP real sale de una cabecera, con real_ip_header y set_real_ip_from para las IPs de la CDN y de nadie más.

limit_req es un leaky bucket: deja salir requests a ritmo constante y la ráfaga es el tamaño del balde. Se parece al token bucket de M08 y se configura igual en la práctica: un ritmo y un tamaño de ráfaga.

/** ./mvnw gatling:test -Dgatling.simulationClass=lab.acortador.RedirectSimulation -Drps=200 */
public class RedirectSimulation extends Simulation {

    int rps = Integer.getInteger("rps", 200);

    HttpProtocolBuilder protocolo = http
            .baseUrl(System.getProperty("baseUrl", "https://localhost"))
            .disableFollowRedirect()
            .shareConnections();

    // demo001 a demo100: los crea la migración V2.
    Iterator<Map<String, Object>> codigos = Stream.generate(() -> Map.<String, Object>of(
            "code", "demo%03d".formatted(ThreadLocalRandom.current().nextInt(1, 101)))).iterator();

    ScenarioBuilder redirigir = scenario("Redirigir")
            .feed(codigos)
            .exec(http("GET /{code}").get("/#{code}").check(status().is(302)));

    {
        setUp(redirigir.injectOpen(constantUsersPerSec(rps).during(60))).protocols(protocolo);
    }
}
La decisión
200 redirecciones por segundo durante 60 s sobre los cien enlaces fijos de la migración V2, sin seguir el 302 (disableFollowRedirect) y con shareConnections: los usuarios virtuales comparten un pool de conexiones, como lo haría un cliente HTTP con keepalive.
Lo que descartas
Una conexión por usuario virtual, que es lo que hace Gatling por defecto. Con 200 usuarios nuevos por segundo serían 200 handshakes TLS por segundo: medirías el costo de TLS y no el balanceo.

Round robin contra least_conn

Corre la carga con least_conn, después comenta esa línea, recarga Nginx sin reiniciarlo y vuelve a correrla. El log de Nginx dice a qué réplica fue cada request:

./mvnw gatling:test -Dgatling.simulationClass=lab.acortador.RedirectSimulation -Drps=200
docker compose logs nginx | grep -o 'up=[^ ]*' | sort | uniq -c

# round robin: comenta least_conn en nginx/nginx.conf y recarga
docker compose exec nginx nginx -s reload

Con 12 000 redirecciones y la tercera réplica 200 ms más lenta, en una laptop:

AlgoritmoA la lentap50p75p95p99Media
Round robin4 000 (33 %)7 ms206 ms210 ms244 ms77 ms
least_conn1 500 (12.5 %)7 ms9 ms209 ms213 ms35 ms

Round robin le da un tercio a cada réplica sin mirar nada, y desde el p75 todo es lento. least_conn ve que la réplica lenta tiene requests acumuladas y le manda menos: la media baja a menos de la mitad y el p75 vuelve a 9 ms. Pero el p95 y el p99 casi no cambian, porque una de cada ocho requests sigue yendo a la réplica lenta, y eso es más que el 5 % que mira el p95.

Trade-off

least_conn reduce cuánto tráfico recibe una réplica lenta, pero no la saca. Las fallas pasivas de Nginx tampoco: max_fails cuenta errores y timeouts, y una réplica que responde bien en 200 ms no comete ninguno. Para sacarla hace falta algo que compare latencias, como la detección de outliers de Envoy, o una persona mirando el p99 por réplica. M03 compara los algoritmos y explica por qué power of two choices se acerca a least_conn con menos estado.

Falla: una réplica que no responde

docker compose pause app2 congela la réplica: el kernel sigue aceptando conexiones TCP, pero nadie contesta. Es peor que apagarla, porque Nginx no recibe un rechazo y tiene que esperar el proxy_read_timeout de 5 s. Cada request lenta esperó los 5 s del timeout antes de que Nginx la reintentara en otra réplica. Nginx corre un worker por núcleo con worker_processes auto, 12 en la laptop de la medición, y sin zone cada worker lleva su propia cuenta de fallas y de conexiones abiertas: cada uno descubre por su lado que app2 no responde, y mientras tanto le sigue mandando requests. Con zone, las cuentas viven en memoria compartida y las ven todos los workers.

least_conn también ayuda aquí: mientras app2 tiene una request colgada, tiene más conexiones abiertas que las otras réplicas y no recibe la siguiente. Las 8 lentas que quedan se reparten a lo largo de los 30 s, porque un chequeo pasivo solo aprende con requests reales, y cada intento le cuesta 5 s a un usuario.

Qué pasa si falla

Los health checks activos, que prueban cada réplica con requests propias y la sacan antes de que la toque un usuario, son de la versión comercial, NGINX Plus, con la directiva health_check. Documentado Con el Nginx abierto tienes las fallas pasivas, un proxy_read_timeout tan corto como permitan tus requests más lentas, o un proxy que los traiga, como HAProxy o Envoy.
