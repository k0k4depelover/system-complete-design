Un solo líder

Un recordatorio tiene que salir una vez: ni cero, ni dos. Con tres réplicas, alguien tiene que decidir quién lo manda. Vas a elegir un líder con un Lease de Kubernetes, matarlo, congelarlo y contar lo que manda cuando despierta tarde, y a ver qué lo frena de verdad: el Lease, la clave de idempotencia o el fencing token.

La excusa

Una app de recordatorios: "avísame mañana a las 9 que tengo dentista". Cada recordatorio sale como un SMS por un proveedor externo que cobra por mensaje. Si sale dos veces, pagas dos veces y la persona se molesta. Si no sale, pierde el turno. Y si lo canceló, no puede salir.

La API corre en tres réplicas para no caerse con una. Pero si las tres despachan los vencidos, cada recordatorio sale hasta tres veces. Hace falta que despache una sola a la vez y que otra tome el turno en segundos si esa se cae: es la elección de líder. Lo difícil no es elegir. Es que un líder puede dejar de serlo sin enterarse: una pausa larga del recolector de basura, una máquina virtual congelada o una red que se corta. Cuando vuelve, sigue con lo que estaba haciendo.

DELETE /api/reminders/{id}

Cancela solo si el recordatorio no salió: el UPDATE exige delivered_at IS NULL. Cancelar dos veces no es un error. Lo que ya salió no se puede deshacer, y la API lo dice.

Códigos de respuesta

  • 404No existe.
  • 409Ya salió. Un ProblemDetail con detail "El recordatorio 1 ya salió: no se puede cancelar".
POST /v1/messages

El proveedor de mentira hace de la empresa que manda los SMS. Tarda 200 ms en aceptar cada mensaje y anota en la tabla messages todo lo que recibe, con quién lo mandó. Tiene dos defensas, y las activa quien llama: la clave de idempotencia y el fencing token.

Request

POST /v1/messages HTTP/1.1
Host: proveedor:8080
Content-Type: application/json
X-Sender: recordatorios-7d9f8c6b5-x2kqp_5e1f0a3b
Idempotency-Key: reminder-1
Fencing-Token: 3

{"reminderId": 1, "text": "Dentista a las 9", "dueAt": "…"}

Respuesta 201, un mensaje nuevo; 200 con "repeated": true si la clave ya había llegado

{"id": 1, "repeated": false}

Respuesta 409, en application/problem+json, si el token es más bajo que la valla

{"type": "https://proveedor.example/problemas/token-vencido", "title": "Token vencido", "status": 409,
 "detail": "El token 2 es más bajo que el último que recibí: hay un líder más nuevo", "instance": "/v1/messages"}

Códigos de respuesta

  • 201Mensaje nuevo: sale.
  • 200La clave ya estaba: no sale otra vez, solo se cuenta el intento en repeats.
  • 409Token vencido: el proveedor ya vio uno más alto.
PUT /v1/fence

Sube la valla del proveedor a este token. Desde ahí rechaza cualquier token más bajo. Un token igual pasa; bajarla no se puede.

Request

{"token": 3}

Códigos de respuesta

  • 204La valla quedó en ese token.
  • 409Ya estaba más alta: el mismo ProblemDetail de /v1/messages.

Trade-off

fabric8 7.9.0 trae por defecto un cliente HTTP sobre Vert.x 4.5.31, que está construido sobre Netty 4.1.136. Spring Boot 4.1.1 fija Netty en 4.2.17.Final, así que Maven le pondría a Vert.x 4.5 una versión de Netty que no se probó con él. Documentado fabric8 deja cambiar de cliente HTTP con una exclusión y otra dependencia Documentado: el de kubernetes-httpclient-jdk usa el HttpClient de Java y no trae Netty. Para un Lease que se renueva cada 2 s, alcanza de sobra.

La 8.0.0 salió el 24 de septiembre de 2026, con Jackson 3, Vert.x 5 y cambios incompatibles. Documentado Esta guía usa la 7.9.0, la última de la línea 7, que usa Jackson 2.21. Un solo nodo
En A07 hacían falta tres nodos para drenar uno. Para elegir un líder no: compiten procesos, no máquinas, y las tres réplicas compiten igual en un nodo. El contenedor corre el mismo binario de k3s que instalarías en una máquina: el control plane y los pods, juntos.
Privilegiado
k3s arranca su propio containerd y maneja cgroups y redes dentro del contenedor, así que necesita privileged. Es un laboratorio: no lo hagas con contenedores que no controlas.
El kubeconfig y los puertos
K3S_KUBECONFIG_OUTPUT lo escribe en cluster/kube/kubeconfig.yaml, apuntando a https://127.0.0.1:6443, la dirección que --tls-san mete en el certificado. El 8080 de tu máquina es el 80 de Traefik, y el 5000 es el registro de imágenes.

Una imagen, dos papeles
El perfil decide qué es cada proceso. Con recordatorios es la API y el despachador; con proveedor, el proveedor de mentira. Las clases de cada uno llevan @Profile, y las pruebas activan los dos en el mismo proceso.
Cuatro modos
app.leader.mode decide quién despacha: nadie, todas las réplicas, la dueña del Lease o la que tome el candado de ShedLock. Cada modo es una clase con @ConditionalOnProperty, así que cambiar de modo es cambiar una variable del Deployment.
Los tres plazos
Son los valores por defecto de kube-controller-manager: el Lease dura 15 s, el líder se rinde si no logra renovar en 10 s, y se intenta cada 2 s. Documentado fabric8 exige que leaseDuration sea mayor que renewDeadline, y este mayor que el reintento con su margen al azar.
El PID en un archivo
spring.pid.file lo escribe ApplicationPidFileWriter al arrancar. Los experimentos lo leen para congelar y matar a la JVM.
Apagado por fases
Al recibir SIGTERM, Spring detiene sus componentes por fases y espera hasta 20 s en cada una: primero el despachador, después el Lease y al final las requests HTTP. El orden se ve en el paso 5.

package lab.recordatorios.reminders;

import java.util.List;
import java.util.Optional;

import org.springframework.context.annotation.Profile;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
@Profile("recordatorios")
public class ReminderRepository {

    public record Range(long from, long to) {
    }

    private static final String COLUMNS = "id, text, due_at, delivered_at, cancelled_at, created_at";

    private final JdbcClient jdbc;

    public ReminderRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    public Reminder insert(String text, long inSeconds) {
        return jdbc.sql("""
                INSERT INTO reminders (text, due_at)
                VALUES (:text, now() + make_interval(secs => :inSeconds))
                RETURNING %s
                """.formatted(COLUMNS))
                .param("text", text)
                .param("inSeconds", inSeconds)
                .query(Reminder.class)
                .single();
    }

    /** Crea count recordatorios con el mismo texto, repartidos en spreadSeconds a partir de inSeconds. */
    public Range insertBatch(String text, int count, long inSeconds, double spreadSeconds) {
        return jdbc.sql("""
                WITH created AS (
                    INSERT INTO reminders (text, due_at)
                    SELECT :text, now() + make_interval(secs => :inSeconds + :spreadSeconds * (g - 1) / :count)
                      FROM generate_series(1, :count) AS g
                     ORDER BY g
                    RETURNING id
                )
                SELECT min(id), max(id) FROM created
                """)
                .param("text", text)
                .param("count", count)
                .param("inSeconds", inSeconds)
                .param("spreadSeconds", spreadSeconds)
                .query((rs, n) -> new Range(rs.getLong(1), rs.getLong(2)))
                .single();
    }

    public Optional<Reminder> find(long id) {
        return jdbc.sql("SELECT " + COLUMNS + " FROM reminders WHERE id = :id")
                .param("id", id)
                .query(Reminder.class)
                .optional();
    }

    /** true si lo canceló ahora; false si no existe, ya salió o ya estaba cancelado. */
    public boolean cancel(long id) {
        return jdbc.sql("""
                UPDATE reminders SET cancelled_at = now()
                 WHERE id = :id AND delivered_at IS NULL AND cancelled_at IS NULL
                """)
                .param("id", id)
                .update() == 1;
    }

    /** Los vencidos que faltan entregar, del más viejo al más nuevo. Usa el índice parcial reminders_pending. */
    public List<Reminder> due(int limit) {
        return jdbc.sql("""
                SELECT %s FROM reminders
                 WHERE due_at <= now() AND delivered_at IS NULL AND cancelled_at IS NULL
                 ORDER BY due_at, id
                 LIMIT :limit
                """.formatted(COLUMNS))
                .param("limit", limit)
                .query(Reminder.class)
                .list();
    }

    /**
     * Anota la entrega solo si nadie la anotó antes y nadie lo canceló: un compare-and-set.
     * false quiere decir que esta entrega sobró.
     */
    public boolean markDelivered(long id) {
        return jdbc.sql("""
                UPDATE reminders SET delivered_at = now()
                 WHERE id = :id AND delivered_at IS NULL AND cancelled_at IS NULL
                """)
                .param("id", id)
                .update() == 1;
    }
}

import java.util.Optional;

import org.springframework.context.annotation.Profile;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Transactional;

import lab.recordatorios.provider.ProviderController.Accepted;
import lab.recordatorios.provider.ProviderController.Message;

@Repository
@Profile("proveedor")
public class ProviderRepository {

    private final JdbcClient jdbc;

    public ProviderRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    /**
     * Anota un mensaje. La valla y el mensaje van en la misma transacción: el UPDATE de la valla
     * deja la fila bloqueada hasta el commit, y ningún token más bajo puede colarse en medio.
     */
    @Transactional
    public Accepted register(Long token, String key, String sender, Message message) {
        if (token != null) {
            raiseFence(token);
        }
        // Sin clave, idempotency_key queda en NULL y nunca choca: cada pedido es un mensaje nuevo.
        Optional<Long> id = jdbc.sql("""
                INSERT INTO messages (reminder_id, text, due_at, idempotency_key, fencing_token, sender)
                VALUES (:reminderId, :text, :dueAt, :key, :token, :sender)
                ON CONFLICT (idempotency_key) DO NOTHING
                RETURNING id
                """)
                .param("reminderId", message.reminderId())
                .param("text", message.text())
                .param("dueAt", message.dueAt())
                .param("key", key)
                .param("token", token)
                .param("sender", sender)
                .query(Long.class)
                .optional();
        if (id.isPresent()) {
            return new Accepted(id.get(), false);
        }
        // La clave ya estaba: el mensaje no sale otra vez. Solo se cuenta el intento.
        long existing = jdbc.sql("UPDATE messages SET repeats = repeats + 1 WHERE idempotency_key = :key RETURNING id")
                .param("key", key)
                .query(Long.class)
                .single();
        return new Accepted(existing, true);
    }

    /** Sube la valla a este token, o lanza StaleFencingToken si ya vio uno más alto. Un token igual pasa. */
    public void raiseFence(long token) {
        int updated = jdbc.sql("UPDATE fence SET token = :token WHERE resource = 'messages' AND token <= :token")
                .param("token", token)
                .update();
        if (updated == 0) {
            throw new StaleFencingToken(token);
        }
    }
}

La decisión
Un proveedor propio, para ver todo lo que llega: cada mensaje queda en messages con su remitente, su clave y su token. La clave de idempotencia funciona como la de Stripe en M27: la segunda vez que llega reminder-1, el proveedor responde 200 y no lo manda de nuevo. La valla guarda el token más alto que vio. El UPDATE de la valla y el INSERT del mensaje van en la misma transacción, y el UPDATE deja la fila de la valla bloqueada hasta el commit: entre comparar el token y anotar el mensaje no se puede colar otro remitente. Los 200 ms de espera van antes de la transacción, para no tener la valla bloqueada mientras tanto.
Lo que descartas
Comprobar el token en el despachador, antes de llamar. Es comprobar y después actuar: el líder viejo pasa la comprobación, se congela, y cuando despierta manda igual. La valla tiene que estar donde ocurre el efecto, en el que recibe la escritura. También descartas simular el proveedor solo en las pruebas: aquí quieres verlo con los tiempos del clúster.
Qué puede salir mal
Que creas que un proveedor real hace esto. Muchos aceptan una clave de idempotencia, pero casi ninguno acepta un fencing token: la valla solo puede vivir en algo que controlas, como tu propia base o un servicio tuyo delante del proveedor. Un pedido sin Fencing-Token se salta la valla, así que solo protege si todos los que escriben mandan token. Y la fila de la valla ordena todas las entregas en fila: a 5 por segundo no se nota, a miles por segundo sí, y harían falta una valla por recurso o por partición.

package lab.recordatorios.dispatch;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.OptionalLong;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.context.SmartLifecycle;
import org.springframework.web.client.RestClientException;

import lab.recordatorios.reminders.Reminder;
import lab.recordatorios.reminders.ReminderRepository;

/**
 * Entrega al proveedor los recordatorios vencidos, en lotes. No decide quién despacha ni cuándo:
 * eso lo hacen los schedulers de cada modo, que le pasan el token del turno si lo hay.
 */
public class Dispatcher implements SmartLifecycle {

    private static final Logger log = LoggerFactory.getLogger(Dispatcher.class);

    // El experimento de la caída: si existe este archivo, el proceso muere justo después de entregar
    // un recordatorio y antes de anotarlo, como si se cortara la luz en el peor momento.
    private static final Path CRASH_FLAG = Path.of(System.getProperty("java.io.tmpdir"), "detener-tras-entrega");
    private static final int MAX_FAILURES_IN_A_ROW = 3;

    private final ReminderRepository reminders;
    private final ProviderClient provider;
    private final int batchSize;
    private final boolean fencing;

    private final ReentrantLock batch = new ReentrantLock();
    private volatile boolean stopping;
    private long raised = -1;   // el último token con el que se subió la valla; solo se toca con el candado del lote

    public Dispatcher(ReminderRepository reminders, ProviderClient provider, int batchSize, boolean fencing) {
        this.reminders = reminders;
        this.provider = provider;
        this.batchSize = batchSize;
        this.fencing = fencing;
    }

    /** Entrega un lote y devuelve cuántos recordatorios quedaron anotados como entregados. */
    public int dispatchBatch(OptionalLong token) {
        if (stopping) {
            return 0;
        }
        OptionalLong sent = fencing ? token : OptionalLong.empty();
        batch.lock();
        try {
            // La valla sube al empezar el turno, no con la primera entrega: así frena al líder viejo
            // aunque el nuevo todavía no tenga nada que mandar.
            if (sent.isPresent() && sent.getAsLong() != raised) {
                try {
                    provider.raiseFence(sent.getAsLong());
                } catch (FencedOut e) {
                    log.warn("El proveedor rechazó el token {}: hay un líder más nuevo. No entrego nada.", e.token());
                    return 0;
                } catch (RestClientException e) {
                    log.warn("No se pudo subir la valla al token {} ({}); pruebo en la próxima vuelta",
                            sent.getAsLong(), e.getMessage());
                    return 0;
                }
                raised = sent.getAsLong();
                log.info("Valla subida al token {}", raised);
            }

            List<Reminder> due = reminders.due(batchSize);
            int marked = 0;
            int failures = 0;
            for (Reminder reminder : due) {
                if (stopping) {
                    break;
                }
                try {
                    provider.deliver(reminder, sent);
                } catch (FencedOut e) {
                    log.warn("El proveedor rechazó el token {}: hay un líder más nuevo. Dejo el lote.", e.token());
                    break;
                } catch (RestClientException e) {
                    log.warn("No se pudo entregar el recordatorio {} ({}); queda para el próximo lote",
                            reminder.id(), e.getMessage());
                    if (++failures == MAX_FAILURES_IN_A_ROW) {
                        break;
                    }
                    continue;
                }
                failures = 0;
                crashIfAsked(reminder);
                if (reminders.markDelivered(reminder.id())) {
                    marked++;
                } else {
                    log.warn("El recordatorio {} ya estaba entregado o cancelado: esta entrega sobró", reminder.id());
                }
            }
            if (!due.isEmpty()) {
                log.info("Lote: {} de {} anotados, token {}", marked, due.size(),
                        sent.isPresent() ? sent.getAsLong() : "ninguno");
            }
            return marked;
        } finally {
            batch.unlock();
        }
    }

    private void crashIfAsked(Reminder reminder) {
        try {
            if (Files.deleteIfExists(CRASH_FLAG)) {
                log.error("Encontré {}: me detengo después de entregar el recordatorio {} y antes de anotarlo",
                        CRASH_FLAG, reminder.id());
                Runtime.getRuntime().halt(1);
            }
        } catch (IOException e) {
            log.warn("No pude revisar {}: {}", CRASH_FLAG, e.getMessage());
        }
    }

    @Override
    public void start() {
        stopping = false;
    }

    // Spring lo llama al apagar, antes que a LeaseLeader: el lote en curso termina la entrega que tiene
    // en vuelo, la anota y no empieza otra. Recién después se suelta el Lease.
    @Override
    public void stop() {
        stopping = true;
        try {
            if (batch.tryLock(15, TimeUnit.SECONDS)) {
                batch.unlock();
            } else {
                log.warn("El lote no terminó en 15 s; sigo apagando");
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    @Override
    public boolean isRunning() {
        return !stopping;
    }
}

/** El cliente HTTP del proveedor de mensajes. Un 409 quiere decir que la valla rechazó el token. */
public class ProviderClient {

    public record Message(long reminderId, String text, OffsetDateTime dueAt) {
    }

    public record Fence(long token) {
    }

    private final RestClient http;
    private final String sender;
    private final boolean idempotent;

    public ProviderClient(String baseUrl, Duration timeout, String sender, boolean idempotent) {
        // HTTP/1.1 fijo: el proveedor habla HTTP/1.1, y así el cliente no intenta negociar HTTP/2.
        // El mismo plazo para conectar y para esperar la respuesta: pasado ese tiempo, la entrega cuenta como fallida.
        HttpClient client = HttpClient.newBuilder()
                .version(HttpClient.Version.HTTP_1_1)
                .connectTimeout(timeout)
                .build();
        JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory(client);
        factory.setReadTimeout(timeout);
        this.http = RestClient.builder().baseUrl(baseUrl).requestFactory(factory).build();
        this.sender = sender;
        this.idempotent = idempotent;
    }

    /** Manda un recordatorio. Con clave, el proveedor descarta lo repetido; con token, lo compara con su valla. */
    public void deliver(Reminder reminder, OptionalLong token) {
        http.post()
                .uri("/v1/messages")
                .headers(headers -> {
                    headers.set("X-Sender", sender);
                    if (idempotent) {
                        headers.set("Idempotency-Key", "reminder-" + reminder.id());
                    }
                    token.ifPresent(t -> headers.set("Fencing-Token", Long.toString(t)));
                })
                .contentType(MediaType.APPLICATION_JSON)
                .body(new Message(reminder.id(), reminder.text(), reminder.dueAt()))
                .retrieve()
                .onStatus(status -> status.value() == 409, (request, response) -> {
                    throw new FencedOut(token.orElse(-1));
                })
                .toBodilessEntity();
    }

    /** Sube la valla del proveedor a este token: desde ahí rechaza cualquier token más bajo. */
    public void raiseFence(long token) {
        http.put()
                .uri("/v1/fence")
                .contentType(MediaType.APPLICATION_JSON)
                .body(new Fence(token))
                .retrieve()
                .onStatus(status -> status.value() == 409, (request, response) -> {
                    throw new FencedOut(token);
                })
                .toBodilessEntity();
    }
}

El Dispatcher solo sabe entregar un lote: hasta 50 vencidos, del más viejo al más nuevo, con el índice parcial reminders_pending. Quién lo llama y con qué token lo decide el scheduler de cada modo. Mandar primero es entregar al menos una vez: si el proceso muere entre las dos cosas, el próximo líder lo manda otra vez, y la clave lo absorbe. La valla sube cuando cambia el token, al empezar el turno, no con la primera entrega: así frena al líder viejo aunque el nuevo no tenga nada que mandar.
Lo que descartas
Anotar primero y mandar después, que es entregar como mucho una vez: si muere en medio, el recordatorio se pierde sin que nadie lo note, y para un turno con el dentista es peor que un duplicado. Una transacción alrededor de mandar y anotar: el SMS no se deshace con un rollback, y la transacción tendría una conexión tomada 200 ms por recordatorio. Y, por ahora, SELECT … FOR UPDATE SKIP LOCKED, que deja despachar a las tres réplicas a la vez, cada una con filas distintas, sin líder: es una alternativa de verdad, y está en las decisiones guiadas.
Qué puede salir mal
El lote se lee una vez y se manda desde la memoria. Un recordatorio que la persona cancela después de la lectura sale igual, aunque el DELETE haya respondido 204: lo vas a provocar en el congelamiento corto. Y CRASH_FLAG es una puerta trasera para los experimentos: un archivo que hace morir al proceso. En un servicio real, sácala.

El método stop() es lo que hace el despachador cuando el pod se apaga: deja de empezar entregas, espera hasta 15 s a que termine la que está en vuelo y la anota. Como implementa SmartLifecycle con la fase por defecto, Spring lo detiene antes que al LeaseLeader del paso 5, que usa una fase menor. import java.util.OptionalLong;

import java.util.concurrent.CompletableFuture;

import io.fabric8.kubernetes.api.model.coordination.v1.Lease;

import org.springframework.context.SmartLifecycle;

/**
 * Compite por el Lease y sabe si este proceso es el líder. El token del turno es el contador
 * leaseTransitions del Lease: sube cada vez que el Lease cambia de dueño, y nunca baja.
 */
public class LeaseLeader implements SmartLifecycle {

    private static final Logger log = LoggerFactory.getLogger(LeaseLeader.class);

    private final KubernetesClient kubernetes;
    private final AppProps.Leader props;

    private volatile boolean running;
    private volatile boolean leader;
    private CompletableFuture<?> election;

    public LeaseLeader(KubernetesClient kubernetes, AppProps.Leader props) {
        this.kubernetes = kubernetes;
        this.props = props;
    }

    public boolean isLeader() {
        return leader;
    }

    /**
     * El token de este turno, leído del Lease. Vacío si este proceso no es el dueño según el API,
     * aunque crea serlo: es la última comprobación antes de despachar un lote.
     */
    public OptionalLong token() {
        if (!leader) {
            return OptionalLong.empty();
        }
        try {
            Lease lease = kubernetes.leases().inNamespace(props.namespace()).withName(props.lease()).get();
            if (lease == null || lease.getSpec() == null
                    || !Instance.ID.equals(lease.getSpec().getHolderIdentity())) {
                return OptionalLong.empty();
            }
            Integer transitions = lease.getSpec().getLeaseTransitions();
            return OptionalLong.of(transitions == null ? 0 : transitions);
        } catch (KubernetesClientException e) {
            log.warn("No pude leer el Lease {}: {}", props.lease(), e.getMessage());
            return OptionalLong.empty();
        }
    }

    @Override
    public synchronized void start() {
        running = true;
        compete();
    }

    // Un LeaderElector sirve para una sola elección. Cuando termina (este proceso perdió el Lease,
    // o no pudo renovarlo a tiempo), se arma otro y se vuelve a competir.
    private synchronized void compete() {
        if (!running) {
            return;
        }
        LeaderElectionConfig config = new LeaderElectionConfig(
                new LeaseLock(props.namespace(), props.lease(), Instance.ID),
                props.leaseDuration(), props.renewDeadline(), props.retryPeriod(),
                new LeaderCallbacks(this::onStartLeading, this::onStopLeading,
                        holder -> log.info("El Lease ahora es de {}",
                                holder == null || holder.isEmpty() ? "nadie" : holder)),
                true,   // releaseOnCancel: al apagarse, suelta el Lease en lugar de esperar a que venza
                "recordatorios");
        election = kubernetes.leaderElector().withConfig(config).build().start();
        election.whenComplete((ignored, error) -> {
            if (error != null && !(error instanceof CancellationException)) {
                log.warn("La elección terminó con un error: {}", error.toString());
            }
            compete();
        });
    }

    // Los dos callbacks corren en el hilo del LeaderElector, dentro de su sección sincronizada:
    // tienen que volver enseguida. Por eso solo cambian una bandera.
    private void onStartLeading() {
        leader = true;
        log.info("Soy el líder: {}", Instance.ID);
    }

    private void onStopLeading() {
        leader = false;
        log.info("Dejé de ser el líder: {}", Instance.ID);
    }

    @Override
    public void stop() {
        CompletableFuture<?> current;
        synchronized (this) {
            running = false;
            current = election;
        }
        // Cancelar la elección suelta el Lease en este mismo hilo: deja leaseDurationSeconds en 1,
        // y el próximo líder entra en segundos en lugar de esperar los 15 del vencimiento.
        if (current != null) {
            current.cancel(true);
        }
        leader = false;
    }

    @Override
    public boolean isRunning() {
        return running;
    }

    // Después del Dispatcher, que usa la fase por defecto: primero termina el lote, después suelta el Lease.
    @Override
    public int getPhase() {
        return SmartLifecycle.DEFAULT_PHASE - 1;
    }
}

import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;

/** Modo lease: todas las réplicas tienen el reloj andando, pero solo despacha la dueña del Lease. */
@Component
@Profile("recordatorios")
@ConditionalOnProperty(name = "app.leader.mode", havingValue = "lease")
public class LeaseScheduler {

    private final LeaseLeader leader;
    private final Dispatcher dispatcher;

    public LeaseScheduler(LeaseLeader leader, Dispatcher dispatcher) {
        this.leader = leader;
        this.dispatcher = dispatcher;
    }

    @Scheduled(fixedDelayString = "${app.dispatch.every-ms}")
    public void tick() {
        if (!leader.isLeader()) {
            return;
        }
        // El token se lee del Lease en cada vuelta, sin guardarlo: si este proceso perdió el Lease
        // y lo volvió a ganar, el número ya es otro.
        OptionalLong token = leader.token();
        if (token.isEmpty()) {
            return;
        }
        dispatcher.dispatchBatch(token);
    }
}

/**
 * Modo shedlock: en cada vuelta, la réplica que toma el candado de la tabla shedlock despacha un lote
 * y lo suelta. Las demás se saltan la vuelta. No hay token: ShedLock no da ninguno.

@Profile("recordatorios")
@ConditionalOnProperty(name = "app.leader.mode", havingValue = "shedlock")

    private final Dispatcher dispatcher;

    public ShedLockScheduler(Dispatcher dispatcher) {
        this.dispatcher = dispatcher;
    }

    // lockAtMostFor: si el dueño no lo suelta en ese plazo (murió, o está congelado), otra réplica lo toma.

    // El método tiene que ser público y no final: ShedLock lo envuelve con un proxy.
    @Scheduled(fixedDelayString = "${app.dispatch.every-ms}")
    @SchedulerLock(name = "recordatorios", lockAtMostFor = "${app.shedlock.lock-at-most-for}", lockAtLeastFor = "0s")

La decisión
ShedLock no elige un líder. En cada vuelta, la réplica que toma la fila recordatorios de la tabla shedlock despacha un lote y la suelta. Tomarla es un UPDATE que exige lock_until vencido, y soltarla exige locked_by igual a uno mismo. Con usingDbTime(), la hora la pone PostgreSQL, no cada réplica. Documentado Una réplica que no lo consigue se salta la vuelta, no espera. lockAtMostFor tiene que ser bastante más largo que lo que dura la tarea. Documentado Un lote de 50 tarda 50 × 200 ms = 10 s, y 20 s es el doble.
Lo que descartas
KeepAliveLockProvider, que extiende el candado mientras la tarea corre. Documentado Permite un lockAtMostFor corto sin cortar un lote largo, pero un proceso congelado no extiende nada, y al despertar sigue igual: no arregla al zombi. Y un token: ShedLock no da ninguno, así que no hay valla que subir.
Qué puede salir mal
Un lockAtMostFor más corto que el lote: el candado vence en medio, otra réplica lo toma y las dos mandan lo mismo, sin que nadie esté congelado. Que el dueño viejo no pueda soltar el candado de otro está bien, pero no le impide seguir entregando.

Empiezan sin defensas, con APP_DELIVERY_IDEMPOTENT y APP_DELIVERY_FENCING en false: los experimentos las encienden de a una. shareProcessNamespace pone a los contenedores del pod en el mismo espacio de procesos, y el proceso 1 pasa a ser el del sandbox del pod, no la JVM. Documentado Importa porque el kernel no deja que otro proceso del mismo espacio le mande SIGSTOP ni SIGKILL al proceso 1. Documentado Los 45 s de gracia cubren los 5 del preStop, los 15 del lote, soltar el Lease y los 20 del apagado ordenado.
Lo que descartas
Una liveness corta. Con 6 fallas cada 10 s, Kubernetes reinicia un contenedor que no responde en 60 s, y un congelamiento de 30 s no llega: el experimento necesita que el zombi despierte, no que lo reinicien. La readiness sí lo saca del Service a los pocos segundos, sin reiniciarlo.
Qué puede salir mal
Que el proveedor y las réplicas arranquen a la vez y corran Flyway contra la misma base: Flyway toma un candado antes de migrar, y el que llega segundo espera. Documentado Y que una réplica quede en CrashLoopBackOff por memoria: cada pod pide 384 MiB, y son cuatro, más PostgreSQL, PgBouncer, Traefik y k3s.

       count(*) AS messages,

       (max(received_at) AT TIME ZONE 'UTC')::time(0) AS last
  FROM messages
 WHERE text = :'texto'

 ORDER BY first;

--   duplicates: mensajes de más, el mismo recordatorio anotado dos o más veces por el proveedor.
--   absorbed: los repetidos que la clave de idempotencia frenó (no salieron).
--   cancelled_but_sent: los que llegaron después de cancelados.
SELECT (SELECT count(*) FROM reminders WHERE text = :'texto')                                AS reminders,
       (SELECT count(*) FROM reminders WHERE text = :'texto' AND cancelled_at IS NOT NULL)   AS cancelled,
       (SELECT count(*) FROM reminders
         WHERE text = :'texto' AND delivered_at IS NULL AND cancelled_at IS NULL)            AS pending,
       count(m.id)                                                                           AS messages,
       count(m.id) - count(DISTINCT m.reminder_id)                                           AS duplicates,
       coalesce(sum(m.repeats), 0)                                                           AS absorbed,
       count(*) FILTER (WHERE r.cancelled_at < m.received_at)                                AS cancelled_but_sent
  FROM messages m
  JOIN reminders r ON r.id = m.reminder_id
 WHERE m.text = :'texto';

       round(max(extract(epoch FROM received_at - due_at))::numeric, 2)                                                  AS max_s
  FROM messages
 WHERE text = :'texto';

Un relevo ordenado

Borrar el pod del líder es lo que pasa en cada despliegue y en cada drain. Con lider.sh corriendo en la otra terminal, crea 60 recordatorios repartidos en 30 s, deja que el líder trabaje 10 s y bórralo, guardando su log antes de que desaparezca:

mkdir -p target
curl -s -X POST localhost:8080/api/reminders/batch -H 'Content-Type: application/json' \
     -d '{"text": "relevo", "count": 60, "inSeconds": 0, "spreadSeconds": 30}'
sleep 10

Lo que tienes que ver, en orden. Durante los 5 s del preStop, el líder sigue despachando: todavía no recibió el SIGTERM. Después, en lider.sh, DURATION baja de 15 a 1: el líder soltó el Lease. Al final de su log aparecen su último "Lote", "El Lease ahora es de nadie" y "Dejé de ser el líder". Unos segundos después, HOLDER cambia a otra réplica y TRANSITIONS sube en 1.

La peor demora tiene una cota que se calcula. Desde que el Lease se suelta, vence en 1 s; una candidata lo nota en su próxima pregunta, como mucho 4.4 s después; despacha en su siguiente vuelta, hasta 1 s más; y el proveedor tarda 0.2 s. Son unos 1 + 4.4 + 1 + 0.2 = 6.6 s en el peor caso. Compara el max_s del informe con eso, y con la demora de "primero". duplicates tiene que dar 0: el despachador terminó y anotó la entrega que tenía en vuelo antes de soltar el Lease.

Falla: sin líder

El punto de partida que este proyecto evita: las tres réplicas despachan por su cuenta. Cambia el modo, espera el rollout y crea 30 recordatorios que vencen ya:

kubectl -n recordatorios set env deploy/recordatorios APP_LEADER_MODE=all
kubectl -n recordatorios rollout status deploy/recordatorios
curl -s -X POST localhost:8080/api/reminders/batch -H 'Content-Type: application/json' \
     -d '{"text": "sin-lider", "count": 30, "inSeconds": 0, "spreadSeconds": 0}'
sleep 15
scripts/informe.sh sin-lider

La cuenta antes de mirar. Cada réplica lee los vencidos en su próxima vuelta, y las tres vueltas caen dentro de 1 s. Entonces cada una manda todo lo que leyó, desde la memoria. La primera lee los 30. Una que lee hasta 1 s más tarde se encuentra con que la primera ya anotó como mucho 5, a 0.2 s cada uno, y manda al menos 25. En total salen entre 30 + 25 + 25 = 80 y 90 mensajes para 30 recordatorios: duplicates entre 50 y 60. Cada recordatorio queda anotado una sola vez, porque markDelivered es un compare-and-set, y eso es justo lo engañoso: la base dice que todo salió bien.

Repite con la clave encendida:

kubectl -n recordatorios set env deploy/recordatorios APP_DELIVERY_IDEMPOTENT=true
kubectl -n recordatorios rollout status deploy/recordatorios
curl -s -X POST localhost:8080/api/reminders/batch -H 'Content-Type: application/json' \
     -d '{"text": "sin-lider-clave", "count": 30, "inSeconds": 0, "spreadSeconds": 0}'

scripts/informe.sh sin-lider-clave
kubectl -n recordatorios set env deploy/recordatorios APP_LEADER_MODE=lease APP_DELIVERY_IDEMPOTENT=false

Ahora messages tiene que dar 30 y duplicates 0, con absorbed entre 50 y 60: la persona recibe un SMS por recordatorio, pero el proveedor atendió el triple de pedidos. Con un proveedor que no acepta claves, esos pedidos serían SMS, y los pagarías.

Falla: el líder se cae

Ahora sin aviso: kill -KILL a la JVM del líder, que no alcanza a soltar el Lease ni a terminar el lote. El contenedor se reinicia dentro del mismo pod, con otra identidad.

curl -s -X POST localhost:8080/api/reminders/batch -H 'Content-Type: application/json' \

En lider.sh, RENEW se congela en la última renovación y HOLDER sigue con la identidad muerta. La cuenta: esa renovación fue entre 0 y 2 s antes del kill, y el Lease vence 15 s después de ella, o sea entre 13 y 15 s después del kill. Una candidata lo nota en su próxima pregunta, hasta 4.4 s más tarde. El relevo tiene que llegar entre 13 y 19.4 s después del kill, y el max_s del informe, ser esa espera más hasta 1.2 s. Compáralo con el del relevo ordenado: la diferencia es lo que vale soltar el Lease al apagarse. El pod tiene que mostrar 1 en RESTARTS.

duplicates da 0 o 1: 1 si el kill llegó mientras una entrega esperaba la respuesta del proveedor, que la anotó igual, y el líder nuevo la mandó otra vez. Para provocarlo siempre, usa la bandera del despachador: el líder muere justo después de que el proveedor acepta un recordatorio, y antes de anotarlo.

Falla: el líder congelado

El caso que el Lease no resuelve. zombi.sh crea 100 recordatorios que vencen ya, espera 3 s a que el líder esté a mitad de su primer lote de 50, lo congela con kill -STOP, cancela del 26 al 50 a los 2 s, y lo despierta a los 30 s, cuando otra réplica ya tomó el turno:

#!/usr/bin/env bash
# El líder congelado. Crea 100 recordatorios que vencen ya, congela a la réplica que los está entregando,
# cancela del 26 al 50 mientras duerme y la despierta. Al final, el informe.
# Uso: scripts/zombi.sh <texto, una palabra> [lease|shedlock] [segundos congelado, 30 por defecto]
# Las horas van en UTC, como las de PostgreSQL y las del Lease.
set -euo pipefail
cd "$(dirname "$0")"

TEXTO=${1:?Uso: scripts/zombi.sh <texto> [lease|shedlock] [segundos]}
MODO=${2:-lease}
CONGELADO=${3:-30}
NS=recordatorios
[ "$CONGELADO" -gt 2 ] || { echo "El congelamiento tiene que durar más de 2 s"; exit 1; }
val() { ./psql.sh -qtA -c "$1" | tr -d '\r'; }
# Espera hasta que pasen N segundos desde el congelamiento: cada llamada a kubectl también tarda.
hasta() { while [ "$SECONDS" -lt "$1" ]; do sleep 0.2; done; }

# 1. Cien recordatorios que vencen ya, con ids seguidos.
RANGO=$(curl -s -X POST http://localhost:8080/api/reminders/batch -H 'Content-Type: application/json' \
  -d "{\"text\": \"$TEXTO\", \"count\": 100, \"inSeconds\": 0, \"spreadSeconds\": 0}")
DESDE=$(echo "$RANGO" | sed -E 's/.*"from": *([0-9]+).*/\1/')
echo "$(date -u +%T) Creados: $RANGO"

# 2. Tres segundos para que el despachador empiece el lote; después, quién lo tiene.
sleep 3
if [ "$MODO" = shedlock ]; then
  DUENO=$(val "SELECT locked_by FROM shedlock WHERE name = 'recordatorios' AND lock_until > timezone('utc', now())")
else
  DUENO=$(kubectl -n $NS get lease recordatorios-lider -o jsonpath='{.spec.holderIdentity}')
fi
POD=${DUENO%_*}
[ -n "$POD" ] || { echo "Nadie tiene el turno: ¿las réplicas corren en modo $MODO?"; exit 1; }

# 3. Congelarlo: la JVM no ejecuta nada más hasta el SIGCONT, pero sus conexiones siguen abiertas.
kubectl -n $NS exec "$POD" -c app -- sh -c 'kill -STOP $(cat /tmp/app.pid)'
SECONDS=0
ANOTADOS=$(val "SELECT count(*) FROM reminders WHERE text = '$TEXTO' AND delivered_at IS NOT NULL")
echo "$(date -u +%T) Congelé a $DUENO; alcanzó a anotar $ANOTADOS"

# 4. A los 2 s, la persona cancela del 26 al 50. Por SQL, con el mismo UPDATE que el DELETE de la API:
#    el pod congelado sigue en el Service hasta que falle su readiness, y una request que le toque se quedaría esperando.
hasta 2
val "UPDATE reminders SET cancelled_at = now()
      WHERE id BETWEEN $((DESDE + 25)) AND $((DESDE + 49)) AND delivered_at IS NULL AND cancelled_at IS NULL" > /dev/null
echo "$(date -u +%T) Cancelé del $((DESDE + 25)) al $((DESDE + 49))"

# 5. Despertarlo cuando termine el congelamiento.
hasta "$CONGELADO"
kubectl -n $NS exec "$POD" -c app -- sh -c 'kill -CONT $(cat /tmp/app.pid)'
echo "$(date -u +%T) Desperté a $DUENO después de unos $SECONDS s"

# 6. Esperar a que termine lo que tenía en vuelo, y el informe.
sleep 20
./informe.sh "$TEXTO"

Falla: un congelamiento corto

Con la clave y la valla encendidas, congela 5 s en vez de 30:

scripts/zombi.sh corto lease 5

La cuenta, antes de mirar. La última renovación fue como mucho 2 s antes del congelamiento, así que al despertar, unos 5 o 6 s después, pasaron como mucho unos 8 s: menos que los 10 s de renewDeadline, y A renueva. Las candidatas necesitan 15 s sin renovación, así que nadie toma el turno. En lider.sh, RENEW se detiene unos segundos y vuelve, con el mismo HOLDER y el mismo TRANSITIONS. Nadie subió la valla, y A, que sigue siendo el líder legítimo, manda su lote desde la memoria: tiene que dar messages 100, duplicates 0 y cancelled_but_sent 25. Si aun así HOLDER cambia, cada kubectl exec tarda más en tu máquina y el congelamiento real se alargó: repite con scripts/zombi.sh corto2 lease 3.

La valla frena a un líder viejo, no a un líder lento. Aquí el problema no es de liderazgo: el lote se leyó antes de la cancelación y se mandó después. Para arreglarlo, la carrera tiene que decidirse en la base, donde una fila solo puede estar en un estado. El despachador reclama cada recordatorio justo antes de mandarlo, y la cancelación solo gana si llega antes del reclamo:

-- V4: el reclamo
ALTER TABLE reminders ADD COLUMN claimed_at timestamptz;

-- El despachador, antes de cada entrega: si no actualiza una fila, el recordatorio no sale.
UPDATE reminders SET claimed_at = now()
 WHERE id = :id AND delivered_at IS NULL AND cancelled_at IS NULL
   AND (claimed_at IS NULL OR claimed_at < now() - interval '1 minute');

-- La cancelación, en vez de exigir delivered_at IS NULL: si ya está reclamado, 409.
UPDATE reminders SET cancelled_at = now()
 WHERE id = :id AND claimed_at IS NULL AND delivered_at IS NULL AND cancelled_at IS NULL;

El reclamo vence al minuto para que un despachador que muere después de reclamar no deje el recordatorio trabado: lo retoma el siguiente, y si el primero alcanzó a mandarlo, la clave absorbe el repetido. A la persona que cancela tarde le cuesta un 409 en lugar de un 204, pero ese 409 dice la verdad. Implementarlo es un cambio en ReminderRepository y una línea en el bucle del Dispatcher; hazlo al terminar los experimentos, porque cambia sus cuentas.

Cómo conectar

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A00, el laboratorio

    Es la misma división que en A00: la app pasa por PgBouncer en modo transaction y Flyway va directo al primario. ShedLock convive bien con ese modo, porque toma y suelta el candado con sentencias sueltas, sin estado de sesión. Un advisory lock de sesión, la otra forma clásica de elegir líder en PostgreSQL, es justo lo que A00 mostró que se rompe detrás de PgBouncer.

  • Con A01, detrás de Nginx

    El balanceador reparte la API entre las tres réplicas y no sabe quién es el líder, ni tiene por qué: el liderazgo es para el trabajo de fondo, no para el tráfico. Si alguna vez una ruta tiene que llegar solo al líder, es una señal de que esa ruta es trabajo de fondo.

  • Con A02, una API que no se rompe

    El 409 de la cancelación es un ProblemDetail como los de A02, y la clave de idempotencia es la misma idea que el If-Match: una escritura que dice con qué estado cuenta, y que el servidor rechaza si el estado cambió.

  • Con A03, caché que aguanta un pico

    El candado SET NX de A03 contra el cache stampede es un líder de corta duración: uno recalcula y los demás esperan. Si el que recalcula se congela, otro lo hace cuando vence la clave, y el viejo escribe un valor viejo al despertar. Ahí no hay valla, pero el daño dura un TTL; aquí, un SMS no se borra.

  • Con A04, primario y réplicas

    La lectura de los vencidos y la valla tienen que ir al primario. Si el despachador leyera los pendientes de una réplica con lag, volvería a mandar recordatorios que el primario ya tiene anotados: el compare-and-set salvaría la marca, pero el SMS ya habría salido.

  • Con A05, dos primarios

    Dos sucursales que despachan cada una sus recordatorios son dos líderes a propósito, y funcionan por la misma regla de A05: cada fila tiene una sucursal dueña, y solo la dueña la despacha. Sin esa regla, cada recordatorio replicado sale dos veces.

  • Con A06, repartir los datos

    Con muchos recordatorios, un solo líder no alcanza. Un Lease por shard, recordatorios-lider-0, -1 y así, deja que cada réplica lidere algunos, con un token y una valla por shard. Y la migración de A06, que hoy vive en la memoria de una réplica, es trabajo para un líder: una sola réplica tiene que llevarla.

  • Con A07, Kubernetes

    Es el mismo clúster con un nodo en lugar de tres. Con los tres nodos de A07, drena el nodo del líder: el drain borra el pod, y el relevo es el ordenado, con el Lease soltado. El PodDisruptionBudget de A07 no protege al líder en particular: protege a la cantidad de réplicas.
