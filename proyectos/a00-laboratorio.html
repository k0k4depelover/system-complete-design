La excusa

Una API de notas: crear una, leer una y listar las últimas. Es tan chica que no distrae, y por eso sirve para fijar lo que todos los proyectos siguientes repiten sin volver a explicarlo: las versiones, la base de datos con su pooler, las migraciones, las pruebas, la integración continua y la forma de medir.

Esta guía no explica cómo crear un proyecto de Spring. Supone que sabes REST, SQL y Docker, y se concentra en las decisiones que no son obvias: dónde se conecta cada cosa, qué rompe un pooler en modo transacción y cómo se escribe una prueba de carga que diga algo.

Crea una nota. PostgreSQL pone el id, un UUIDv7, y la fecha.

{"id": "01a0ff11-26a5-7be7-b07a-dbe6a682e77f", "title": "Primera", "body": "Hola",

Códigos de respuesta

  • 201Creada; Location apunta a la nota nueva.
  • 400Título vacío o de más de 200 caracteres, o body de más de 10 000.

Puerto 5433

Si tienes un PostgreSQL instalado en tu sistema, ya ocupa el 5432. Con el contenedor en el 5432, Flyway se conecta al equivocado y falla con "la autentificación password falló para el usuario app". Publicarlo en el 5433 evita la confusión.

El volumen

Desde la imagen 18, los datos viven en /var/lib/postgresql/18/docker, así que el volumen se monta en /var/lib/postgresql. Si lo montas en .../data, como en las versiones anteriores, el contenedor no arranca. Documentado

POOL_MODE: transaction

PgBouncer le presta una conexión del servidor a un cliente solo mientras dura una transacción. Con 20 conexiones reales atiende a cientos de clientes, pero lo que vive en la sesión deja de ser tuyo: lo vas a medir en Cómo comprobar que funciona.

DEFAULT_POOL_SIZE: 20

Las conexiones reales con PostgreSQL por cada par de usuario y base. Cada una es un proceso del servidor con su memoria; el límite protege a la base.

Paso a paso

Cada paso dice qué decides, qué descartas y qué puede salir mal. El código completo de cada archivo está en el paso; si quieres escribirlo tú, lee la decisión y vuelve al código solo para comparar.

Paso 1. Fija las versiones

Crea el proyecto con Spring Initializr o a mano, con Java 25 y Spring Boot 4.1.1, y deja en el pom solo las dependencias de la tabla anterior.

La decisión
Versiones exactas en el pom (4.1.1, 3.16.0) y en las imágenes (postgres:18, edoburu/pgbouncer:v1.26.0-p0).
Lo que descartas
latest en las imágenes. Funciona hoy y se rompe el día que sale una versión mayor, sin que nadie haya tocado el repositorio.
Qué puede salir mal
Mezclar guías viejas de Spring Boot 3 con este pom. Los nombres cambiaron: spring-boot-starter-web pasó a spring-boot-starter-webmvc, Flyway necesita su starter, y los paquetes de pruebas de MVC se movieron a org.springframework.boot.webmvc.test.

Paso 2. Levanta la base y su pooler

docker compose up -d
docker compose ps                     # los dos en running; postgres, además, healthy

PgBouncer tiene una consola propia: una base virtual llamada pgbouncer. Entra con el usuario de ADMIN_USERS y mira los pools:

Paso 3. La tabla, con Flyway directo a PostgreSQL

-- uuidv7() es nativa desde PostgreSQL 18: ids que no se adivinan y que crecen con el tiempo.
CREATE TABLE notes (
    id         uuid        PRIMARY KEY DEFAULT uuidv7(),
    title      text        NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
    body       text        NOT NULL DEFAULT '',
    created_at timestamptz NOT NULL DEFAULT now()
);
spring:
  application:
    name: notas
  datasource:
    # La aplicación habla con PgBouncer (6432), nunca directo con PostgreSQL.
    url: ${DB_URL:jdbc:postgresql://localhost:6432/app}
    username: ${DB_USER:app}
    password: ${DB_PASSWORD:app}
    hikari:
      maximum-pool-size: 10
      connection-timeout: 3000     # milisegundos: esperar más un pool lleno solo esconde el problema
  flyway:
    # Las migraciones van directo a PostgreSQL (5433 en tu máquina): necesitan una sesión propia.
    url: ${FLYWAY_URL:jdbc:postgresql://localhost:5433/app}
    user: ${DB_USER:app}
    password: ${DB_PASSWORD:app}
  mvc:
    problemdetails:
      enabled: true

management:
  endpoints:
    web:
      exposure:
        include: health, info, metrics
La decisión
Dos URLs: la aplicación usa PgBouncer (6432) y Flyway va directo a PostgreSQL (5433). Los ids son uuidv7(), nativa desde PostgreSQL 18. Documentado
Lo que descartas
Migrar a través de PgBouncer en modo transacción. Una migración suele hacer SET lock_timeout y después un ALTER TABLE; si van en transacciones separadas, cada una puede caer en una conexión distinta del servidor, y el SET queda en la conexión de otro cliente. Descartas también bigserial: un id secuencial se adivina y no se puede generar fuera de la base.
Qué puede salir mal
Olvidar que ahora hay dos URLs. En producción, la de Flyway apunta al primario, no a una réplica ni al pooler. Y si la red solo deja pasar el puerto del pooler, la migración se corre aparte, como un paso del despliegue.

Ordenar por un UUIDv7 es ordenar por fecha de creación, porque sus primeros 48 bits son los milisegundos desde 1970. Por eso ORDER BY id DESC usa el índice de la clave primaria y no necesitas otro sobre created_at. M00 explica el formato y por qué un UUID aleatorio, en cambio, ensucia el índice B-tree.

Paso 4. El repositorio, con SQL a la vista

package lab.notas.notes;

import java.util.List;
import java.util.Optional;
import java.util.UUID;

import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
public class NoteRepository {

    private final JdbcClient jdbc;

    public NoteRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    public Note insert(NewNote note) {
        // RETURNING devuelve la fila con el id y la fecha que puso PostgreSQL: un viaje, no dos.
        return jdbc.sql("""
                INSERT INTO notes (title, body)
                VALUES (:title, :body)
                RETURNING id, title, body, created_at
                """)
                .param("title", note.title())
                .param("body", note.body() == null ? "" : note.body())
                .query(Note.class)
                .single();
    }

    public Optional<Note> findById(UUID id) {
        return jdbc.sql("SELECT id, title, body, created_at FROM notes WHERE id = :id")
                .param("id", id)
                .query(Note.class)
                .optional();
    }

    public List<Note> latest(int limit) {
        // Los UUIDv7 empiezan con la hora: ordenar por id es ordenar por fecha de creación.
        return jdbc.sql("SELECT id, title, body, created_at FROM notes ORDER BY id DESC LIMIT :limit")
                .param("limit", limit)
                .query(Note.class)
                .list();
    }
}

Paso 5. El controlador y sus errores

package lab.notas.notes;

import java.util.List;
import java.util.UUID;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;
import org.springframework.web.util.UriComponentsBuilder;

@RestController
@RequestMapping("/api/notes")
public class NoteController {

    private final NoteRepository notes;

    public NoteController(NoteRepository notes) {
        this.notes = notes;
    }

    @PostMapping
    public ResponseEntity<Note> create(@Valid @RequestBody NewNote body, UriComponentsBuilder uri) {
        Note note = notes.insert(body);
        return ResponseEntity.created(uri.path("/api/notes/{id}").build(note.id())).body(note);
    }

    @GetMapping("/{id}")
    public Note get(@PathVariable UUID id) {
        // ResponseStatusException se convierte en un ProblemDetail (RFC 9457) con status 404.
        return notes.findById(id).orElseThrow(() ->
                new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe la nota " + id));
    }

    @GetMapping
    public List<Note> latest(@RequestParam(defaultValue = "20") @Min(1) @Max(100) int limit) {
        return notes.latest(limit);
    }
}
La decisión
spring.mvc.problemdetails.enabled: true y ResponseStatusException: los 404 y los 400 salen como Problem Details sin escribir un manejador.
Lo que descartas
Un formato de error propio, como {"error": "..."}. Cada cliente tendría que aprenderlo, y el estándar ya trae status, title, detail e instance.
Qué puede salir mal
Un limit sin tope. ?limit=1000000 obliga a la base a mandar un millón de filas y a la aplicación a tenerlas en memoria. @Max(100) lo corta con un 400.

Agrega el controlador de los experimentos. No va en una aplicación real: muestra en qué proceso del servidor cayó tu consulta, y con eso vas a ver al pooler compartir conexiones.

Paso 6. El tamaño del pool

Hay dos pools en fila: Hikari, en la aplicación, con 10 conexiones hacia PgBouncer, y PgBouncer, con hasta 20 hacia PostgreSQL. La configuración está en el application.yaml del paso 3.

La decisión
Hikari con 10 conexiones y connection-timeout de 3 000 ms. Si el pool está lleno 3 s, la request falla con un 500 y el problema se ve.
Lo que descartas
Un pool de 100 "por si acaso" y el timeout por defecto de 30 s. Más conexiones no hacen más rápida a la base: compiten por los mismos núcleos y discos. Y 30 s de espera convierten una base lenta en hilos colgados en toda la aplicación.
Qué puede salir mal
Escalar a 5 réplicas de la aplicación con 10 conexiones cada una: son 50 clientes para 20 conexiones reales. En modo transacción está bien, porque una conexión real solo se presta mientras dura una transacción; en modo sesión, 30 clientes esperarían.

El connection-timeout de Hikari es un número en milisegundos. Si escribes 3s, la aplicación no arranca: "Failed to convert from type [java.lang.String] to type [long] for value [3s]".

package lab.notas;

    @Bean
    @ServiceConnection

            registry.add("spring.flyway.user", postgres::getUsername);
            registry.add("spring.flyway.password", postgres::getPassword);

import io.gatling.javaapi.core.ScenarioBuilder;
import io.gatling.javaapi.core.Simulation;
import io.gatling.javaapi.http.HttpProtocolBuilder;

/** ./mvnw gatling:test -Dgatling.simulationClass=lab.notas.NotasSimulation */
public class NotasSimulation extends Simulation {

    HttpProtocolBuilder protocolo = http
            .baseUrl(System.getProperty("baseUrl", "http://localhost:8080"))
            .contentTypeHeader("application/json");

    ScenarioBuilder crearYLeer = scenario("Crear y leer una nota")
            .exec(http("crear").post("/api/notes")
                    .body(StringBody("""
                            {"title": "carga", "body": "#{randomUuid()}"}
                            """))
                    .check(status().is(201), header("Location").saveAs("location")))
            .exec(http("leer").get("#{location}")
                    .check(status().is(200)));

    {
        setUp(crearYLeer.injectOpen(constantUsersPerSec(50).during(60)))
                .protocols(protocolo)
                .assertions(global().responseTime().percentile(99.0).lt(250));
    }
}
La decisión
Un modelo abierto: llegan 50 usuarios nuevos por segundo, cada uno crea y lee una nota, lo que da 100 requests por segundo, y la corrida falla si el p99 pasa de 250 ms.
Lo que descartas
Un modelo cerrado, con 50 usuarios que repiten en bucle. Si el servidor se pone lento, los usuarios esperan y mandan menos, y la prueba se vuelve amable justo cuando debería apretar. En producción la gente sigue llegando aunque tu servidor esté lento.
Qué puede salir mal
Mirar el promedio. Con 7 ms de promedio puedes tener requests de 2 s. Los percentiles se explican en M00.

Cero errores, 100 requests por segundo y la assertion del p99 en OK. Crear cuesta tres veces más que leer: escribe en el WAL y espera el fsync del commit.

Falla 1. Un SET que se filtra a otro cliente

Mira primero qué conexión usa la aplicación, y después conéctate a PgBouncer con psql, cambia un parámetro de sesión y vuelve a mirar:

curl -s localhost:8080/api/lab/conexion
# {"backend_pid":179,"statement_timeout":"0"}

docker compose exec postgres psql "postgres://app:app@pgbouncer:5432/app" \
  -c "SET statement_timeout = '50ms'" -c "SELECT pg_backend_pid()"
# 179

curl -s localhost:8080/api/lab/conexion
# {"backend_pid":179,"statement_timeout":"50ms"}

Tu SET quedó en el proceso 179 del servidor, y la siguiente request de la aplicación recibió ese mismo proceso. Desde ahora, cualquier consulta de la aplicación que tarde más de 50 ms se cancela, y nadie en la aplicación cambió nada. RESET statement_timeout, por el mismo camino, lo arregla.

Qué pasa si falla

En modo transacción, todo lo que vive en la sesión se comparte: SET, tablas temporales, LISTEN y advisory locks de sesión. Si necesitas un parámetro para una consulta, usa SET LOCAL dentro de una transacción: dura hasta el commit y no se filtra.

Falla 2. Un advisory lock que no excluye

P='docker compose exec -T postgres psql -At postgres://app:app@pgbouncer:5432/app'
$P -c "SELECT pg_advisory_lock(42), pg_backend_pid()"       # cliente A: |179
$P -c "SELECT pg_try_advisory_lock(42), pg_backend_pid()"   # cliente B: t|179

docker compose exec -T postgres psql -At -U app -d app \
  -c "SELECT pg_try_advisory_lock(42), pg_backend_pid()"    # directo:   f|308

A toma el lock 42 y se desconecta de PgBouncer, pero la conexión del servidor sigue viva y el lock sigue tomado en el proceso 179. B, otro cliente, recibe ese mismo proceso y obtiene el lock otra vez: t. Un lock de sesión es reentrante para su sesión, y para PostgreSQL A y B son la misma sesión. Directo a la base, en el proceso 308, la respuesta correcta es f.

Si tu código usa pg_advisory_lock para que dos instancias no hagan lo mismo a la vez, detrás de PgBouncer en modo transacción no lo impide. La versión de transacción, pg_advisory_xact_lock, se libera en el commit y sí funciona.

Falla 3. Prepared statements

El driver de PostgreSQL prepara una consulta en el servidor después de usarla 5 veces y le pone un nombre, como S_1. Desde PgBouncer 1.21, el pooler sigue esos nombres en modo transacción con max_prepared_statements, y desde la 1.24 viene en 200. Documentado Para ver qué pasaba antes, apágalo:

services:
  pgbouncer:
    environment:
      MAX_PREPARED_STATEMENTS: 0
docker compose -f compose.yaml -f override0.yaml up -d pgbouncer
ID=$(curl -s -X POST localhost:8080/api/notes -H 'Content-Type: application/json' -d '{"title": "x"}'   | python -c "import sys, json; print(json.load(sys.stdin)['id'])")
python carga.py "http://localhost:8080/api/notes/$ID" 3000 40    # 3 000 GET con 40 hilos

carga.py es un script de diez líneas que manda requests con un pool de hilos y cuenta los códigos de respuesta; está en la solución de abajo. Gatling también sirve, pero aquí interesa contar errores, no latencias.

Cerca del 17 % de las requests falla. Con pocos clientes a la vez no lo ves: con curl en secuencia, o con 30 en paralelo, las 600 requests dieron 200, porque PgBouncer le devuelve a cada cliente la última conexión que se liberó y casi siempre es la misma. El error aparece cuando hay concurrencia de verdad, que es justo en producción.

Después de la carga, SHOW POOLS muestra cl_active 10, las 10 conexiones de Hikari, y sv_idle 10: con 40 requests HTTP a la vez, PgBouncer no necesitó más de 10 conexiones reales.

Ver carga.py 
import sys, urllib.request, concurrent.futures as cf, collections, time

url, n, hilos = sys.argv[1], int(sys.argv[2]), int(sys.argv[3])

def pedir(_):
    try:
        with urllib.request.urlopen(url, timeout=10) as r:
            return r.status
    except urllib.error.HTTPError as e:
        return e.code

inicio = time.time()
with cf.ThreadPoolExecutor(hilos) as ex:
    codigos = collections.Counter(ex.map(pedir, range(n)))
print(dict(codigos), round(time.time() - inicio, 1), "s")
