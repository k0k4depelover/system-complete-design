Dos primarios

Dos sucursales de una tienda de café venden cada una por su lado, contra su propia base, y las dos bases se copian entre sí. Vas a provocar los tres conflictos de tener dos primarios, ver qué hace PostgreSQL con cada uno y diseñar el inventario para que no ocurran.

Proyecto

Plan
Bloque 2
Tiempo estimado
4 a 5 h
Módulos

Estado
Sin empezar

Al terminar podrás

  • Conectar dos PostgreSQL con replicación lógica en las dos direcciones, sin que los cambios reboten entre ellas.
  • Medir cuánto tarda una venta de una sucursal en verse en la otra.
  • Provocar los tres conflictos de tener dos primarios, sobre un valor, sobre un invariante y sobre una clave, y leer qué hizo PostgreSQL con cada uno.
  • Destrabar una replicación detenida por un choque de clave, reparando los datos o saltando la transacción.
  • Diseñar el esquema para no tener conflictos: cada fila con una sucursal dueña, ids UUIDv7, traspasos con recibo idempotente y un solo dueño del catálogo.

La excusa

Una tienda de café tiene dos sucursales, norte y sur. Cada una tiene su propia base y su propia app, y tiene que seguir vendiendo aunque se corte el enlace con la otra. Las dos bases se copian entre sí: cada sucursal ve el catálogo, el stock de la otra y todas las ventas.

Con dos bases que aceptan escrituras, el problema ya no es solo el retraso. Las dos pueden cambiar lo mismo a la vez, y ninguna se entera hasta que le llega el cambio de la otra. Vas a provocarlo de tres maneras y después a diseñar el inventario para que no pase: ninguna fila la escriben las dos.

Dos primarios, ninguna réplica
Las dos bases aceptan escrituras. wal_level=logical agrega al WAL lo que hace falta para publicar los cambios fila por fila, por tabla. Se lee al arrancar, por eso va en el command. Documentado
Quién cambió cada fila
track_commit_timestamp=on guarda cuándo se confirmó cada transacción y desde qué origen. Sin eso, PostgreSQL 18 no puede saber que una fila que llega de la otra base había cambiado aquí, y no cuenta ese conflicto. Documentado
Puertos a la vista
El 5433 es norte y el 5434 es sur, para entrar con psql. El 8081 es app-norte y el 8082, app-sur. Solo norte monta scripts/: conectar.sh corre desde ahí contra las dos.

Paso a paso

Paso 1. Las mismas tablas y los mismos datos en las dos

CREATE TABLE products (
    id          uuid   PRIMARY KEY,
    sku         text   NOT NULL UNIQUE,
    name        text   NOT NULL,
    price_cents bigint NOT NULL CHECK (price_cents >= 0)
);

-- Una fila por sucursal y producto. Solo la sucursal dueña de la fila la modifica.
CREATE TABLE stock (
    branch     text NOT NULL,
    product_id uuid NOT NULL REFERENCES products (id),
    qty        int  NOT NULL CHECK (qty >= 0),
    PRIMARY KEY (branch, product_id)
);

-- Solo se insertan, con UUIDv7 generados en cada sucursal: nunca chocan.
CREATE TABLE sales (
    id         uuid        PRIMARY KEY DEFAULT uuidv7(),
    branch     text        NOT NULL,
    product_id uuid        NOT NULL REFERENCES products (id),
    qty        int         NOT NULL CHECK (qty > 0),
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE transfers (
    id          uuid        PRIMARY KEY DEFAULT uuidv7(),
    from_branch text        NOT NULL,
    to_branch   text        NOT NULL,
    product_id  uuid        NOT NULL REFERENCES products (id),
    qty         int         NOT NULL CHECK (qty > 0),
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE transfer_receipts (
    transfer_id uuid        PRIMARY KEY REFERENCES transfers (id),
    branch      text        NOT NULL,
    received_at timestamptz NOT NULL DEFAULT now()
);

La decisión
Las dos bases corren las mismas migraciones, y la V2 carga en las dos los mismos productos, con ids fijos, y el mismo stock de partida. Al suscribirse, copy_data = false: no hay nada que copiar. El stock es una fila por sucursal y producto, y las ventas y los traspasos tienen ids uuidv7() generados en cada base.
Lo que descartas
Cargar los datos en una sola y dejar que la otra los copie al suscribirse. La copia inicial no filtra por origen: si la base de la que copias ya recibió filas de la tuya, te las devuelve, y chocan con las que tienes. Documentado Sirve en una dirección, contra una base vacía, y la otra suscripción va igual sin copia.
Qué puede salir mal
Publicar FOR ALL TABLES. Incluiría flyway_schema_history, y cada migración de una sucursal le llegaría a la otra como una fila que ya tiene. Por eso conectar.sh nombra las tablas una por una, y cada base lleva su propio historial de migraciones.

Cargar lo mismo en las dos tiene un efecto que vas a ver en los contadores. La primera vez que llega un cambio de la otra base a una fila de la V2, PostgreSQL lo cuenta como conflicto: esa fila se escribió aquí, en la migración. Después de la primera carga, sur ya contaba dos, uno por cada fila de stock de norte que había cambiado. El contador no distingue un conflicto real de uno inofensivo.

Paso 2. Conectar en las dos direcciones

#!/bin/sh
# Conecta las dos sucursales: cada una publica sus tablas y se suscribe a la otra.
#   origin = none   reenvía solo lo que se escribió en la sucursal, no lo que le llegó de la otra;
#                   sin eso, cada cambio rebotaría entre las dos.
#   copy_data = false  las dos ya tienen los mismos datos de partida (los puso la migración V2).
# La tabla de Flyway no se publica: cada sucursal lleva su propio historial de migraciones.
set -e
export PGPASSWORD=app
TABLAS="products, stock, sales, transfers, transfer_receipts"

for node in norte sur; do
  psql -h "$node" -U app -d app -v ON_ERROR_STOP=1 -qc "CREATE PUBLICATION inventario FOR TABLE $TABLAS"
done

psql -h norte -U app -d app -v ON_ERROR_STOP=1 -qc "CREATE SUBSCRIPTION desde_sur
    CONNECTION 'host=sur dbname=app user=app password=app'
    PUBLICATION inventario WITH (origin = none, copy_data = false)"

psql -h sur -U app -d app -v ON_ERROR_STOP=1 -qc "CREATE SUBSCRIPTION desde_norte
    CONNECTION 'host=norte dbname=app user=app password=app'
    PUBLICATION inventario WITH (origin = none, copy_data = false)"

echo "norte y sur conectadas"
La decisión
Replicación lógica: cada base publica sus tablas y se suscribe a la otra. La suscripción abre un slot en la otra base, que le manda cada transacción confirmada, fila por fila. origin = none pide solo los cambios que se escribieron en esa base, sin los que le llegaron por otra suscripción. Documentado
Lo que descartas
Una extensión de varios primarios, como pgactive o EDB Postgres Distributed, que suman resolución de conflictos y más herramientas. Documentado Aquí ves lo que hace PostgreSQL 18 sola, que es poco, y por eso el diseño tiene que evitar los conflictos.
Qué puede salir mal
Olvidar origin = none. El valor por defecto, any, manda también lo que llegó de otra suscripción: sur le devolvería a norte cada venta que acaba de recibir de ella. Documentado Y si una sucursal queda caída días, la otra guarda en su slot todo el WAL que no le pudo mandar: en producción, ponle un techo con max_slot_wal_keep_size.

Paso 3. Cada fila de stock tiene una dueña

package lab.sucursales.inventory;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.UUID;

import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
public class InventoryRepository {

    private final JdbcClient jdbc;

    public InventoryRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    public List<ProductStock> products() {
        Map<UUID, ProductStock> out = new LinkedHashMap<>();
        jdbc.sql("""
                SELECT p.id, p.sku, p.name, p.price_cents, s.branch, s.qty
                  FROM products p JOIN stock s ON s.product_id = p.id
                 ORDER BY p.sku, s.branch
                """)
                .query(rs -> {
                    UUID id = rs.getObject("id", UUID.class);
                    ProductStock product = out.get(id);
                    if (product == null) {
                        product = new ProductStock(id, rs.getString("sku"), rs.getString("name"),
                                rs.getLong("price_cents"), new LinkedHashMap<>());
                        out.put(id, product);
                    }
                    product.stock().put(rs.getString("branch"), rs.getInt("qty"));
                });
        return List.copyOf(out.values());
    }

    /** Solo toca la fila de esta sucursal: es la única que esta sucursal escribe. */
    public boolean takeFromOwnStock(String branch, UUID productId, int qty) {
        return jdbc.sql("""
                UPDATE stock SET qty = qty - :qty
                 WHERE branch = :branch AND product_id = :product AND qty >= :qty
                """)
                .param("branch", branch)
                .param("product", productId)
                .param("qty", qty)
                .update() == 1;
    }

    public void addToOwnStock(String branch, UUID productId, int qty) {
        jdbc.sql("UPDATE stock SET qty = qty + :qty WHERE branch = :branch AND product_id = :product")
                .param("branch", branch)
                .param("product", productId)
                .param("qty", qty)
                .update();
    }

    public Sale insertSale(String branch, UUID productId, int qty) {
        return jdbc.sql("""
                INSERT INTO sales (branch, product_id, qty) VALUES (:branch, :product, :qty)
                RETURNING id, branch, product_id, qty, created_at
                """)
                .param("branch", branch)
                .param("product", productId)
                .param("qty", qty)
                .query(Sale.class)
                .single();
    }

    public Optional<Sale> findSale(UUID id) {
        return jdbc.sql("SELECT id, branch, product_id, qty, created_at FROM sales WHERE id = :id")
                .param("id", id)
                .query(Sale.class)
                .optional();
    }

    public Transfer insertTransfer(String from, String to, UUID productId, int qty) {
        return jdbc.sql("""
                INSERT INTO transfers (from_branch, to_branch, product_id, qty)
                VALUES (:from, :to, :product, :qty)
                RETURNING id, from_branch, to_branch, product_id, qty, created_at
                """)
                .param("from", from)
                .param("to", to)
                .param("product", productId)
                .param("qty", qty)
                .query(Transfer.class)
                .single();
    }

    /** Los traspasos que llegaron por replicación y esta sucursal todavía no recibió. */
    public List<Transfer> pendingTransfersTo(String branch) {
        return jdbc.sql("""
                SELECT t.id, t.from_branch, t.to_branch, t.product_id, t.qty, t.created_at
                  FROM transfers t
                 WHERE t.to_branch = :branch
                   AND NOT EXISTS (SELECT 1 FROM transfer_receipts r WHERE r.transfer_id = t.id)
                 ORDER BY t.id
                """)
                .param("branch", branch)
                .query(Transfer.class)
                .list();
    }

    /** El recibo es de quien recibe. ON CONFLICT hace que recibir dos veces no sume dos veces. */
    public boolean insertReceipt(UUID transferId, String branch) {
        return jdbc.sql("""
                INSERT INTO transfer_receipts (transfer_id, branch) VALUES (:id, :branch)
                ON CONFLICT (transfer_id) DO NOTHING
                """)
                .param("id", transferId)
                .param("branch", branch)
                .update() == 1;
    }

    public boolean productExists(UUID id) {
        return jdbc.sql("SELECT EXISTS (SELECT 1 FROM products WHERE id = :id)")
                .param("id", id)
                .query(Boolean.class)
                .single();
    }

    public boolean updatePrice(UUID id, long priceCents) {
        return jdbc.sql("UPDATE products SET price_cents = :price WHERE id = :id")
                .param("id", id)
                .param("price", priceCents)
                .update() == 1;
    }
}
package lab.sucursales.inventory;

import java.util.List;
import java.util.UUID;

import lab.sucursales.Branch;

import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.server.ResponseStatusException;

@Service
public class InventoryService {

    private final InventoryRepository repo;
    private final Branch branch;

    public InventoryService(InventoryRepository repo, Branch branch) {
        this.repo = repo;
        this.branch = branch;
    }

    public List<ProductStock> products() {
        return repo.products();
    }

    /** Vende solo de su propio stock: la otra sucursal no puede vender estas mismas unidades. */
    @Transactional
    public Sale sell(UUID productId, int qty) {
        takeOrFail(productId, qty);
        return repo.insertSale(branch.me(), productId, qty);
    }

    public Sale sale(UUID id) {
        return repo.findSale(id).orElseThrow(() ->
                new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe la venta " + id));
    }

    /**
     * Mover stock a otra sucursal: resto del mío y dejo un traspaso. No toco la fila de la otra:
     * ella lo suma cuando el traspaso le llega.
     */
    @Transactional
    public Transfer send(UUID productId, int qty, String to) {
        if (to.equals(branch.me())) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "No puedes traspasarte a ti misma");
        }
        takeOrFail(productId, qty);
        return repo.insertTransfer(branch.me(), to, productId, qty);
    }

    @Transactional
    public boolean receive(Transfer transfer) {
        if (!repo.insertReceipt(transfer.id(), branch.me())) {
            return false;
        }
        repo.addToOwnStock(branch.me(), transfer.productId(), transfer.qty());
        return true;
    }

    public List<Transfer> pendingTransfers() {
        return repo.pendingTransfersTo(branch.me());
    }

    /** El catálogo tiene una sola dueña. Si las dos lo editaran, cada una terminaría con el precio de la otra. */
    @Transactional
    public void changePrice(UUID id, long priceCents) {
        if (!branch.ownsCatalog()) {
            throw new ResponseStatusException(HttpStatus.CONFLICT,
                    "El catálogo se edita en " + branch.catalogOwner() + "; esta sucursal es " + branch.me());
        }
        if (!repo.updatePrice(id, priceCents)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe el producto " + id);
        }
    }

    private void takeOrFail(UUID productId, int qty) {
        if (!repo.takeFromOwnStock(branch.me(), productId, qty)) {
            if (!repo.productExists(productId)) {
                throw new ResponseStatusException(HttpStatus.NOT_FOUND, "No existe el producto " + productId);
            }
            throw new ResponseStatusException(HttpStatus.CONFLICT,
                    "En " + branch.me() + " no quedan " + qty + " unidades de " + productId);
        }
    }
}
La decisión
Solo la sucursal dueña cambia su fila de stock: takeFromOwnStock filtra por branch = me, y la condición qty >= :qty va en el mismo UPDATE, así que dos ventas a la vez en la misma sucursal no bajan de cero. Las ventas y los traspasos solo se insertan, con UUIDv7 que no chocan. Ninguna fila la escriben las dos, así que no hay conflicto que resolver.
Lo que descartas
Una sola fila de stock por producto, compartida. Cada sucursal resta de su copia, y la última en llegar pisa a la otra. Lo vas a provocar: 20 tazas vendidas de 10.
Qué puede salir mal
Que una sucursal se quede sin stock mientras la otra tiene. En la carga, norte respondió 409 a 221 ventas de café con 90 unidades en sur. Es el precio de no compartir la fila: cada una vende lo suyo, y para equilibrar se traspasa. Y la fila es caliente: todas las ventas de café de una sucursal esperan su lock, una tras otra.

Paso 4. Traspasos con recibo

package lab.sucursales.inventory;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

/** Cada segundo, suma al stock propio los traspasos que llegaron de la otra sucursal. */
@Component
public class TransferReceiver {

    private static final Logger log = LoggerFactory.getLogger(TransferReceiver.class);

    private final InventoryService inventory;

    public TransferReceiver(InventoryService inventory) {
        this.inventory = inventory;
    }

    @Scheduled(fixedDelayString = "${app.receive-every-ms}")
    public int receivePending() {
        int received = 0;
        for (Transfer t : inventory.pendingTransfers()) {
            if (inventory.receive(t)) {
                received++;
                log.info("Recibido el traspaso {}: {} unidades desde {}", t.id(), t.qty(), t.fromBranch());
            }
        }
        return received;
    }
}
La decisión
Para mover stock, sur resta de su fila y deja un traspaso. Norte lo recibe por replicación y, en una transacción, guarda un recibo y suma a su fila. El recibo tiene el id del traspaso como clave, y ON CONFLICT DO NOTHING hace que recibir dos veces sume una sola. El recibo vuelve a sur por replicación: sur sabe que llegó.
Lo que descartas
Que sur sume directamente en la fila de norte. Rompe la regla de una dueña por fila: una venta de norte al mismo tiempo pisaría la suma, o la suma a la venta.
Qué puede salir mal
Unidades en camino. Si norte está caída, el traspaso espera en sur, y esas unidades no están en ningún stock. cuadrar.sql las cuenta aparte. Cancelar un traspaso tampoco es simple: sur tendría que saber que norte no lo recibió, y eso solo lo sabe norte.

Paso 5. Un solo dueño del catálogo

Este paso es changePrice, en InventoryService: si la sucursal no es catalog-owner, responde 409.

La decisión
Los precios y las altas de productos se editan solo en norte. Es un primario único dentro de un sistema con dos: el catálogo cambia poco, y que una sucursal no pueda cambiar un precio durante un corte es aceptable.
Lo que descartas
Dejar que las dos editen y confiar en que PostgreSQL elija. PostgreSQL 18 no elige: siempre aplica el cambio que llega. Documentado Si las dos cambian el mismo precio durante un corte, cada una termina con el de la otra. Lo vas a medir.
Qué puede salir mal
Dar de alta productos en las dos. Dos SKU iguales chocan con la restricción UNIQUE, y la replicación se detiene hasta que alguien la destraba. También lo vas a provocar.

La decisión
Dos escenarios, uno por sucursal, cada uno contra su app: el 80 % vende café y el 20 % traspasa té a la otra. Lo que se prueba no es la latencia: es que al terminar cada unidad esté en algún lado. cuadrar.sql suma, en cada base, el stock, lo vendido y lo que va en camino, y saca una huella de cada tabla para comparar las dos bases.
Lo que descartas
Comparar solo cuántas filas hay. Dos bases pueden tener las mismas 3 910 ventas y un stock distinto. La huella md5 de las filas ordenadas cambia con cualquier diferencia.
Qué puede salir mal
Cuadrar mientras hay traspasos sin recibir. Aparecen en en_camino, no como faltantes, pero las huellas de las dos bases todavía no coinciden. Espera un par de segundos a que el receptor los sume.

Las dos vendieron las 10 tazas de la fila de norte, cada una contra su copia, y las dos bases convergieron: coinciden en que quedan 0 y se vendieron 20. La replicación llevó las dos bases al mismo estado, y ese estado viola el invariante. Ninguna regla de resolución lo arregla después, porque las dos ventas ya se hicieron. Esta vez PostgreSQL no aplica nada: un INSERT que choca con una restricción única es un error, y la suscripción se detiene. Documentado El worker vuelve a arrancar cada 5 s, lo intenta con la misma transacción y falla otra vez; apply_error_count sube con cada intento. Todo lo que viene después espera: la venta de té que sur hizo un segundo más tarde nunca llegó a norte. Un SKU repetido frena la replicación entera, no solo el catálogo.

Destrabar: saltar o reparar

Hay dos salidas. La primera es saltar la transacción que choca, con la posición del WAL que trae la línea CONTEXT, en finished at:

for par in "norte desde_sur" "sur desde_norte"; do
  set -- $par
  lsn=$(docker compose logs $1 | grep -A3 insert_exists | grep -o 'finished at [0-9A-F]*/[0-9A-F]*' | tail -1 | cut -d' ' -f3)
  echo "$1 salta la transacción que termina en $lsn"
  q $1 "ALTER SUBSCRIPTION $2 SKIP (lsn = '$lsn')"
done
sleep 6
for n in norte sur; do echo "$n: ventas de té $(q $n "SELECT count(*) FROM sales WHERE product_id = '$TE'"), MATE-500 = $(q $n "SELECT name FROM products WHERE sku = 'MATE-500'")"; done
norte salta la transacción que termina en 0/1EF48F0
sur salta la transacción que termina en 0/1EEE108
norte: ventas de té 1, MATE-500 = Yerba mate (norte)
sur: ventas de té 1, MATE-500 = Yerba mate (sur)

La replicación siguió y la venta de té llegó a norte. Pero cada base se quedó con su propia yerba, con ids distintos: las dos divergen para siempre en esa fila, y nada lo avisa.

Qué pasa si falla

SKIP descarta la transacción remota entera, no solo la fila que choca. Documentado Si esa transacción traía también una venta, la venta no llega nunca a la otra sucursal, y el inventario deja de cuadrar sin ningún error.

La otra salida es reparar los datos para que la transacción que llega ya no choque. Con otro SKU repetido, cada sucursal renombra su propia fila:

pausar
q norte "INSERT INTO products (id, sku, name, price_cents) VALUES (uuidv7(), 'MIEL-250', 'Miel (norte)', 900)"
q sur   "INSERT INTO products (id, sku, name, price_cents) VALUES (uuidv7(), 'MIEL-250', 'Miel (sur)', 950)"
reanudar
for n in norte sur; do echo "$n errores: $(q $n 'SELECT apply_error_count FROM pg_stat_subscription_stats')"; done
# Cada sucursal renombra su propia fila: la transacción remota ya no choca y se aplica entera.
q norte "UPDATE products SET sku = 'MIEL-250-N' WHERE sku = 'MIEL-250'"
q sur   "UPDATE products SET sku = 'MIEL-250-S' WHERE sku = 'MIEL-250'"
sleep 8
for n in norte sur; do echo "$n: $(q $n "SELECT string_agg(sku || ' ' || name, ', ' ORDER BY sku) FROM products WHERE sku LIKE 'MIEL%'") errores $(q $n 'SELECT apply_error_count FROM pg_stat_subscription_stats')"; done
norte errores: 5
sur errores: 5
norte: MIEL-250-N Miel (norte), MIEL-250-S Miel (sur) errores 6
sur: MIEL-250-N Miel (norte), MIEL-250-S Miel (sur) errores 6

Las dos bases terminaron con los dos productos, y la replicación siguió sola, sin perder nada: el worker volvió a intentar y esta vez la transacción entró. El contador pasó de 5 a 6 por un último intento fallido antes del arreglo, y después no subió más. Reparar cuesta más que saltar, porque tienes que decidir qué hacer con cada fila, pero no pierde ninguna otra escritura.

Cómo conectar

Este proyecto funciona solo. Si quieres juntarlo con uno anterior:

  • Con A00, el laboratorio

    Las ventas y los traspasos usan uuidv7(), los ids de A00. Con dos primarios dejan de ser una preferencia: cada base genera los suyos sin preguntarle a la otra y no chocan. Con un bigserial, las dos secuencias empezarían en 1 y la primera venta de cada sucursal chocaría con la otra. Si pones el PgBouncer de A00 delante de cada base, ponlo solo para la app: las suscripciones se conectan directo a la otra base.

  • Con A01, detrás de Nginx

    Pon varias réplicas de cada app detrás de un Nginx, pero un upstream por sucursal. Repartir las cajas de norte entre las dos apps no es balancear: una venta que entra por sur resta del stock de sur. Aquí, a qué app va cada request es una decisión de negocio.

  • Con A02, una API que no se rompe

    El 409 de sur al cambiar un precio ya es un ProblemDetail, como los errores de A02: dale un type propio para que el cliente sepa que tiene que ir a norte. Y el If-Match de A02 solo protege dentro de una base: comprueba la versión de norte, no un cambio de sur que todavía no llegó. Es otra razón para que el catálogo tenga una sola dueña.

  • Con A03, caché que aguanta un pico

    Si cada sucursal cachea el catálogo como en A03, la app de sur nunca se entera de un cambio de precio: el cambio llega por replicación, no por su API, y nadie publica la invalidación. Un trigger en sur no alcanza por defecto, porque los cambios que aplica una suscripción no disparan los triggers comunes; hay que marcarlo con ENABLE REPLICA o ENABLE ALWAYS. Documentado O que norte publique la invalidación en un canal que las dos escuchen.

  • Con A04, primario y réplicas

    Cada sucursal puede tener su réplica física, como en A04, para sobrevivir a la caída de su base. Pero el slot de la suscripción de la otra sucursal vive en el primario: si promueves la réplica, el slot no está, y la otra sucursal deja de recibir. Desde PostgreSQL 17, una suscripción con failover = true y sync_replication_slots en la réplica conservan el slot. Documentado
