Seguridad e identidad

Cada request de un sistema real responde dos preguntas antes de hacer nada: quién la envía y si puede hacer lo que pide. Este módulo recorre cómo se contesta eso entre usuarios, aplicaciones y servicios, cómo se protegen los datos y las claves, y los errores que más se explotan en APIs reales.

10.1Autenticación, autorización y el modelo de amenazas

Autenticar es comprobar quién hace la request; autorizar es decidir si esa identidad puede hacer eso con ese recurso. Son dos pasos, y el segundo se olvida más: una API que verifica el token y después devuelve cualquier factura que le pidan está autenticada, pero no autorizada.

Antes de elegir mecanismos se hace un modelo de amenazas, respondiendo tres preguntas: qué protegemos (dinero, conversaciones privadas, credenciales), de quién (usuarios curiosos, atacantes externos, un empleado, un servicio comprometido) y qué pasa si falla cada barrera. De ahí sale el principio de defensa en profundidad: ninguna barrera única, varias capas independientes, y el menor privilegio posible en cada una.

Con cookies, tres atributos no se negocian: HttpOnly (el JavaScript de la página no puede leerla, lo que frena el robo por XSS), Secure (solo viaja por HTTPS) y SameSite=Lax o Strict (no se envía en requests iniciadas por otros sitios, lo que frena el CSRF).

Un JWT tiene tres partes: header, payload y firma. El payload está codificado, no cifrado, así que cualquiera puede leerlo; lo que la firma garantiza es que nadie lo modificó. Una API que recibe un JWT verifica, en cada request, la firma con el algoritmo que ella decide, la expiración (exp), el emisor (iss), la audiencia (aud) y después los permisos (scope, role) contra el recurso pedido. El patrón habitual combina lo mejor de ambos mundos: un access token JWT corto (5 a 15 minutos) que las APIs verifican localmente, y un refresh token opaco de larga duración, guardado de forma segura, que solo el servidor de autorización acepta y que se puede revocar. Los refresh tokens se rotan en cada uso: si uno aparece dos veces, alguien lo robó, y se revoca toda la familia. Las claves de firma se rotan publicando las públicas en un JWKS con un kid por clave, así las APIs aceptan la vieja y la nueva durante la transición.

10.3OAuth 2.0 y OpenID Connect

OAuth 2.0 resuelve la delegación: que una aplicación actúe sobre tus recursos en otro servicio, con permisos limitados (scopes), sin conocer tu contraseña. OpenID Connect le agrega identidad: además del access token, un ID token que dice quién eres. Hay cuatro roles: el usuario (dueño de los recursos), el cliente (la app), el servidor de autorización (emite tokens) y el resource server (la API).

Otros flujos y errores a conocer:

  • Client credentials: para servicio a servicio, sin usuario. El servicio se autentica con su propia credencial y recibe un token con sus scopes.
  • El flujo implícito está en desuso: entregaba el token en la URL, donde se filtra en historiales y logs.
  • Validar las redirect URI exactas: aceptar cualquier URL "que empiece con" la registrada permite que un atacante reciba el código.

10.4API keys

Para APIs que consumen servidores de otras empresas, las API keys siguen siendo lo más práctico. El diseño que usan los proveedores serios:

  1. Formato reconocibleUn prefijo con el tipo y el entorno más una parte aleatoria larga: sk_live_…, sk_test_…. El prefijo permite detectarlas en repositorios públicos; GitHub escanea los repositorios buscando formatos de claves de proveedores asociados y les avisa cuando encuentra una. Documentado
  2. Guardar solo un hashLa clave completa se muestra una sola vez al crearla. Como es larga y aleatoria, basta un SHA-256 (no hace falta bcrypt). Para buscarla, se indexa por el hash.
  3. Scopes y restriccionesSolo lectura, solo ciertos endpoints, IPs permitidas. La clave de un proceso de reportes no debería poder emitir reembolsos.
  4. Rotación sin cortesDos claves activas a la vez: el cliente cambia a la nueva, verifica y revoca la vieja.

10.5Identidad entre servicios

Dentro del sistema, cada servicio necesita saber con certeza quién lo llama, sin confiar en "viene de la red interna". Con mTLS, ambos extremos presentan certificados de corta duración (horas) emitidos automáticamente por una autoridad interna; el estándar SPIFFE define identidades del tipo spiffe://empresa/ns/pagos/sa/api. Un service mesh (M03) suele encargarse de todo esto sin tocar el código. Sobre esa identidad se escriben políticas: "solo el servicio de checkout puede llamar a POST /pagos". Es el núcleo de lo que se llama zero trust: ninguna request se acepta por venir de dentro.

10.6Secretos, cifrado y KMS

Los secretos (contraseñas de bases, claves de APIs de terceros, claves de firma) no van en el código, ni en el repositorio, ni en variables de entorno que terminan en logs. Van en un gestor de secretos, se entregan a cada servicio con su identidad, se rotan y cada acceso queda auditado.

Un efecto útil: si cada usuario tiene su propia DEK, borrarla vuelve ilegibles todos sus datos, incluidas las copias en backups que no puedes modificar. Esa técnica, llamada crypto-shredding, es una forma práctica de cumplir con pedidos de borrado como los del GDPR.

10.7Aislamiento multi-tenant

En un SaaS, el peor incidente posible es que un cliente vea los datos de otro. El error que lo causa casi siempre es el mismo: BOLA (también llamado IDOR), una consulta que filtra por el id del objeto pero no por el tenant. Las defensas, en capas:

  • El tenant sale del token, nunca de la request: el cliente no puede elegir su tenant enviando un parámetro.
  • Filtro obligatorio en la capa de datos: un repositorio que agrega tenant_id a toda consulta, y pruebas que verifican que ninguna consulta lo omite.
  • Row-level security en PostgreSQL como red de seguridad: aunque el código olvide el filtro, la base no devuelve filas de otro tenant.
ALTER TABLE facturas ENABLE ROW LEVEL SECURITY;

CREATE POLICY aislamiento_tenant ON facturas
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- En cada request, la aplicación fija el tenant del token antes de consultar:
SET LOCAL app.tenant_id = '6f1c…';
SELECT * FROM facturas WHERE id = $1;   -- una factura de otro tenant simplemente no aparece

El otro eje del aislamiento es la capacidad: límites por tenant (M08) para que un cliente ruidoso no degrade a los demás, y en clientes muy grandes, su propia base o su propia celda.

Qué pasa con un SSRF en la nube

En 2019, una vulnerabilidad SSRF en un firewall de aplicaciones mal configurado permitió a una atacante pedir credenciales al servicio de metadatos de AWS desde dentro de la infraestructura de Capital One, y con ellas leer datos de más de 100 millones de personas. Documentado A raíz de casos así, AWS lanzó IMDSv2, que exige un token de sesión obtenido con un PUT y no se puede disparar con un simple GET redirigido.

Sobre los datos personales (PII): recolectar solo lo necesario, cifrarlo, no escribirlo en logs (los logs se copian a muchos más lugares que la base), definir cuánto tiempo se retiene y tener un proceso de borrado que llegue también a réplicas, cachés, índices de búsqueda y backups. Y registrar en un log de auditoría inmutable quién accedió a qué.

Ejercicio de diseño: la API pública de un producto de IA

Vas a exponer una API de un modelo de lenguaje a empresas. Tendrán API keys para sus servidores, un panel web para sus empleados con inicio de sesión corporativo, y permisos por proyecto. Los prompts de los clientes pueden contener datos confidenciales. Un cliente debe poder revocar una clave filtrada y que deje de funcionar en segundos.

Diseña la autenticación de cada tipo de acceso, la autorización por proyecto, el almacenamiento de claves y cómo proteges los prompts.

Ver la solución de referencia
  • API keys de servidor: formato sk-proj-… con prefijo escaneable, guardadas como SHA-256, asociadas a un proyecto y con scopes. El gateway valida la clave contra una caché con TTL de unos segundos, alimentada por eventos de revocación: una clave revocada deja de funcionar en segundos sin consultar la base en cada request.
  • Panel web: OIDC con el proveedor de identidad corporativo del cliente (SSO), authorization code con PKCE, sesión en cookie HttpOnly, Secure y SameSite=Lax.
  • Autorización: roles por proyecto (owner, member, reader) evaluados en cada request; el proyecto sale de la clave o de la sesión, nunca de un parámetro libre. Pruebas automáticas de BOLA para cada endpoint.
  • Prompts: cifrados en reposo con envelope encryption y una DEK por organización (permite crypto-shredding si el cliente se va), fuera de los logs de aplicación, con retención configurable (por ejemplo 30 días, o cero para clientes que lo exijan) y accesos auditados.
  • Entre servicios: mTLS con identidades SPIFFE; el servicio de inferencia solo acepta llamadas del gateway.
