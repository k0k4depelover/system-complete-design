Seguridad e identidad

Cada request de un sistema real responde dos preguntas antes de hacer nada: quién la envía y si puede hacer lo que pide. Este módulo recorre cómo se contesta eso entre usuarios, aplicaciones y servicios, cómo se protegen los datos y las claves, y los errores que más se explotan en APIs reales.

10.1Autenticación, autorización y el modelo de amenazas

Autenticar es comprobar quién hace la request; autorizar es decidir si esa identidad puede hacer eso con ese recurso. Son dos pasos, y el segundo se olvida más: una API que verifica el token y después devuelve cualquier factura que le pidan está autenticada, pero no autorizada.

Antes de elegir mecanismos se hace un modelo de amenazas, respondiendo tres preguntas: qué protegemos (dinero, conversaciones privadas, credenciales), de quién (usuarios curiosos, atacantes externos, un empleado, un servicio comprometido) y qué pasa si falla cada barrera. De ahí sale el principio de defensa en profundidad: ninguna barrera única, varias capas independientes, y el menor privilegio posible en cada una.

Con cookies, tres atributos no se negocian: HttpOnly (el JavaScript de la página no puede leerla, lo que frena el robo por XSS), Secure (solo viaja por HTTPS) y SameSite=Lax o Strict (no se envía en requests iniciadas por otros sitios, lo que frena el CSRF).

Un JWT tiene tres partes: header, payload y firma. El payload está codificado, no cifrado, así que cualquiera puede leerlo; lo que la firma garantiza es que nadie lo modificó. Una API que recibe un JWT verifica, en cada request, la firma con el algoritmo que ella decide, la expiración (exp), el emisor (iss), la audiencia (aud) y después los permisos (scope, role) contra el recurso pedido. En producción real

El patrón habitual combina lo mejor de ambos mundos: un access token JWT corto (5 a 15 minutos) que las APIs verifican localmente, y un refresh token opaco de larga duración, guardado de forma segura, que solo el servidor de autorización acepta y que se puede revocar. Los refresh tokens se rotan en cada uso: si uno aparece dos veces, alguien lo robó, y se revoca toda la familia. Las claves de firma se rotan publicando las públicas en un JWKS con un kid por clave, así las APIs aceptan la vieja y la nueva durante la transición.

JWT con estado: revocar sin esperar al exp

El JWT puro tiene un problema que el callout anterior nombró: no se puede revocar antes de que venza. Un access token corto lo acota a minutos, pero "minutos" sigue siendo demasiado para un despido, un robo o un "cerrar sesión en todos los dispositivos". La solución habitual no es abandonar el JWT, sino darle un poco de estado: el token sigue trayendo un identificador de sesión (sid) y, en cada request, se comprueba contra un almacén que se puede borrar al instante. Para no pagar una consulta a la base en cada request, ese almacén es una caché en memoria (Redis).

El peso de autenticar recae en un único punto de entrada, el API gateway (M03): verifica la firma del JWT localmente —rápido, sin red— y, además, mira en Redis si la sesión sigue viva. Detrás, un servicio de identidad es el único que emite tokens, los rota y los revoca, con su propia base. Explora el flujo completo: el inicio de sesión, una request normal, qué pasa si Redis cae, la renovación con el refresh token, el robo de un refresh token y el cierre de todas las sesiones.

Las dos piezas de estado tienen trabajos distintos. El access token es un JWT de 10 minutos que viaja en cada request y se verifica sin consultar a nadie; lo único con estado es el chequeo del sid en Redis. El refresh token es un identificador opaco de larga vida que solo el servicio de identidad acepta, y solo en /auth/refresh: sirve para pedir un access token nuevo cuando el viejo vence, nunca para llamar a una API. Se guarda de forma que el JavaScript de la página no pueda leerlo (una cookie HttpOnly en la web, el llavero del sistema en el móvil) y en la base vive solo su hash.

El truco de la rotación con detección de reuso: cada vez que se usa un refresh token, el servidor emite uno nuevo y marca el viejo como usado, sin borrarlo. Si un token ya usado vuelve a aparecer, hay dos copias en circulación —una es del atacante— y el servidor no puede saber cuál es la legítima. La única respuesta segura es revocar la sesión entera. Víctima y atacante quedan fuera; la víctima vuelve a entrar con su contraseña y su segundo factor, el atacante no. Es la recomendación de la RFC 9700, la guía de seguridad vigente de OAuth 2.0: los refresh tokens de clientes públicos tienen que estar atados al cliente (sender-constrained) o rotarse. Documentado

Trade-off

Darle estado al JWT recupera la revocación inmediata, pero reintroduce justo lo que el JWT puro evitaba: una dependencia en cada request (Redis) y un servicio de identidad que es ahora un punto crítico. La ganancia es que la dependencia es una caché en memoria de sub-milisegundo, no la base, y que si Redis cae tienes margen para decidir entre fallar cerrado (seguro) o fallar abierto en rutas de solo lectura (disponible), como muestra el escenario "Redis no responde". Si tu caso no necesita revocar en segundos, el JWT puro con access tokens cortos es más simple y más barato: no todo sistema necesita esta máquina.

10.3OAuth 2.0 y OpenID Connect

OAuth 2.0 resuelve la delegación: que una aplicación actúe sobre tus recursos en otro servicio, con permisos limitados (scopes), sin conocer tu contraseña. OpenID Connect le agrega identidad: además del access token, un ID token que dice quién eres. Hay cuatro roles: el usuario (dueño de los recursos), el cliente (la app), el servidor de autorización (emite tokens) y el resource server (la API).

Otros flujos y errores a conocer:

  • Client credentials: para servicio a servicio, sin usuario. El servicio se autentica con su propia credencial y recibe un token con sus scopes.
  • El flujo implícito está en desuso: entregaba el token en la URL, donde se filtra en historiales y logs.
  • Validar las redirect URI exactas: aceptar cualquier URL "que empiece con" la registrada permite que un atacante reciba el código.

PKCE paso a paso: el secreto que nunca viaja

El paso delicado del flujo es el canje del código. El código vuelve a tu app por el navegador, y el navegador es un lugar con fugas: el código queda en el historial, en los logs del servidor, y en el móvil puede llegar a otra app que registró el mismo esquema de URL (miapp://callback). Si un atacante intercepta ese código, ¿qué le impide canjearlo por los tokens? Eso es lo que resuelve PKCE (se pronuncia "pixy").

Es un algoritmo automático, definido en la RFC 7636, y el usuario no ve nada de él. Documentado Tu app hace tres cosas:

  1. Antes de empezar: genera un secretoEl code_verifier, 43 a 128 caracteres aleatorios, que se queda en la memoria de la app. Calcula su hash, el code_challenge = BASE64URL(SHA256(verifier)).
  2. Al pedir el código: manda el hashEn la URL de /authorize va el code_challenge, nunca el verifier. El servidor de autorización lo guarda junto al código que va a emitir. Del hash no se puede volver al verifier.
  3. Al canjear el código: manda el secreto originalEn el POST /token, tu app envía el code_verifier. El servidor le aplica SHA-256 y compara con el challenge que guardó. Si coinciden, entrega los tokens. Un atacante que interceptó el código no tiene el verifier —nunca salió de la memoria de tu app— y no puede reconstruirlo desde el challenge, porque un hash no se invierte.

Pruébalo: genera un verifier, mira su challenge, y después intenta canjear el código como la app (que tiene el verifier) o como un atacante (que robó el código pero no el verifier, o que solo vio el challenge).

10.4API keys

Para APIs que consumen servidores de otras empresas, las API keys siguen siendo lo más práctico. El diseño que usan los proveedores serios:

  1. Formato reconocibleUn prefijo con el tipo y el entorno más una parte aleatoria larga: sk_live_…, sk_test_…. El prefijo permite detectarlas en repositorios públicos; GitHub escanea los repositorios buscando formatos de claves de proveedores asociados y les avisa cuando encuentra una. Documentado
  2. Guardar solo un hashLa clave completa se muestra una sola vez al crearla. Como es larga y aleatoria, basta un SHA-256 (no hace falta bcrypt). Para buscarla, se indexa por el hash.
  3. Scopes y restriccionesSolo lectura, solo ciertos endpoints, IPs permitidas. La clave de un proceso de reportes no debería poder emitir reembolsos.
  4. Rotación sin cortesDos claves activas a la vez: el cliente cambia a la nueva, verifica y revoca la vieja.

10.5Identidad entre servicios

Dentro del sistema, cada servicio necesita saber con certeza quién lo llama, sin confiar en "viene de la red interna". Con mTLS, ambos extremos presentan certificados de corta duración (horas) emitidos automáticamente por una autoridad interna; el estándar SPIFFE define identidades del tipo spiffe://empresa/ns/pagos/sa/api. Un service mesh (M03) suele encargarse de todo esto sin tocar el código. Sobre esa identidad se escriben políticas: "solo el servicio de checkout puede llamar a POST /pagos". Es el núcleo de lo que se llama zero trust: ninguna request se acepta por venir de dentro.

10.6Secretos, cifrado y KMS

Los secretos (contraseñas de bases, claves de APIs de terceros, claves de firma) no van en el código, ni en el repositorio, ni en variables de entorno que terminan en logs. Van en un gestor de secretos, se entregan a cada servicio con su identidad, se rotan y cada acceso queda auditado.

Para cifrar datos en reposo a gran escala se usa envelope encryption con un KMS. La primera vez cuesta entenderlo, así que hay dos versiones de lo mismo: el diagrama tal cual, y una explicación desde cero con una analogía y más detalle. Empieza por la que te sirva.

Analogía

Piensa en un banco. La bóveda es el KMS: nunca se mueve y casi nadie entra. Dentro hay una llave maestra (la KEK) que jamás sale de la bóveda. Cada documento que guardas va en un sobre cerrado con su propio candado (la DEK: una llave distinta por documento). ¿Dónde guardas la llave de cada candado? No en tu bolsillo: la metes en una cajita que solo la bóveda sabe abrir, y guardas la cajita junto al sobre. Para leer un documento, le llevas la cajita a la bóveda, que te devuelve la llave del candado; abres el sobre, lees, y tiras la llave. Nunca sacaste la llave maestra, y aun así cifraste millones de documentos sin molestar a la bóveda más que con una cajita diminuta cada vez.

Traducido: la DEK (clave de datos) cifra el dato; la KEK (clave maestra) cifra la DEK. Se guarda el dato cifrado junto a la DEK cifrada. Esto resuelve dos problemas a la vez. Primero, el KMS nunca ve tus datos: solo cifra y descifra claves de 32 bytes. Segundo, puedes cifrar un archivo de un gigabyte sin mandarlo a ningún lado.

  1. CifrarTu servicio le pide al KMS una DEK nueva (GenerateDataKey). El KMS devuelve dos copias: la DEK en claro y la DEK cifrada con la KEK. Tu servicio cifra el dato con la DEK en claro, en su propia CPU, borra la DEK en claro de memoria, y guarda el dato cifrado junto a la DEK cifrada.
  2. LeerTu servicio lee el dato cifrado y la DEK cifrada. Manda al KMS solo la DEK cifrada (Decrypt); el KMS la desenvuelve dentro de su hardware y la devuelve en claro. Con ella, tu servicio descifra el dato localmente. Cada Decrypt queda registrado: quién, cuándo, para qué.
  3. Rotar la clave maestraCuando toca cambiar la KEK, el KMS crea una versión nueva y conserva la vieja. Lo nuevo se envuelve con la versión nueva; lo viejo se sigue abriendo con la versión vieja. No se recifran los datos. Si hay que retirar del todo una versión vieja, se recifran las DEK (unos cientos de bytes por fila), nunca los datos.
  4. Borrar criptográficamenteSi destruyes una KEK, todas las DEK que envolvió quedan imposibles de abrir, y con ellas todos los datos, en todas las copias a la vez. Es la base del borrado criptográfico que viene abajo.

Pruébalo en las cuatro escenas: cifrar, leer, rotar la clave maestra y el borrado criptográfico.

Dos detalles que no se ven en el dibujo

El nonce
AES-GCM necesita, además de la clave, un número que no se repita (el nonce, 12 bytes aleatorios). Se guarda junto al dato cifrado, en claro: no es secreto, pero repetir un nonce con la misma clave rompe el cifrado. Por eso una DEK por dato, o un nonce aleatorio por mensaje, evita el problema.
El contexto de cifrado (AAD)
Al pedir el Decrypt se puede exigir un "contexto" (por ejemplo, {tenant: acme, tabla: facturas}). El KMS solo desenvuelve la DEK si el contexto coincide con el del cifrado. Así una DEK cifrada para una fila no sirve para otra, aunque alguien la copie en la base.

Trade-off

¿Por qué no cifrar todo directamente con la KEK y ahorrarse las DEK? Porque el KMS no está hecho para eso. Encrypt de AWS KMS acepta como máximo 4 KB de datos, cada llamada es una ida y vuelta por la red y cada una se cobra (del orden de 0.03 USD por cada 10 000 requests). Documentado Cifrar un video llamando al KMS sería imposible y carísimo. Con envelope encryption, el KMS solo toca la DEK —32 bytes— una vez al cifrar y una al leer, y el trabajo pesado (AES sobre gigabytes) lo hace tu CPU, que es gratis y rápida.

Borrado criptográfico: borrar lo que no puedes alcanzar

Un pedido de borrado del GDPR ("borren todos mis datos") tiene una parte fácil y una difícil. La fácil es el DELETE en la base. La difícil son las copias que no puedes editar: los backups de los últimos 30 días, que a propósito son inmutables (si un backup se pudiera editar, no serviría para recuperarse de un ataque). No puedes entrar a cada backup a borrar unas filas.

El borrado criptográfico (crypto-shredding) le da la vuelta al problema: si el dato está cifrado y destruyes la clave, el dato queda ilegible en todos lados a la vez, aunque no puedas tocarlo. La idea es dar a cada usuario (o a cada tenant) su propia clave, en una jerarquía:

  • Una KEK por tenant o por usuario en el KMS. Los datos de cada uno se cifran con DEK envueltas por su KEK.
  • Para borrar a un usuario: DELETE en la base y programar la destrucción de su KEK en el KMS.
  • Cuando el KMS destruye la KEK, las DEK de ese usuario que quedaron en los backups ya no se pueden desenvolver. Los datos cifrados siguen ahí, pero son ruido.

La clave del diseño: hay que destruir algo que no esté en los backups. Si la KEK del usuario estuviera guardada en tu base y esa base se respalda, restaurar un backup viejo la traería de vuelta. Por eso la KEK vive en el KMS, no en tu base. Dos formas de hacerlo:

Dónde vive la clave a destruirCómo se destruyeCuidado con
Una KEK por usuario en el KMSScheduleKeyDeletion: AWS KMS obliga a esperar de 7 a 30 días antes de destruirla, por si fue un error. DocumentadoCada KEK cuesta (del orden de 1 USD al mes); millones de usuarios con una KEK cada uno se vuelve caro. Sirve mejor por tenant.
Una tabla de claves sin backups (o con retención corta)Un DELETE normal: como la tabla no se respalda, no reaparece al restaurar.Esa tabla es ahora un punto único de pérdida: si la pierdes, pierdes todos los datos. Necesita su propia protección.
 
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

# Cifrar un mensaje con la clave del usuario (envelope encryption)
dek_claro, dek_cifrada = kms.generate_data_key(KeyId=kek_de(user_id), KeySpec="AES_256")
nonce = os.urandom(12)
ciphertext = AESGCM(dek_claro).encrypt(nonce, mensaje, aad=f"user:{user_id}".encode())
del dek_claro                                    # fuera de memoria cuanto antes
db.insert(mensajes, user_id=user_id, nonce=nonce, dek_cifrada=dek_cifrada, ciphertext=ciphertext)

# Borrado criptográfico: el usuario ejerce su derecho al olvido
db.delete(mensajes, user_id=user_id)             # la parte fácil
kms.schedule_key_deletion(KeyId=kek_de(user_id), PendingWindowInDays=7)   # la parte que alcanza a los backups
audit.log(actor="system", action="user.crypto_shred", target=user_id, result="ok")   # sin PII

Qué derrota al borrado criptográfico

El borrado solo vale si el dato en claro no se escapó por otro lado antes. Cada una de estas copias sobrevive a destruir la clave: los logs donde se registró el contenido, los índices de búsqueda, las cachés, los almacenes de analítica, los embeddings de un RAG y la propia DEK si quedó cacheada en memoria de un servicio. El borrado criptográfico es la última línea, no la única: hay que recolectar poco, no escribir datos personales en los logs (10.8) y tener un proceso de borrado que llegue a todas esas copias.

Honestidad: el GDPR no nombra esta técnica. Habla de "borrado" y de "seudonimización"; el borrado criptográfico es una forma de ingeniería, aceptada en la práctica, de cumplir el derecho al olvido cuando el borrado físico no alcanza. Diseño de referencia Se registra en el log de auditoría una lápida sin datos personales: qué usuario, cuándo y que se destruyó la clave.

10.7Aislamiento multi-tenant

En un SaaS, el peor incidente posible es que un cliente vea los datos de otro. El error que lo causa casi siempre es el mismo: BOLA (también llamado IDOR), una consulta que filtra por el id del objeto pero no por el tenant. Las defensas, en capas:

  • El tenant sale del token, nunca de la request: el cliente no puede elegir su tenant enviando un parámetro.
  • Filtro obligatorio en la capa de datos: un repositorio que agrega tenant_id a toda consulta, y pruebas que verifican que ninguna consulta lo omite.
  • Row-level security en PostgreSQL como red de seguridad: aunque el código olvide el filtro, la base no devuelve filas de otro tenant. Es una política de la propia base, y se explica a fondo —con sus trampas— en M05.
ALTER TABLE facturas ENABLE ROW LEVEL SECURITY;

CREATE POLICY aislamiento_tenant ON facturas
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- En cada request, la aplicación fija el tenant del token antes de consultar:
SET LOCAL app.tenant_id = '6f1c…';
SELECT * FROM facturas WHERE id = $1;   -- una factura de otro tenant simplemente no aparece

El otro eje del aislamiento es la capacidad: límites por tenant (M08) para que un cliente ruidoso no degrade a los demás, y en clientes muy grandes, su propia base o su propia celda.

Qué pasa con un SSRF en la nube

En 2019, una vulnerabilidad SSRF en un firewall de aplicaciones mal configurado permitió a una atacante pedir credenciales al servicio de metadatos de AWS desde dentro de la infraestructura de Capital One, y con ellas leer datos de más de 100 millones de personas. Documentado A raíz de casos así, AWS lanzó IMDSv2, que exige un token de sesión obtenido con un PUT y no se puede disparar con un simple GET redirigido.

BOLA: pedir el objeto de otro

Cómo funciona. La API comprueba que estás autenticado, pero no que el objeto que pides sea tuyo. Tienes la factura 123 y pides la 124: si el código hace SELECT * FROM facturas WHERE id = 124 sin mirar el dueño, te la entrega. Es el riesgo número uno del OWASP API Top 10 y el más común en las filtraciones de datos entre usuarios.

Mitigación. Autorizar por objeto, no solo por sesión, y en la capa de datos. El tenant y el usuario salen del token (10.2); la consulta siempre los incluye; row-level security (10.7, M05) es la red de seguridad.

-- Vulnerable: confía en el id que mandó el cliente
SELECT * FROM facturas WHERE id = $1;

-- Correcto: ata el objeto al dueño verificado por el token
SELECT * FROM facturas WHERE id = $1 AND tenant_id = $2;   -- $2 sale del token, no de la request

Cómo detectarlo. Un pico de respuestas 403 o 404 por una cuenta que prueba ids secuenciales; un usuario que accede a muchos objetos de tenants distintos. Pruebas automáticas que, para cada endpoint con id, repiten la request con el token de otro usuario y esperan un 404.

BFLA y asignación masiva: hacer de más

Cómo funciona. Dos primos de BOLA. En BFLA (autorización de función rota) el objeto es tuyo, pero la acción no debería serlo: llamas a DELETE /usuarios/88 o POST /admin/reembolsos siendo un usuario normal, y la API no comprueba el rol. En la asignación masiva, la API vuelca el JSON que mandas directo sobre el objeto, y agregas un campo que no deberías poder tocar: {"email": "...", "role": "admin"} en un endpoint de editar perfil.

Mitigación. Para BFLA, comprobar el permiso de la acción en cada endpoint que cambia estado, no solo en la UI que lo esconde. Para la asignación masiva, una lista explícita de campos aceptados (un DTO), nunca "guarda todo lo que vino".

# Vulnerable: escribe cualquier campo que venga en el cuerpo
usuario.update(**request.json)              # el cliente manda "role": "admin"

# Correcto: solo los campos permitidos para esta acción
usuario.nombre = datos.nombre
usuario.avatar = datos.avatar               # "role" no está en la lista: se ignora

Cómo detectarlo. Registrar los cambios de campos sensibles (rol, permisos, estado de pago) en el log de auditoría; alertar si cambian fuera del flujo de administración.

Inyección SQL

Cómo funciona. Datos del usuario concatenados dentro de una consulta. Un campo de búsqueda con '; DROP TABLE… o con una subconsulta cambia lo que la base ejecuta. En 2015, una atacante usó inyección SQL para leer los datos de 156 959 clientes de TalkTalk; el regulador británico multó a la empresa con 400 000 libras porque la misma vulnerabilidad ya había sido explotada meses antes y la habían ignorado. Documentado

Mitigación. Consultas parametrizadas, siempre: el dato viaja como parámetro, nunca como texto de la consulta. Es gratis y cierra la clase entera de ataques.

# Vulnerable: el nombre se vuelve parte del SQL
cursor.execute("SELECT * FROM clientes WHERE nombre = '" + nombre + "'")

# Correcto: el nombre es un parámetro, nunca código
cursor.execute("SELECT * FROM clientes WHERE nombre = %s", (nombre,))

Cómo detectarlo. Errores de SQL en los logs con fragmentos de entrada del usuario; un WAF que marca patrones de inyección; revisiones que prohíben construir SQL con concatenación de cadenas.

XSS y CSRF: atacar por el navegador de la víctima

Cómo funcionan. En el XSS (cross-site scripting), el atacante logra que su JavaScript corra en tu página, en el navegador de la víctima: así lee tokens, cookies accesibles o lo que el usuario escribe. Hay tres tipos: almacenado (el script queda guardado, por ejemplo en un comentario, y se sirve a todos), reflejado (viaja en un parámetro de la URL que la página devuelve sin escapar) y de DOM (el propio JavaScript de la página mete datos no confiables en el HTML). En el CSRF (cross-site request forgery), otro sitio hace que el navegador de la víctima dispare una acción en el tuyo aprovechando que sus cookies viajan solas.

Mitigación. Contra XSS: escapar todo lo que se pinta en la página según el contexto (el framework moderno lo hace si no lo esquivas), una Content-Security-Policy que limite qué scripts corren, y cookies HttpOnly para que un XSS no lea la sesión. Contra CSRF: cookies SameSite=Lax o Strict, y un token anti-CSRF en los formularios.

Cómo detectarlo. Reportes de violación de la CSP (llegan a un endpoint que tú defines), picos de requests con payloads sospechosos en los parámetros, y revisiones que prohíben insertar HTML sin escapar.

Ataques al propio JWT

Cómo funcionan. Tres clásicos, todos por confiar en lo que dice el token en vez de en lo que fija el servidor. alg: none: el atacante quita la firma y pone el algoritmo en "none"; si la librería le cree, acepta un token sin firmar. Confusión de algoritmo (RS256 a HS256): el atacante firma con la clave pública (que es, justamente, pública) tratándola como secreto de HMAC; si el servidor no fija el algoritmo, verifica con ella y pasa. kid malicioso: el campo que elige la clave apunta a un archivo o a una inyección que el atacante controla.

Mitigación. El servidor fija el algoritmo y la clave; nunca los lee del token. El laboratorio de 10.2 deja probar alg: none y ver por qué se rechaza.

# Vulnerable: confía en el header del token
jwt.decode(token, clave, algorithms=jwt.get_unverified_header(token)["alg"])

# Correcto: el algoritmo lo decide el servidor
jwt.decode(token, clave_publica, algorithms=["ES256"], audience="api.miapp.ia", issuer="https://auth.miapp.ia")

Cómo detectarlo. Alertar sobre tokens que llegan con alg inesperado o kid desconocido; contar los 401 por firma inválida.

Relleno de credenciales y robo de sesión

Cómo funcionan. En el relleno de credenciales, el atacante prueba masivamente usuarios y contraseñas filtrados de otros sitios, apostando a que la gente las reutiliza. En 2023, un ataque así sobre unas 14 000 cuentas de 23andMe (clientes que reusaron contraseñas y no tenían segundo factor) terminó exponiendo datos de 6.9 millones de personas, porque esas cuentas estaban conectadas a muchas otras. Documentado El robo de sesión o de refresh token salta la contraseña del todo: en 2023, un malware en la laptop de un ingeniero de CircleCI robó una cookie de sesión con el segundo factor ya resuelto, y con ella el atacante llegó a producción. Documentado

Mitigación. Contra el relleno: límites de tasa por cuenta y por IP (M08), segundo factor, y comparar contra listas de contraseñas filtradas al registrarse. Contra el robo de sesión: tokens de acceso cortos, rotación de refresh tokens con detección de reuso (10.2), y atar la sesión al dispositivo cuando el riesgo lo amerita.

Cómo detectarlo. Una tasa de fallos de login altísima con muchas IPs y pocas contraseñas por cuenta; un refresh token presentado dos veces (lo que dispara la revocación de la familia, 10.2); una sesión que aparece de golpe en otro país o con otro navegador.

El log de auditoría

Un log de auditoría responde, después de un incidente, la pregunta que siempre llega: ¿quién hizo qué, cuándo y desde dónde? No es lo mismo que los logs de la aplicación. Los logs de aplicación son para depurar, son ruidosos y se rotan en días; el de auditoría registra solo acciones sensibles, es la fuente para una investigación o una obligación legal, y se guarda mucho más tiempo. Cada entrada anota el actor, la acción, el objeto, el momento, el origen y el resultado, y para los cambios, el antes y el después.

  • Solo-añadir (append-only) y aparte: en un almacén separado que ni siquiera la aplicación pueda editar o borrar, como S3 con Object Lock (el mismo mecanismo que el ledger de pagos de M27). Si el atacante entra, no puede borrar sus huellas.
  • Encadenado por hash: cada entrada incluye el hash de la anterior, así cualquier borrado o cambio en medio se nota (la misma idea de una cadena de bloques, sin la parte distribuida).
  • Sin secretos ni datos personales de más: se registra "el usuario u_42 leyó la factura 7", no el contenido de la factura. El log se copia a muchos lugares; meterle datos sensibles los esparce.
  • Con retención definida: por obligación legal suelen ser años, y se decide antes, no después.

Las tablas de bitácora dentro de la base (triggers, pgAudit) se tratan en el módulo de seguridad en bases de datos (M35), de la Parte IV.

Sobre los datos personales (PII): recolectar solo lo necesario, cifrarlo, no escribirlo en logs (los logs se copian a muchos más lugares que la base), definir cuánto tiempo se retiene y tener un proceso de borrado que llegue también a réplicas, cachés, índices de búsqueda y backups (el borrado criptográfico de 10.6 ayuda con lo que no puedes alcanzar). Y registrar en el log de auditoría quién accedió a qué.

Ejercicio de diseño: la API pública de un producto de IA

Vas a exponer una API de un modelo de lenguaje a empresas. Tendrán API keys para sus servidores, un panel web para sus empleados con inicio de sesión corporativo, y permisos por proyecto. Los prompts de los clientes pueden contener datos confidenciales. Un cliente debe poder revocar una clave filtrada y que deje de funcionar en segundos.

Diseña la autenticación de cada tipo de acceso, la autorización por proyecto, el almacenamiento de claves y cómo proteges los prompts.

Ver la solución de referencia
  • API keys de servidor: formato sk-proj-… con prefijo escaneable, guardadas como SHA-256, asociadas a un proyecto y con scopes. El gateway valida la clave contra una caché con TTL de unos segundos, alimentada por eventos de revocación: una clave revocada deja de funcionar en segundos sin consultar la base en cada request.
  • Panel web: OIDC con el proveedor de identidad corporativo del cliente (SSO), authorization code con PKCE, sesión en cookie HttpOnly, Secure y SameSite=Lax.
  • Autorización: roles por proyecto (owner, member, reader) evaluados en cada request; el proyecto sale de la clave o de la sesión, nunca de un parámetro libre. Pruebas automáticas de BOLA para cada endpoint.
  • Prompts: cifrados en reposo con envelope encryption y una DEK por organización (permite crypto-shredding si el cliente se va), fuera de los logs de aplicación, con retención configurable (por ejemplo 30 días, o cero para clientes que lo exijan) y accesos auditados.
  • Entre servicios: mTLS con identidades SPIFFE; el servicio de inferencia solo acepta llamadas del gateway.
