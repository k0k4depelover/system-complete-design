12.1.1El mapa: un forward pass completo

En M12 el modelo fue una función: entran tokens, salen logits. Esa función tiene una forma muy regular. Casi todos los LLM actuales son un transformer decoder-only: una tabla que convierte cada token en un vector, una pila de bloques iguales que transforman esos vectores, y una capa final que convierte el último vector en un puntaje por token del vocabulario. Llamar al modelo una vez, con todos los tokens que entran en esa llamada, es un forward pass, o una pasada. El prefill es una pasada con todos los tokens del prompt; cada paso de decode es una pasada con un solo token por request.

La lámina muestra una pasada de Llama 3.1 70B, que usamos de ejemplo en todo el módulo porque es el de M12 y M13. Mírala entera antes de leer cada sección; vuelve a ella cuando un nombre se confunda con otro.

  1. IDs de tokensEl tokenizer convierte el texto en una lista de enteros, uno por token: T posiciones. M12.2
  2. Tabla de embeddingsUna matriz de 128 256 filas por 8192 columnas: cada ID elige una fila. Es una lectura, no una cuenta. 12.1.2
  3. Flujo residualLa matriz [T, 8192] que atraviesa los 80 bloques. Cada bloque le suma algo; nadie la reemplaza. 12.1.2
  4. RMSNormReescala cada vector antes de cada rama para que los números no crezcan con las 160 sumas. 12.1.2
  5. Proyecciones Q, K y VTres multiplicaciones de matrices: la consulta, la clave y el valor de cada token, repartidos en cabezas. 12.1.4
  6. RoPERota Q y K según la posición del token, para que la atención sepa qué está cerca de qué. 12.1.4
  7. Atención causalCada token compara su consulta con las claves de los anteriores y mezcla sus valores. Es lo único que mezcla información entre tokens. 12.1.4
  8. KV cacheLas K y V de cada token, por capa, guardadas para no recalcularlas en cada paso. 12.1.6
  9. Proyección OJunta las 64 cabezas en un vector de 8192 antes de sumarlo al flujo. 12.1.4
  10. Suma residualx = x + rama(x). Por eso cada bloque refina en lugar de reescribir. 12.1.2
  11. MLPTres matrices grandes (gate, up y down) que trabajan cada token por separado. Tiene el 82 % de los pesos de cada bloque. 12.1.2
  12. RMSNorm finalUna última normalización del vector que sale del bloque 80. 12.1.5
  13. LM headUna matriz de 8192 por 128 256: del vector final a un logit por token. Solo corre en la última posición. 12.1.5
  14. MuestreoTemperatura, top-k y top-p convierten los logits en un token elegido. 12.1.9

Analogía

Piensa en una carpeta que pasa por 80 escritorios en fila. En cada escritorio, alguien la lee, escribe notas en los márgenes y la pasa al siguiente; nadie borra lo que ya estaba. El primer empleado de cada escritorio (la atención) puede mirar las carpetas de los clientes anteriores, guardadas en un archivo (el KV cache); el segundo (el MLP) trabaja solo con esta carpeta. Al final, alguien lee la última página y escribe una palabra. Para escribir la siguiente palabra, la carpeta entera vuelve a recorrer los 80 escritorios, aunque ahora con una sola hoja nueva.

La suma da 70 554 millones, los 70.6 mil millones que anuncia Meta. Dos cosas salen de la tabla. La primera: el MLP tiene el 82 % de los pesos de cada bloque, así que es la pieza que más lee y más calcula. La segunda: la cuenta de M12, unas 2 operaciones por parámetro por token, sale de aquí. Cada peso de una matriz participa una vez por token en una multiplicación y una suma; la tabla de embeddings no suma nada porque solo se lee una fila.

Qué hace cada pieza del bloque

  • El flujo residual. La salida de la tabla de embeddings es una matriz [T, 8192], una fila por token. Esa matriz es el flujo residual: cada rama de cada bloque lee una copia normalizada, calcula algo y lo suma de vuelta, x = x + rama(x). Como nada se reemplaza, la información de las primeras capas llega intacta a las últimas, y las 80 capas se pueden entrenar sin que la señal se pierda en el camino.
  • La normalización. Antes de cada rama, RMSNorm divide cada vector por la raíz de la media de sus cuadrados y lo multiplica por 8192 pesos aprendidos. Sin eso, 160 sumas seguidas harían crecer los números sin control. Llama aplica la norma antes de cada rama (pre-norm), no después. Documentado
  • La atención. Es la única pieza que mezcla información entre tokens: cada posición mira las anteriores y trae lo que le sirve. Tiene la sección 12.1.4 para ella.
  • El MLP. Trabaja cada token por separado, sin mirar a los otros. Llama usa la variante SwiGLU: dos proyecciones a 28 672 (gate y up), una se pasa por la función SiLU y se multiplica elemento por elemento con la otra, y una tercera (down) vuelve a 8192. Documentado Se suele leer como la memoria de hechos del modelo: la atención decide qué información juntar y el MLP la transforma.

En código, una pasada completa es corta. Este esqueleto en Python es el modelo entero, sin los detalles de la atención, que vienen en 12.1.4:

def bloque(x, capa, cache):
    x = x + atencion(rmsnorm(x, capa.norm_1), capa, cache)   # mezcla entre tokens
    x = x + mlp(rmsnorm(x, capa.norm_2), capa)               # cada token por separado
    return x

def mlp(x, capa):
    return (silu(x @ capa.W_gate) * (x @ capa.W_up)) @ capa.W_down

def forward(ids, modelo, cache):
    x = modelo.embedding[ids]                  # [T, 8192]: una fila de la tabla por token
    for i, capa in enumerate(modelo.capas):    # 80 bloques, siempre en orden
        x = bloque(x, capa, cache[i])
    x = rmsnorm(x[-1], modelo.norm_final)      # solo la última posición
    return x @ modelo.lm_head                  # [128 256]: un logit por token del vocabulario

Fíjate en que la función es la misma para el prefill y para el decode. Lo único que cambia es T: 2000 en el prefill de un prompt de 2000 tokens, 1 en cada paso de decode. Todo lo que sigue en el módulo sale de esa diferencia.

12.1.3Una multiplicación de matrices, contada

Casi todo el tiempo de una pasada se va en multiplicar la matriz de activaciones [T, a] por una matriz de pesos [a, b]. Esa operación tiene dos costos que se cuentan por separado:

FLOPs = 2 × T × a × b   ·   bytes ≈ a × b × bytes por peso + T × (a + b) × 2

El primer término de los bytes son los pesos, que se leen una vez por pasada sin importar T. El segundo son las activaciones que entran y salen, en BF16. Dividir FLOPs por bytes da la intensidad aritmética, las operaciones por byte leído (M13.3). Cuando T es chico frente a a y b, los pesos dominan los bytes y la cuenta se simplifica: la intensidad es 2 × T ÷ bytes por peso. Cada fila de activaciones reutiliza los pesos ya leídos; más filas, más cuentas por el mismo viaje a memoria.

A esa operación se le dice GEMM (matriz por matriz) cuando T es grande, y GEMV (matriz por vector) cuando T es 1. El nombre importa porque las bibliotecas y los profilers los distinguen: la misma capa corre como GEMM en el prefill y como GEMV en el decode de un solo usuario.

Con la proyección Q de Llama 3.1 70B, de 8192 por 8192, la intensidad según cuántos tokens entran en la pasada es esta. La H100 cambia de régimen en 590 FLOP por byte en FP8 y en 295 en BF16 (989 TFLOPS ÷ 3.35 TB/s):

La regla que sale de la tabla: desde unos 300 tokens por pasada, una proyección deja de esperar a la memoria, en FP8 o en BF16. El prefill de un prompt mediano pasa ese umbral de sobra. El decode llega a él solo si junta cientos de usuarios en el mismo paso, porque en el decode T es la cantidad de usuarios del batch: cada uno aporta una fila. Es la misma cuenta de M12.5, ahora vista desde una sola matriz.

Definición

Tokens por pasada tokens per forward pass

La cantidad de filas que entran a cada multiplicación de matrices en una pasada: los tokens de prefill más un token por usuario en decode.

Intuición
Cada viaje a la memoria trae los pesos de una capa; cuantas más filas los usan antes de tirarlos, más trabajo útil por viaje.
Ejemplo
Un prefill de 2000 tokens: 2000 filas. Un paso de decode con 64 usuarios: 64 filas. Un paso mixto con un trozo de 512 y 64 usuarios: 576.
Por qué importa en producción
Es la perilla que los motores mueven: el continuous batching suma filas de decode y el chunked prefill elige cuántas de prefill entran en cada paso (M15).

12.1.4La atención por dentro

La atención responde, para cada token, una pregunta: de todo lo que vino antes, ¿qué me sirve? Lo hace con tres vectores por token y por cabeza, que salen de las proyecciones de la lámina (marca 5):

  • Q, la consulta: qué está buscando este token.
  • K, la clave: qué ofrece cada token, para ser encontrado.
  • V, el valor: lo que entrega cada token si lo eligen.

Analogía

Una biblioteca. La consulta es lo que le preguntas al bibliotecario; cada libro tiene una etiqueta en el lomo (la clave) y un contenido (el valor). El bibliotecario compara tu pregunta con todas las etiquetas, le da a cada libro un puntaje según cuánto se parece, y te arma un resumen que mezcla los contenidos en proporción a esos puntajes. La máscara causal es una regla de la biblioteca: solo puedes consultar libros que llegaron antes que tú.

Paso a paso, en una capa y una cabeza:

  1. ProyectarQ = x · W_q, K = x · W_k, V = x · W_v. En Llama 3.1 70B, Q tiene 64 cabezas de 128 números y K y V tienen 8.
  2. RotarRoPE gira cada par de números de Q y K un ángulo que depende de la posición. Así el producto de una consulta y una clave depende de cuán lejos están los dos tokens (M16.5). V no se rota.
  3. CompararEl puntaje entre la consulta i y la clave j es su producto escalar dividido por √128 ≈ 11.3: S = Q · Kᵀ ÷ √128.
  4. Tapar el futuroLa máscara causal pone −∞ en los puntajes de las claves posteriores a la consulta. Ningún token puede mirar a uno que todavía no existía cuando se generó.
  5. NormalizarSoftmax convierte cada fila de puntajes en pesos positivos que suman 1: eˢ dividido por la suma de eˢ de la fila. Un −∞ da peso 0.
  6. MezclarLa salida de la consulta i es la suma de los V de cada token pesados por esos pesos. Las 64 cabezas se pegan en un vector de 8192 y la proyección O lo mezcla antes de sumarlo al flujo residual.

¿Por qué dividir por √128? El producto escalar de dos vectores de 128 números al azar tiene una dispersión que crece con √128. Sin la división, los puntajes serían tan grandes que softmax daría casi todo el peso a una sola clave, y en el entrenamiento los gradientes se apagarían. Es la escala que propuso el paper original del transformer. Documentado

Con GQA (M12.4), las 64 consultas no tienen cada una su K y su V: se reparten en 8 grupos, y cada grupo lee el mismo par. El cálculo de la atención sigue siendo de 64 cabezas; lo que baja es lo que se guarda y se lee. Documentado

La atención entera cabe en unas líneas de NumPy. Este programa la calcula de dos maneras: con el prefill de 7 tokens y un paso de decode que usa el cache, y recalculando los 8 tokens desde cero. La última fila sale igual, y esa igualdad es la razón por la que existe el KV cache: guardar K y V no aproxima nada, solo evita repetir cuentas.

import numpy as np

rng = np.random.default_rng(0)
d, dh = 64, 16                       # ancho del modelo y de la cabeza (de juguete)
Wq, Wk, Wv = (rng.normal(size=(d, dh)) / d**0.5 for _ in range(3))

def softmax(x):
    x = x - x.max(axis=-1, keepdims=True)          # estabilidad numérica: no cambia el resultado
    e = np.exp(x)
    return e / e.sum(axis=-1, keepdims=True)

def atencion(X):
    """Prefill: todas las posiciones a la vez, con máscara causal."""
    Q, K, V = X @ Wq, X @ Wk, X @ Wv                   # [T, dh] cada una
    S = Q @ K.T / dh**0.5                              # [T, T]: cada consulta contra cada clave
    futuro = np.triu(np.ones_like(S, dtype=bool), k=1)
    S[futuro] = -np.inf                                # nadie mira tokens posteriores
    return softmax(S) @ V, K, V                        # [T, dh], y K y V para el cache

def paso_decode(x, K_cache, V_cache):
    """Decode: una sola posición nueva contra todo lo guardado."""
    q, k, v = x @ Wq, x @ Wk, x @ Wv                   # [dh] cada una
    K_cache = np.vstack([K_cache, k])                  # se agrega, no se recalcula
    V_cache = np.vstack([V_cache, v])
    s = K_cache @ q / dh**0.5                          # [T + 1]: una fila de la matriz
    return softmax(s) @ V_cache, K_cache, V_cache

X = rng.normal(size=(8, d))                            # 8 tokens: 7 de prompt y 1 nuevo
_, K, V = atencion(X[:7])                              # prefill del prompt
fila, K, V = paso_decode(X[7], K, V)                   # decode del token 8
completo, _, _ = atencion(X)                           # sin cache: recalcular los 8
print(np.allclose(fila, completo[-1]))                 # True: el mismo resultado

El simulador muestra la matriz de puntajes de una cabeza mientras se genera una respuesta. Prueba primero con el KV cache y después sin él, y compara las celdas calculadas en total:

Con 7 tokens de prompt y 6 pasos de decode, el cache deja el total en 91 celdas, una por cada par posible. Sin el cache, cada paso recalcula el triángulo entero y el total sube a 399. La diferencia crece con el cuadrado del largo: en una respuesta de 500 tokens sobre un prompt de 2000, recalcular todo en cada paso haría unas 1000 veces más trabajo de atención, y además habría que recalcular las proyecciones de todos los tokens.

Lo que cuesta la atención

En el prefill, cada una de las T consultas se compara con hasta T claves, en 64 cabezas de 128 números, dos veces (QKᵀ y la suma de los V). Con la máscara causal, los kernels se saltean la mitad tapada:

FLOPs de la atención en un prefill ≈ 2 × T² × 8192 × 80 = 1.31 millones × T²

Las proyecciones y el MLP cuestan unas 2 × 70 600 millones × T, en línea recta con T. Las dos cuentas se igualan cuando T ≈ 70 600 millones ÷ (8192 × 80), unos 108 000 tokens. Por debajo, la atención es una parte chica del prefill: el 1.8 % con 2000 tokens. Por encima, domina. Es la curva que dibuja M16.1.

La matriz que no cabe: FlashAttention

El problema de la atención no son solo los FLOPs. Escrita de la manera directa, calcula la matriz de puntajes S entera, la guarda en la HBM, la vuelve a leer para el softmax y otra vez para multiplicarla por V. Esa matriz tiene T × T valores por cabeza. Con 2000 tokens y 64 cabezas en BF16 son 512 MB por capa; con 32 768 tokens, 137 GB por capa, más que la memoria de una H100.

FlashAttention calcula lo mismo sin escribir esa matriz. Documentado Trae a la SRAM del chip (M13.1) un bloque de consultas y va recorriendo bloques de claves y valores; calcula cada pedazo de S ahí mismo, lo usa y lo tira. El truco que lo permite es el softmax en línea: para cada consulta guarda el máximo de los puntajes vistos y la suma de sus exponenciales. Cuando un bloque nuevo trae un máximo mayor, reescala lo acumulado por e elevado a la diferencia de máximos y sigue. Al final el resultado es exacto, idéntico al de la matriz completa, y la memoria extra crece con T y no con T².

La primera versión es de 2022; FlashAttention-2 (2023) reparte mejor el trabajo entre los SMs y FlashAttention-3 (2024) usa las instrucciones de la H100 y FP8. Documentado En el decode el problema cambia: hay una sola consulta por usuario, así que no hay bloques de consultas que repartir entre los SMs. Flash-Decoding (2023) reparte entonces el largo del cache: cada SM procesa un tramo de claves y valores, y los resultados se combinan con el mismo softmax en línea. Documentado

12.1.5Prefill paso a paso

Antes de que la GPU vea un token, la request recorre el servidor. El diagrama sigue a una request de 2000 tokens de prompt de punta a punta; esta sección se ocupa de su primera pasada, y la siguiente, de las demás.

  1. Plantilla y tokenizerEn la CPU: los mensajes se envuelven con la plantilla de chat y se tokenizan. Resultan 2000 IDs (M12.2).
  2. AdmisiónEl scheduler del motor la admite cuando hay bloques libres de KV cache para sus 2000 tokens. Si el prompt empieza con un prefijo que ya está en el cache, como un prompt de sistema compartido, esos tokens no se recalculan (M15.4).
  3. EmbeddingSe leen 2000 filas de la tabla: una matriz [2000, 8192]. Son 33 MB en BF16 y ninguna cuenta.
  4. 80 bloquesEn cada uno, las proyecciones y el MLP son GEMMs de 2000 filas. RoPE usa las posiciones 0 a 1999. K y V de los 2000 tokens se escriben en el cache: 4 kB por token y capa, 655 MB en total. La atención causal corre con FlashAttention.
  5. LM head en una sola posiciónSolo hace falta el logit de la última posición, porque el siguiente token sale de ahí. Aplicar el LM head a una fila cuesta 2 × 8192 × 128 256 ≈ 2100 millones de FLOPs; aplicarlo a las 2000 costaría 4.2 billones, el 1.5 % del prefill, para descartarlos.
  6. Primer tokenEl muestreo elige un token, que sale por el stream (M17). Ahí termina el TTFT.

¿Cuánto tarda? Con Llama 3.1 70B en FP8 sobre 4 H100, el cómputo al 40 % del pico y cada pieza limitada por el mayor de sus dos costos (el modelo de la calculadora de 12.1.7):

Tres lecturas de la tabla:

  • El TTFT crece en línea recta con el prompt mientras la atención es chica, y más rápido después. Cuatro veces más prompt, de 2000 a 8000, son 4.2 veces más prefill.
  • Un prompt corto cuesta casi lo mismo que un paso de decode. Con 100 tokens, la pasada está por debajo del quiebre de 12.1.3 y la limita leer los 70.6 GB de pesos: 5.4 ms, contra 5.3 ms de un paso de decode. El TTFT tiene un piso, una lectura completa de los pesos, por corto que sea el prompt.
  • El prefill procesa tokens mucho más rápido que el decode. 2000 tokens en 88 ms son unos 22 700 tokens por segundo para una sola request; el decode de esa misma request da 189 por segundo. Por eso las APIs cobran bastante menos por un token de entrada que por uno de salida (M12.7).

En producción real

El TTFT que ve el usuario es la cola, más el prefill, más la red. Si el TTFT sube sin que suba el largo de los prompts, la causa suele ser la cola, y se arregla con capacidad (M19). Si sube con el largo del prompt, es el prefill: se ataca con prefix caching, que evita recalcular lo repetido, con chunked prefill o desagregación, que lo separan del decode (12.1.8), o recortando el contexto (M16.3). Distinguirlos exige spans separados de cola y prefill en el trace (M11).

12.1.6Decode paso a paso

Después del prefill, la request está en el batch de decode del motor. Cada paso hace la misma pasada de la lámina con un solo token por usuario. Para el token 2001 de nuestra request:

  1. Una filaSe lee la fila del token anterior en la tabla: [1, 8192]. Si hay 64 usuarios en el batch, son 64 filas, una de cada uno.
  2. 80 bloquesCada proyección y el MLP leen sus pesos enteros para multiplicarlos por esas pocas filas. RoPE usa la posición 2000. K y V del token nuevo se agregan al cache de cada capa.
  3. Atención contra el cacheLa consulta del token nuevo se compara con las 2001 claves de su capa y mezcla los 2001 valores: hay que leer los 2000 pares guardados.
  4. LM head y muestreoUna fila por usuario, un token por usuario. El token se convierte en texto y sale por el stream.

Lo que se lee en un paso de decode de un solo usuario con 4000 tokens de contexto, con los pesos en FP8, el KV en BF16 y 4 H100 que leen 13.4 TB/s en total:

5.29 ms por token son 189 tokens por segundo. En esos 5.29 ms la GPU hace unas 150 000 millones de operaciones; al 40 % de su pico podría hacer 16.7 billones. Usa menos del 1 % de su cómputo: el resto del tiempo espera a la memoria.

Analogía

Un cocinero que, para cada plato, tiene que traer a la mesa la despensa entera, abrir cada frasco una vez y devolverla. Cocinar es rápido; el viaje a la despensa no. Si cocina un plato por viaje, pasa casi todo el tiempo caminando. Si cocina 64 platos con el mismo viaje, el viaje se reparte entre los 64. Pero cada comensal trae además su propia caja de apuntes (su KV cache), que hay que leer entera para su plato, y esas cajas no se comparten.

El KV cache por dentro

El cache de una request es una pila de 80 capas. En cada capa hay 8 cabezas, y cada cabeza guarda, por token, un vector K y un vector V de 128 números. Cada paso de decode agrega una columna al final de todas las cabezas de todas las capas. Los motores no reservan un arreglo contiguo por request: lo reparten en bloques de un número fijo de tokens, como páginas de memoria, para no desperdiciar espacio con reservas al largo máximo (M15.3).

La atención del decode tiene una propiedad incómoda. Por cada token del contexto, una consulta hace 2 × 64 × 128 operaciones contra su clave y otras tantas con su valor: 32 768 por capa. Para eso lee K y V de las 8 cabezas de KV: 2 × 8 × 128 × 2 bytes = 4096 bytes. La intensidad es 8 FLOP por byte, sin importar cuántos usuarios haya en el batch, porque cada usuario lee su propio cache. Juntar usuarios ayuda a las proyecciones y al MLP, que comparten los pesos, pero no a la atención. Sin GQA, con 64 cabezas de KV, sería 1; con el KV en FP8, 16. MLA, la atención de DeepSeek (M12.4), reconstruye K y V desde un vector comprimido y hace más cuentas por byte leído. Esa es la razón de fondo por la que la arquitectura de la atención pesa tanto en el costo de servir un modelo.

Lo que no es cómputo ni memoria

Un paso de 5 ms es tan corto que aparecen costos que en el prefill no se notan:

  • Lanzar kernels. Un paso son cientos de kernels: varios por capa, por 80 capas. Lanzar cada uno desde la CPU cuesta microsegundos, y con batches chicos ese tiempo se acerca al de las cuentas. Los CUDA graphs graban la secuencia de un paso una vez y la relanzan entera con una sola llamada (M15.8). Documentado
  • Sincronizar las GPUs. Con tensor parallelism, cada GPU tiene un pedazo de cada matriz y hay que juntar los resultados dos veces por capa, después de la atención y después del MLP: 160 all-reduce por paso. Documentado Cada uno mueve poco, 8192 × 2 bytes = 16 kB por usuario, así que no lo limita el ancho de banda de NVLink sino la latencia de cada sincronización, que se paga 160 veces.
  • La CPU. Armar el batch del paso siguiente, convertir tokens en texto, revisar stop sequences y escribir en cada stream son trabajo de CPU. Si la CPU tarda más que la GPU, la GPU espera. vLLM rediseñó su motor en 2025 (V1) en buena parte para solapar ese trabajo con el de la GPU. Documentado

12.1.7Dónde se va el tiempo de una pasada

La calculadora junta todo lo anterior. Elige cuántos tokens de prefill y cuántos usuarios en decode entran en la pasada, y mira qué pieza se lleva el tiempo y qué la limita. Cada pieza tarda lo que diga el mayor de sus dos costos, y las piezas corren una detrás de otra:

Lo que muestran los ejemplos precargados, con el 70B en FP8 sobre 4 H100:

  • Prefill de 2000 tokens: 88 ms. Todo lo limita el cómputo, salvo el LM head. El MLP se lleva 71 ms, el 81 %; la atención, menos de 2 ms.
  • Decode de un usuario: 5.3 ms. Todo lo limita la memoria; el MLP se lleva 4.2 ms porque es donde están los pesos.
  • Decode de 64 usuarios con 4000 tokens: 11.6 ms. Los pesos se leen una vez para los 64, pero leer los 64 caches (84 GB, 6.3 ms) ya cuesta más que leer el MLP (4.3 ms). Pasa a mandar la atención.
  • El paso mixto, un trozo de 512 tokens de prefill con 64 usuarios: 31 ms. Las proyecciones y el MLP pasan a estar limitados por cómputo por las 576 filas, mientras la atención de los 64 usuarios sigue limitada por la memoria. Es el paso que usa el chunked prefill (12.1.8).

Dos experimentos para hacer con la calculadora. Sube los usuarios en decode a 175: el MLP y las proyecciones pasan a estar limitados por cómputo con el 40 % de eficiencia, y el paso tarda 24.8 ms en lugar de los 22.4 ms del límite de memoria de la figura 12.3. Después baja el contexto a 500 y sube los usuarios a 256: con cachés chicos, el batch sí llena el cómputo, y salen unos 17 800 tokens por segundo. Con contextos largos, en cambio, el KV manda antes de que el cómputo se llene; guardarlo en FP8 (M14.3) baja el paso de 64 usuarios de 11.6 a 8.4 ms.

Trade-off

En el decode, cada usuario más en el batch es casi gratis para las proyecciones y el MLP mientras la pasada no llegue al quiebre de cómputo, y nunca es gratis para la atención, que lee un cache por usuario. Por eso el tamaño de batch que conviene depende del largo de los contextos: con conversaciones cortas, cientos de usuarios por réplica; con contextos de 100 000 tokens, unos pocos, y el TPOT lo decide el KV.

12.1.8Cuando las dos fases comparten la GPU

Un motor con continuous batching (M15.2) arma un batch nuevo en cada paso: las requests que terminan salen y las que llegan entran. Cuando entra una request nueva, su prefill comparte el paso con el decode de los demás. ¿Qué ven los usuarios que ya estaban generando?

Con las cuentas de la calculadora:

  • Solo decode: un paso cada 11.6 ms, un token para cada uno de los 64 usuarios por paso.
  • El prefill entero en un paso: 2000 tokens de prefill y 64 de decode, 96 ms. Los 64 usuarios esperan 96 ms por su siguiente token: un salto de TPOT de 8 veces, que con prompts más largos llega a segundos. La request nueva, en cambio, tiene su primer token a los 96 ms.
  • Chunked prefill de 512 tokens: cuatro pasos de 31 ms, cada uno con un trozo y los 64 decodes. Los usuarios ven saltos de 31 ms en lugar de uno de 96; la request nueva termina su prefill a los 126 ms en lugar de a los 96.

El tamaño del trozo reparte el dolor entre el TTFT del que llega y el TPOT de los que están: ese es el trade-off de M15.5. Cuando los dos SLOs son exigentes y los prompts son largos, la alternativa es no mezclarlos: un grupo de GPUs solo para prefill y otro solo para decode, con el KV cache viajando por la red entre ellos (M15.6). Ahora se ve por qué esa separación tiene sentido: cada grupo trabaja siempre en el régimen para el que está dimensionado, cómputo en uno y memoria en el otro.

12.1.9Del logit al token

La pasada termina con 128 256 logits por usuario: medio megabyte en FP32. El muestreo convierte eso en un token, en la GPU, en cuatro pasos:

  1. TemperaturaDivide cada logit por T. Con T < 1 las diferencias crecen y la distribución se afila; con T > 1 se aplana.
  2. SoftmaxConvierte los logits en probabilidades que suman 1, como en la atención.
  3. RecortarTop-k se queda con los k tokens más probables. Top-p (nucleus sampling) se queda con el grupo más chico de tokens, de más probable a menos, cuya probabilidad suma al menos p. Documentado Después se vuelve a normalizar.
  4. SortearSe elige un token al azar con esas probabilidades. Con temperatura 0 no se sortea: se toma el de mayor logit (greedy).

La cuenta del ejemplo: con logits 5, 4, 3 y 1, e⁵ = 148.4, e⁴ = 54.6, e³ = 20.1 y e¹ = 2.7, que suman 225.8. Las probabilidades son 0.657, 0.242, 0.089 y 0.012. Con temperatura 0.5 los logits pasan a ser 10, 8, 6 y 2, y el favorito sube a 0.867. En código:

import numpy as np

rng = np.random.default_rng()

def muestrear(logits, temperatura=1.0, top_p=1.0):
    if temperatura == 0:
        return int(np.argmax(logits))                  # greedy: siempre el mayor
    z = logits / temperatura
    p = np.exp(z - z.max())
    p /= p.sum()                                       # softmax
    orden = np.argsort(p)[::-1]                        # de más probable a menos
    acumulada = np.cumsum(p[orden])
    corte = np.searchsorted(acumulada, top_p) + 1      # el grupo más chico que llega a top_p
    elegidos = orden[:corte]
    return int(rng.choice(elegidos, p=p[elegidos] / p[elegidos].sum()))

muestrear(np.array([5.0, 4.0, 3.0, 1.0]), temperatura=1.0, top_p=0.9)   # 0, 1 o 2; nunca 3

Después de elegir, el motor revisa si tiene que parar: si salió el token de fin de la plantilla, si el texto terminó en una de las stop sequences de la request o si se llegó a max_tokens. Si la request pidió una salida con forma fija, como un JSON que cumpla un schema, el motor pone −∞ en los logits de los tokens que romperían la forma antes del softmax: es la decodificación restringida (M17). Y aun con temperatura 0, el resultado puede cambiar entre dos llamadas por el orden de las sumas en el batch, como ya viste en M12.1.

12.1.10El bucle a mano

Con la biblioteca transformers de Hugging Face se puede escribir el bucle de generación sin generate(), con el prefill y cada paso de decode a la vista. El programa usa Qwen2.5-0.5B-Instruct, un modelo de 500 millones de parámetros que corre en cualquier GPU con CUDA; necesita PyTorch y transformers 4.56 o posterior. Lo escribes y lo corres tú; los tiempos dependen de tu GPU.

import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

nombre = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(nombre)
modelo = AutoModelForCausalLM.from_pretrained(nombre, dtype=torch.bfloat16).to("cuda").eval()

mensajes = [{"role": "user", "content": "Explica qué es el KV cache en tres frases."}]
ids = tok.apply_chat_template(mensajes, add_generation_prompt=True,
                              return_tensors="pt", return_dict=True)["input_ids"].to("cuda")

def ahora():
    torch.cuda.synchronize()            # la GPU trabaja en paralelo: espera a que termine
    return time.perf_counter()

with torch.inference_mode():
    t0 = ahora()
    salida = modelo(input_ids=ids, use_cache=True)                 # prefill: el prompt entero
    cache = salida.past_key_values                                 # el KV cache de todas las capas
    siguiente = salida.logits[:, -1, :].argmax(dim=-1, keepdim=True)
    t1 = ahora()

    generados = [siguiente.item()]
    while len(generados) < 200 and generados[-1] != tok.eos_token_id:
        salida = modelo(input_ids=siguiente, past_key_values=cache, use_cache=True)   # decode
        cache = salida.past_key_values
        siguiente = salida.logits[:, -1, :].argmax(dim=-1, keepdim=True)
        generados.append(siguiente.item())
    t2 = ahora()

print(f"prompt: {ids.shape[1]} tokens, prefill: {(t1 - t0) * 1000:.1f} ms")
print(f"decode: {(t2 - t1) * 1000 / (len(generados) - 1):.1f} ms por token")
print(tok.decode(generados, skip_special_tokens=True))

Qué mirar al correrlo:

  • Córrelo dos veces. La primera vez incluye la carga de los kernels y la reserva de memoria, y sus tiempos no sirven. Anota los de la segunda.
  • Agranda el prompt diez veces, por ejemplo pegando un texto largo en el mensaje. El prefill tiene que crecer bastante; el tiempo por token de decode, poco. Si los dos crecen igual, revisa que el decode esté pasando past_key_values.
  • Quita el cache en el decode: pasa la secuencia entera en cada paso (el prompt más los tokens generados, unidos con torch.cat) y no pases past_key_values. El tiempo por token tiene que crecer con cada token generado, como en el simulador de 12.1.4 sin cache.
  • Compara con generate(): modelo.generate(ids, max_new_tokens=200, do_sample=False) tiene que producir el mismo texto, porque hace el mismo bucle con greedy.
