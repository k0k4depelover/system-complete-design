Diseño de la API del LLM

La API de un LLM parece un POST más, pero la respuesta tarda decenas de segundos, llega de a pedazos, puede cortarse a la mitad y se cobra por token. Este módulo diseña la API completa: los endpoints y sus esquemas, el streaming con SSE de punta a punta, qué pasa cuando el cliente se va o la red se corta, las herramientas, las salidas estructuradas y los errores que un cliente tiene que saber distinguir.

  • Preparar la infraestructura para el streaming: buffering, timeouts de inactividad y cuántas conexiones abiertas vas a sostener.

  • Distinguir los errores que se reintentan de los que no, antes y después del 200.

17.1Qué tiene de distinta una API de LLM

Desde afuera, una API de LLM es una API HTTP como las del M02: JSON de ida, JSON de vuelta y una clave en un header. Pero casi todas sus cifras están en otra escala, y cada una obliga a una decisión de diseño:

API REST típicaAPI de un LLM
DuraciónDe 10 a 200 msDe 1 a 60 s; minutos con modelos que razonan antes de responder
Tamaño de la requestUnos kilobytesHasta cientos de miles de tokens: varios megabytes. La API de Anthropic acepta hasta 32 MB por request Documentado
RespuestaDe una vezDe a pedazos, token por token
Costo de una requestCasi cero y parejoDe fracciones de centavo a dólares, según los tokens
Qué se limitaRequests por segundoTokens por minuto, además de requests (M18)
Misma entrada, misma salidaSíNo: con muestreo, cada respuesta sale distinta (M12)
Un error a la mitadNo existe: o responde o fallaFrecuente: cuando algo falla, el 200 ya se había enviado

Una decisión de fondo atraviesa todo el módulo: el modelo no guarda estado entre requests (M12). En la API clásica de chat, cada request manda la conversación entera y el servidor la puede olvidar apenas responde. Eso simplifica mucho la operación, porque cualquier réplica atiende cualquier request, pero traslada el costo al cliente, que reenvía y paga todo el historial en cada turno (M16). Las APIs más nuevas ofrecen guardar el estado en el servidor; en 17.2 ves qué se gana y qué se paga.

17.2Los endpoints

La API de OpenAI se convirtió en el estándar de hecho: vLLM, SGLang y casi todos los proveedores exponen rutas compatibles, así que un cliente escrito para ella funciona contra un motor propio cambiando la URL base (M15). La familia completa: Documentado

Códigos de respuesta

  • 200La respuesta completa o, con stream: true, el comienzo de un stream de eventos (17.3).
  • 400Request inválida: un esquema mal formado, o el prompt más max_completion_tokens no entra en la ventana de contexto (M16).
  • 401Clave inválida, revocada o vencida.
  • 404El modelo no existe o la clave no tiene acceso a él.
  • 429Límite de tasa, con Retry-After; o tope de gasto alcanzado, que no se arregla reintentando (M18).
  • 500Falla interna: se reintenta con backoff.
  • 503El modelo está sobrecargado (server_is_overloaded; en Anthropic es un 529): se reintenta respetando Retry-After, o se cambia de modelo.

finish_reason dice por qué terminó la generación, y conviene revisarlo siempre: stop si el modelo terminó solo, length si llegó al máximo de tokens y la respuesta está cortada, tool_calls si pidió una herramienta y content_filter si la cortó un filtro. Documentado El bloque usage es lo que se cobra: cached_tokens son los que salieron del prompt caching (M16) y reasoning_tokens, los que el modelo usó para razonar sin mostrarlos.

En producción real

Cambiar de modelo cambia el comportamiento, la latencia y el costo, así que se hace como un deploy: con evaluaciones, canary y la posibilidad de volver atrás (M22). Por eso se fija una versión con fecha y no un alias que apunta siempre al último modelo. Los proveedores anuncian con meses de anticipación cuándo retiran un modelo; esa fecha tiene que estar en el calendario del equipo, no aparecer como un 404 un lunes a la mañana.

Trade-off

Guardar la conversación en el servidor le ahorra al cliente reenviar el historial y le permite al proveedor reutilizar su KV cache con más facilidad. A cambio, el proveedor guarda tus conversaciones (retención, privacidad, M10) y la conversación queda atada a ese proveedor: para cambiar de modelo o de empresa hay que tener tu propia copia. Los productos serios guardan siempre su propia copia de cada mensaje (M20), usen o no el estado del proveedor.

Embeddings

Un embedding es un vector de números que representa el significado de un texto: dos textos parecidos quedan cerca. Es la base de la búsqueda semántica y del RAG (M16, M20).

POST /v1/embeddings
Authorization: Bearer sk-…
Content-Type: application/json

{
  "model": "modelo-embeddings",
  "input": ["El KV cache guarda claves y valores…", "PagedAttention divide el cache en bloques…"],
  "dimensions": 512
}
{
  "object": "list",
  "data": [
    {"object": "embedding", "index": 0, "embedding": [0.0123, -0.0456, …]},
    {"object": "embedding", "index": 1, "embedding": [-0.0071, 0.0332, …]}
  ],
  "model": "modelo-embeddings",
  "usage": {"prompt_tokens": 21, "total_tokens": 21}
}

En la API de OpenAI, cada texto puede tener hasta 8192 tokens, una request lleva hasta 2048 textos y no más de 300 000 tokens en total, y dimensions recorta el vector para ahorrar espacio en la base vectorial. Documentado Para el sistema, un embedding es solo un prefill: no hay decode ni KV cache que conservar, así que se sirve con batches grandes y sin streaming, optimizando el throughput y no la latencia. Es el endpoint más barato por token, y el que más volumen recibe cuando se indexan documentos.

Archivos y batches

La Batch API recibe un archivo JSONL con miles de requests, cada una con un custom_id propio, y las procesa en diferido:

{"custom_id": "ticket-8812", "method": "POST", "url": "/v1/chat/completions", "body": {"model": "modelo-chat", "messages": [{"role": "user", "content": "Clasifica este ticket: …"}], "max_completion_tokens": 50}}
{"custom_id": "ticket-8813", "method": "POST", "url": "/v1/chat/completions", "body": {"model": "modelo-chat", "messages": [{"role": "user", "content": "Clasifica este ticket: …"}], "max_completion_tokens": 50}}

El archivo se sube con POST /v1/files y purpose: "batch", y el batch se crea apuntando a él:

POST /v1/batches
Authorization: Bearer sk-…
Content-Type: application/json

{"input_file_id": "file-9Qa1", "endpoint": "/v1/chat/completions", "completion_window": "24h"}

El batch pasa por validating, in_progress y finalizing hasta completed, o termina en failed, expired o cancelled. Al final hay un archivo de resultados y otro de errores. En OpenAI cuesta la mitad que las mismas requests síncronas, admite hasta 50 000 requests por batch y no consume los límites por minuto habituales: tiene los suyos. Documentado Al proveedor le conviene: un trabajo que puede esperar horas llena las GPUs de madrugada, cuando el tráfico interactivo baja (M12).

En producción real

Los resultados no vuelven en orden: se unen con la entrada por custom_id, que conviene que sea el id de tu propio registro. Un batch puede terminar con una parte de las requests fallidas en el archivo de errores, y si vence el plazo, las requests terminadas se cobran y las demás se cancelan. Documentado El proceso que lo consume tiene que ser idempotente por custom_id, porque lo vas a correr más de una vez.

17.3Streaming con SSE

Una respuesta de 800 tokens a 50 tokens por segundo tarda 16 segundos en generarse. Sin streaming, el usuario mira una pantalla vacía todo ese tiempo; con streaming, empieza a leer en menos de medio segundo:

Una persona lee en silencio unas 240 palabras por minuto, unas 4 por segundo, según un metaanálisis de Brysbaert de 2019 sobre 190 estudios. Documentado Un modelo a 50 tokens por segundo escribe unas 35 palabras por segundo, mucho más rápido de lo que se lee. Por eso lo que el usuario percibe es el TTFT, no el tiempo total, y por eso también puede detener una respuesta que ve ir por mal camino en el segundo 2 en lugar de pagarla entera.

El formato

SSE (Server-Sent Events) es una respuesta HTTP que no termina: el servidor la mantiene abierta con Content-Type: text/event-stream y va escribiendo eventos de texto. Las reglas son pocas: Documentado

retry: 5000

: un comentario: el cliente lo ignora, pero mantiene viva la conexión

id: 41
event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Hola"}}

id: 42
event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":" mundo"}}
  • Cada línea es un campo: event (el tipo), data (el contenido; varias líneas data se unen con saltos de línea), id y retry.
  • Un evento termina con una línea vacía. Hasta que llega esa línea, el cliente no lo procesa.
  • id guarda el último evento recibido; al reconectar, el navegador lo manda en el header Last-Event-ID para que el servidor siga desde ahí (17.5). retry fija cuántos milisegundos esperar antes de reconectar.
  • Una línea que empieza con dos puntos es un comentario. El estándar recomienda mandar uno cada unos 15 segundos para que ningún proxy cierre la conexión por inactividad.

El navegador trae un cliente de SSE, EventSource, pero no sirve para una API de LLM: solo hace GET y no permite headers propios como Authorization. Documentado Las APIs de LLM reciben un POST con el prompt en el cuerpo, así que los clientes leen el stream con fetch e interpretan el formato ellos mismos, que es lo que hacen los SDK. ¿Por qué no WebSockets? Porque SSE es HTTP común: pasa por proxies, CDNs y balanceadores sin configuración especial, se multiplexa en HTTP/2 y usa la misma autenticación que el resto de la API. Para texto alcanza con un solo sentido. La voz en tiempo real, que sí necesita los dos sentidos, usa WebSockets o WebRTC (M24).

Un cliente que no se rompe

Un cliente de streaming que funciona en la demo y falla en producción suele fallar por alguna de estas razones:

  • Asumir que cada lectura trae eventos completos. Una lectura de la red puede cortar un evento por la mitad, o incluso un carácter de varios bytes como la "ñ". Hay que acumular, decodificar en modo stream y procesar solo hasta la última línea vacía.
  • Romperse con lo desconocido. Los proveedores agregan tipos de evento nuevos, y Anthropic avisa que el código tiene que ignorar los que no conoce. Documentado Lo mismo con los comentarios y los ping.
  • Parsear los argumentos de una herramienta a medida que llegan. Los pedazos no son JSON válido por separado: se concatenan y se parsean cuando termina el bloque.
  • Confiar en que el stream terminó bien porque se cerró. Una respuesta está completa solo si llegó su evento final: [DONE], response.completed o message_stop. Sin él, la respuesta está cortada aunque parezca terminada.
  • Poner un timeout total. Una respuesta larga puede durar minutos y estar sana. Lo que conviene es un timeout entre eventos: si pasan 60 segundos sin nada, ni siquiera un ping, la conexión está muerta.

El núcleo de un cliente en el navegador, con el botón de detener incluido:

const ctrl = new AbortController();
botonDetener.onclick = () => ctrl.abort();          // cierra la conexión (17.4)

const res = await fetch('/api/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ messages, stream: true }),
  signal: ctrl.signal,
});
const reader = res.body.getReader();
const decoder = new TextDecoder();                 // { stream: true } no corta caracteres de varios bytes
let buffer = '';
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  let corte;
  while ((corte = buffer.indexOf('\n\n')) >= 0) {   // un evento termina en una línea vacía
    const crudo = buffer.slice(0, corte);
    buffer = buffer.slice(corte + 2);
    procesar(parsearEvento(crudo));                // ignora comentarios y tipos desconocidos
  }
}
// si no llegó el evento final, la respuesta quedó incompleta

Está simplificado: el estándar también acepta \r\n como fin de línea, y parsearEvento tiene que unir las líneas data de un mismo evento.

La infraestructura entre medio

Entre el motor y el navegador hay proxies, balanceadores y a veces una CDN, y cada uno puede romper el streaming sin dar ningún error:

  • Buffering. Nginx, por defecto, acumula la respuesta del servidor de origen antes de reenviarla. En un stream eso significa que todos los eventos llegan juntos al final. Se desactiva con proxy_buffering off o, respuesta por respuesta, con el header X-Accel-Buffering: no. Documentado Con la compresión pasa lo mismo: gzip acumula para comprimir mejor, así que el stream no se comprime, o se fuerza el envío de cada evento.
  • Timeouts de inactividad. Un balanceador de aplicación de AWS cierra una conexión después de 60 segundos sin datos, salvo que lo configures (hasta 4000). Cloudflare responde con un error 524 si el origen pasa 125 segundos sin enviar nada, y solo en el plan Enterprise se puede cambiar. Documentado Un prefill de 128 000 tokens tarda más de 10 segundos (M16), y un modelo que razona puede pasar minutos sin emitir un token visible. Por eso se mandan comentarios o eventos ping cada unos 15 segundos, y Anthropic los incluye en sus streams.
  • Límite de conexiones del navegador. Sobre HTTP/1.1, el navegador abre como mucho 6 conexiones por dominio, y cada stream abierto ocupa una: con varias pestañas, la séptima espera. Documentado HTTP/2 lleva muchos streams por una sola conexión.
  • Deploys. Reiniciar un gateway corta todos sus streams. Se drena (M03): la instancia deja de recibir requests nuevas y espera a que terminen las que tiene, con un máximo. Con respuestas de minutos, ese máximo es largo, y conviene que el cliente sepa reanudar (17.5).

El streaming también cambia la cuenta de capacidad. Lo que ocupa memoria y descriptores en el gateway ya no son las requests por segundo, sino los streams abiertos, que por la ley de Little son las requests por segundo multiplicadas por la duración de cada stream:

Con los valores de ejemplo, 2000 requests por segundo de 12.8 segundos cada una son 25 600 streams abiertos a la vez. Cada token viaja envuelto en unos 260 bytes de JSON, así que el texto útil es menos del 2 % de lo que se transmite: 1.2 millones de eventos por segundo y 2.5 Gbps de salida para unos 5 MB/s de texto.

Qué pasa si falla

El incidente clásico: se agrega una capa nueva (un proxy corporativo, un WAF, otra CDN) con el buffering activado, y los usuarios ven la respuesta entera de golpe después de 20 segundos. Los dashboards del servidor muestran un TTFT perfecto, porque lo miden donde se genera el primer token, no donde se lo ve. El TTFT se mide también en el cliente (M11), y cada capa nueva se prueba con un stream real antes de salir a producción.

17.4Cuando el cliente se va

El usuario pulsa "Detener", cierra la pestaña o se queda sin señal. Si nadie avisa, la GPU sigue generando tokens que nadie va a leer: se pierde dinero y, sobre todo, un lugar en el batch que otra request estaba esperando (M15). La cancelación tiene que viajar hasta el motor:

  1. El navegador cierra la conexiónAbortController.abort() cierra la conexión TCP o, en HTTP/2, solo ese stream con un RST_STREAM.
  2. El proxy cierra hacia atrásUn proxy bien configurado cierra la conexión con el servidor de origen cuando se cierra la del cliente. Uno que acumula la respuesta puede seguir leyendo del origen como si nada.
  3. El servidor de la API se enteraO porque falla la siguiente escritura, o porque su servidor web le avisa de la desconexión: Starlette, por ejemplo, cancela el generador que produce el stream. Ahí tiene que cancelar su propia llamada al motor, no solo dejar de escribir.
  4. El motor libera la GPUvLLM aborta la request cuando se cierra la conexión con su servidor HTTP: la saca del batch y libera sus bloques del KV cache. En noviembre de 2024 se reportó que, con un middleware agregado, esa detección fallaba y las GPUs seguían generando para nadie. Documentado

En los modos en segundo plano la conexión no es la señal, porque justamente se quiere que la generación siga sin ella. Por eso hay un endpoint explícito, POST /v1/responses/{id}/cancel, idempotente: cancelar dos veces devuelve el mismo objeto final. Documentado Lo que ya se generó hasta que el motor se enteró gastó GPU; cómo se cobra depende del proveedor, y tu sistema tiene que registrar ese uso parcial igual (M21).

Trade-off

Si tu producto permite reanudar (17.5), una conexión cerrada ya no puede significar "cancelar": el usuario que entró a un túnel quiere encontrar la respuesta terminada al salir. Entonces se separan las dos cosas: el botón "Detener" llama a un endpoint de cancelación, y una desconexión solo deja de mandar eventos mientras la generación sigue. El costo es generar respuestas que a veces nadie va a leer.

17.5Streams que sobreviven a un corte

En un teléfono, la conexión se corta todo el tiempo: al cambiar de wifi a datos, al entrar al ascensor o al pasar la app a segundo plano. Hay tres formas de seguir:

EstrategiaCómo funcionaQué cuesta
Reintentar desde ceroEl cliente repite la requestSe genera y se paga todo de nuevo, y la respuesta sale distinta. Es lo único posible en una API sin estado
Continuar desde el clienteEl cliente manda lo que alcanzó a recibir y pide seguir desde ahíSe paga otra vez toda la entrada y el empalme puede no ser perfecto. Es la estrategia que documenta Anthropic; no sirve para bloques de herramientas ni de razonamiento a medio llegar Documentado
Reanudar en el servidorLa generación sigue sin el cliente, los eventos quedan guardados con su número y el cliente vuelve con el último que recibióGuardar los eventos unos minutos. Es el modo en segundo plano de Responses, con starting_after Documentado

La tercera es la que usan los productos de chat, y es la que conviene construir si el producto es tuyo: un stream reanudable separa la generación de la conexión.

El diseño, en detalle: Diseño de referencia

  • Un worker de generación pide los tokens al motor y escribe cada evento en un buffer por respuesta, con un número de secuencia creciente. Un stream de Redis con la clave resp:{id} encaja bien: agrega al final, se lee desde un id y se le pone una expiración.
  • El servidor de la API no genera: lee del buffer desde el número que pide el cliente y lo manda como SSE, con ese número en el campo id. Cuando no hay eventos nuevos, espera bloqueado en el buffer y manda comentarios cada 15 segundos.
  • El cliente guarda el último id y reconecta con Last-Event-ID (o un parámetro como starting_after). Si recibe un evento repetido, lo descarta por su número: el consumo es idempotente.
  • El buffer vive unos minutos después del final. Alcanza para reconectar, para recargar la página y para abrir la conversación en otro dispositivo mientras la respuesta todavía se escribe. El mensaje completo se guarda en la base de datos al terminar (M20).

Guardar eventos tiene una consecuencia de privacidad que conviene decir en voz alta: aun para clientes con retención cero, el modo en segundo plano de OpenAI guarda los datos de la respuesta unos 10 minutos para poder consultarla. Documentado Si tu producto promete no guardar nada, la reanudación tiene que entrar en esa promesa.

17.6Tool calling

Con tool calling el modelo puede pedir datos o acciones que no tiene: consultar un pedido, buscar en la web, ejecutar código. El modelo no ejecuta nada. Declaras funciones con un JSON Schema, el modelo responde con una llamada y sus argumentos, y tu aplicación la ejecuta y le devuelve el resultado:

La declaración, en el formato de Chat Completions:

{
  "type": "function",
  "function": {
    "name": "buscar_pedido",
    "description": "Devuelve el estado de un pedido del usuario actual",
    "parameters": {
      "type": "object",
      "properties": {"pedido_id": {"type": "string", "description": "Número del pedido"}},
      "required": ["pedido_id"],
      "additionalProperties": false
    },
    "strict": true
  }
}

La respuesta del modelo trae finish_reason: "tool_calls" y la llamada, con los argumentos como un string JSON. Tu aplicación ejecuta la función y manda una request nueva con toda la conversación, la llamada y un mensaje con rol tool que lleva el mismo id: Documentado

{"role": "assistant", "tool_calls": [{"id": "call_Qm2", "type": "function",
  "function": {"name": "buscar_pedido", "arguments": "{\"pedido_id\": \"8812\"}"}}]}
{"role": "tool", "tool_call_id": "call_Qm2", "content": "{\"estado\": \"en camino\", \"llega\": \"2026-10-02\"}"}

Responses y Messages hacen lo mismo con otros nombres: un ítem function_call que se responde con function_call_output, o un bloque tool_use que se responde con tool_result. Lo que importa es lo que queda de tu lado:

  • Los argumentos no son una autorización. El modelo puede equivocarse o ser manipulado por un texto que leyó (prompt injection, M22 y M25). Si pide el pedido 8812, tu servicio verifica que ese pedido sea del usuario de la sesión, igual que con cualquier request de un cliente (BOLA, M10).
  • Las acciones con efectos necesitan idempotencia. Si una herramienta cobra, envía un correo o crea un ticket, deriva una idempotency key del id de la llamada: un reintento no puede cobrar dos veces (M02, M27).
  • Los errores vuelven al modelo. Si la herramienta falla o tarda demasiado, se le devuelve el error como resultado ("el servicio de pedidos no responde") para que responda con lo que tiene o proponga otra cosa.
  • Las llamadas pueden venir juntas. Con parallel_tool_calls, el modelo pide varias en un mismo turno: se ejecutan en paralelo y cada una se responde con su id.
  • El bucle necesita un límite. Un modelo puede pedir herramientas en cadena. Se fija un máximo de pasos, de tokens, de tiempo y de dinero por tarea (M25).
  • Las definiciones cuestan tokens. Viajan en cada request como parte de la entrada. Conviene que sean cortas y que estén siempre en el mismo orden para no romper el prompt caching (M16).

Responses ofrece además herramientas que ejecuta el propio proveedor, como la búsqueda en archivos o un intérprete de código: el bucle ocurre dentro de una sola request, y el stream trae eventos del progreso de cada herramienta. Documentado Es cómodo, pero el control de qué se ejecuta y de cuánto tarda pasa al proveedor.

17.7Salidas estructuradas

Cuando la respuesta la lee un programa y no una persona, se necesita JSON que cumpla un esquema. El modo JSON solo garantiza JSON válido; las salidas estructuradas garantizan además que cumpla tu esquema. Documentado

"response_format": {
  "type": "json_schema",
  "json_schema": {
    "name": "clasificacion",
    "strict": true,
    "schema": {
      "type": "object",
      "properties": {
        "motivo": {"type": "string"},
        "prioridad": {"type": "string", "enum": ["alta", "media", "baja"]}
      },
      "required": ["motivo", "prioridad"],
      "additionalProperties": false
    }
  }
}

No es una instrucción que el modelo puede ignorar. El motor aplica decodificación restringida: compila el esquema en una gramática y, en cada paso, enmascara los tokens que dejarían el JSON fuera del esquema antes de muestrear. OpenAI lo describió así al lanzar la función en 2024, y los motores abiertos lo ofrecen con bibliotecas como XGrammar. Documentado

Lo que hay que saber para usarlas bien:

  • El primer uso de un esquema es más lento. La gramática se compila y se guarda en caché: la primera request con un esquema nuevo tiene latencia extra, las siguientes no. Documentado Un esquema que cambia en cada request, por ejemplo con un enum armado a partir de datos del usuario, paga esa compilación cada vez.
  • No se acepta todo JSON Schema. Hay un subconjunto soportado; en modo estricto, todos los campos son obligatorios y no se permiten campos adicionales.
  • El modelo puede negarse. En ese caso la respuesta trae un campo refusal en lugar del JSON. Documentado
  • Un corte deja JSON inválido. Si finish_reason es length, el objeto quedó a medias: se revisa antes de parsear.
  • El orden de los campos importa. El modelo genera de izquierda a derecha: si la prioridad va antes que el motivo, decide sin haber escrito el razonamiento. Se ponen primero los campos que ayudan a decidir.
  • El esquema no reemplaza la validación. Garantiza la forma, no el contenido: que prioridad sea "alta" no quiere decir que sea correcta. Las reglas de negocio se siguen validando en tu código.

17.8Errores y reintentos

Un cliente de una API de LLM tiene que distinguir los errores por lo que hay que hacer con ellos:

CódigoQué significa¿Reintentar?
400Request inválida, o el contexto no entra en la ventanaNo: hay que corregirla, por ejemplo recortando el contexto (M16)
401, 403Clave inválida o sin permisoNo
404Modelo inexistente o sin accesoNo
413Request demasiado grande en bytesNo: los archivos grandes van por /v1/files
429 con Retry-AfterTu límite por minutoSí, después de esperar lo que indica; y frenar el ritmo (M18)
429 sin Retry-AfterTu tope de gastoNo: falla hasta que cambie el mes o el tope
500Falla internaSí, con backoff y jitter
503, 529Sobrecarga del proveedorSí, respetando Retry-After; o usar otro modelo o región

Los dos proveedores distinguen el tope de gasto del límite por minuto: Anthropic lo marca con error_code: enforced_spend_limit_reached y sin retry-after; OpenAI, con el código organization_spend_limit_exceeded o project_spend_limit_exceeded. Documentado Un cliente que reintenta todos los 429 igual se queda horas golpeando una puerta cerrada.

  • El 200 no es el éxito. El éxito es el evento final. Un error a mitad del stream llega como un evento, y la respuesta parcial ya está en pantalla: se muestra lo recibido con el error y se ofrece reintentar.
  • Los SDK ya reintentan. El de Anthropic reintenta dos veces por defecto, con backoff exponencial y respetando retry-after. Documentado Si tu código reintenta encima, las tormentas de reintentos se multiplican (M08).
  • Reintentar genera otra respuesta. Una generación no es idempotente en su contenido: el reintento cuesta de nuevo y dice otra cosa. Para un chat da igual; para una herramienta con efectos, no (17.6).
  • Cada respuesta trae un id. x-request-id en OpenAI, request-id en Anthropic. Se loguea siempre, para cruzar tus traces con el soporte del proveedor (M11).
  • Lo que tarda más de 10 minutos va por streaming o por batch. Anthropic lo recomienda porque algunas redes cortan las conexiones inactivas, y sus SDK rechazan requests sin streaming que podrían superar ese tiempo. Documentado
  • La API cambia. Aparecen campos y tipos de evento nuevos: el cliente los ignora en lugar de fallar. La versión se fija explícitamente, como el header anthropic-version, y el modelo con una versión con fecha.

17.9Seguridad del streaming

El streaming complica tres cosas que sin él son simples:

  • Moderar la salida. Con la respuesta completa, se la revisa antes de mostrarla. Con streaming, el usuario ya leyó el principio cuando llega el final. OpenAI lo advierte: los puntajes de moderación llegan cuando la salida está completa, no con cada delta. Documentado Las opciones son moderar la entrada antes de generar, moderar la salida por ventanas de algunas decenas de tokens y cortar el stream si algo se marca, o no usar streaming en los casos de más riesgo.
  • El tamaño de los paquetes. Aunque el tráfico vaya cifrado, un token por evento deja ver el largo de cada token. Un trabajo presentado en USENIX Security en 2024 reconstruyó con exactitud el 29 % de las respuestas de ChatGPT y de Copilot, y dedujo el tema del 55 %, solo a partir de esa secuencia de largos. Documentado La mitigación es rellenar los eventos (el campo obfuscation de OpenAI) o agrupar varios tokens por evento.
  • Las claves. La clave del proveedor nunca llega al navegador: el cliente habla con tu backend, que autentica al usuario, aplica tus cuotas y llama al proveedor (el patrón BFF del M03).

17.10Impleméntalo: el endpoint de streaming

Un endpoint compatible con Chat Completions que se pone delante de un motor como vLLM, con todo lo de este módulo: cuota reservada al entrar, comentarios cuando hay silencio, cancelación hasta el motor y uso registrado pase lo que pase. Usa FastAPI y el SDK de OpenAI apuntando al motor. Diseño de referencia

import asyncio, time
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from openai import AsyncOpenAI

app = FastAPI()
motor = AsyncOpenAI(base_url="http://vllm.interno:8000/v1", api_key="interno")
SILENCIO = 15   # segundos sin eventos antes de mandar un comentario

@app.post("/v1/chat/completions")
async def chat(request: Request):
    body = await request.json()
    org = request.state.org                        # lo dejó el middleware de autenticación
    reserva = await cuotas.reservar(org, body)     # M18: responde 429 si no alcanza

    async def eventos():
        uso, salida, completo, t0 = None, 0, False, time.monotonic()
        stream = await motor.chat.completions.create(
            model=body["model"], messages=body["messages"],
            max_completion_tokens=body.get("max_completion_tokens", 1024),
            stream=True, stream_options={"include_usage": True})
        siguiente = None
        try:
            it = aiter(stream)
            while True:
                if siguiente is None:
                    siguiente = asyncio.ensure_future(anext(it))
                listo, _ = await asyncio.wait({siguiente}, timeout=SILENCIO)
                if not listo:
                    yield ": keep-alive\n\n"       # nadie corta una conexión que habla
                    continue
                try:
                    chunk = siguiente.result()
                except StopAsyncIteration:
                    completo = True
                    break
                siguiente = None
                if chunk.usage:
                    uso = chunk.usage
                elif chunk.choices and chunk.choices[0].delta.content:
                    salida += 1                    # aproximado: un token por chunk
                yield f"data: {chunk.model_dump_json()}\n\n"
            yield "data: [DONE]\n\n"
        finally:
            # Si el cliente se va, Starlette cancela este generador y se llega acá igual.
            if siguiente is not None:
                siguiente.cancel()
            await stream.close()                   # cierra la conexión con el motor: vLLM aborta
            await cuotas.reconciliar(reserva, uso, salida)
            await metering.registrar(org, body["model"], uso, salida,
                                     completo=completo, segundos=time.monotonic() - t0)

    return StreamingResponse(eventos(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})

Tres detalles que suelen faltar. El bloque finally corre aunque el cliente se vaya, y es el único lugar donde la cuota se reconcilia y el uso se registra en todos los casos; en producción conviene protegerlo de una segunda cancelación o hacerlo en una tarea aparte. stream.close() es lo que le avisa al motor que deje de generar. Y los comentarios de keep-alive salen de una espera con timeout sobre el próximo chunk, no de un temporizador aparte que podría escribir en medio de un evento.

Para que el stream sobreviva a un corte, la generación se muda a un worker que escribe en un stream de Redis, y el endpoint que habla con el cliente solo lee (17.5):

import redis.asyncio as redis
r = redis.Redis()
TTL = 600   # segundos para reconectar después del final

async def generar(rid: str, body: dict):
    """Worker: genera una sola vez y guarda cada evento con su número de secuencia."""
    clave, seq = f"resp:{rid}", 0
    async for chunk in await motor.chat.completions.create(**body, stream=True):
        seq += 1
        await r.xadd(clave, {"data": chunk.model_dump_json()}, id=f"0-{seq}")
        if seq == 1:
            await r.expire(clave, TTL)             # si el worker muere, la clave vence igual
    await r.xadd(clave, {"data": "[DONE]"}, id=f"0-{seq + 1}")
    await r.expire(clave, TTL)

@app.get("/v1/respuestas/{rid}/eventos")
async def eventos(rid: str, request: Request):
    ultimo = int(request.headers.get("Last-Event-ID", 0))

    async def leer():
        nonlocal ultimo
        while True:
            res = await r.xread({f"resp:{rid}": f"0-{ultimo}"}, block=15000, count=100)
            if not res:
                yield ": keep-alive\n\n"
                continue
            for id_, campos in res[0][1]:
                ultimo = int(id_.decode().split("-")[1])
                data = campos[b"data"].decode()
                yield f"id: {ultimo}\ndata: {data}\n\n"
                if data == "[DONE]":
                    return

    return StreamingResponse(leer(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})

Los ids explícitos 0-1, 0-2… hacen que el número de secuencia sea el propio id del stream de Redis, y XREAD desde 0-{ultimo} devuelve solo lo posterior. Lo que conviene medir desde el primer día:

  • TTFT y TPOT medidos en el cliente, no solo en el servidor.
  • El porcentaje de streams que terminan con su evento final, y los que terminan cortados, por causa.
  • Cancelaciones por minuto y el tiempo entre la desconexión y el abort en el motor.
  • Tokens generados después de una desconexión: lo que se tira.
  • Reconexiones y cuántas logran reanudar.
  • Streams abiertos por instancia y la duración de los streams en p99.

Ejercicio de diseño: el streaming de un asistente móvil

Un asistente recibe 3000 requests por segundo en el pico. Las respuestas promedian 700 tokens a 40 tokens por segundo, con un TTFT de 0.8 s, y un 10 % de las requests usa un modelo que razona hasta 60 segundos antes del primer token visible. El 30 % de los usuarios está en el teléfono, donde la conexión se corta seguido. El producto tiene un botón "Detener" y promete que, si la red se corta, la respuesta sigue al volver dentro de 2 minutos. Adelante del servicio hay Cloudflare y un balanceador de AWS.

Diseña el streaming: cuántos streams vas a sostener, qué configuras en la infraestructura, cómo se reanuda, qué significa cancelar, qué errores ve el cliente y qué mides.

Ver la solución de referencia
  • Capacidad: un stream normal dura 0.8 + 700 ÷ 40 = 18.3 s, y uno con razonamiento, hasta unos 78 s. Promediando, 0.9 × 18.3 + 0.1 × 78 ≈ 24 s, así que por la ley de Little hay 3000 × 24 ≈ 72 000 streams abiertos. A 10 000 por instancia son 8 gateways solo por conexiones, más margen para perder una zona.
  • Infraestructura: buffering desactivado en cada proxy (X-Accel-Buffering: no) y sin compresión del stream. El timeout de inactividad del balanceador se sube, por ejemplo a 300 s, y aun así se manda un comentario cada 15 s: eso cubre los 125 s de Cloudflare durante los 60 s de razonamiento. Todo sobre HTTP/2.
  • Reanudación: la generación va en workers que escriben en streams de Redis por respuesta, con ids secuenciales y una expiración de 5 minutos, más que los 2 prometidos. El cliente guarda el último id y reconecta con Last-Event-ID y backoff con jitter, para que un corte masivo no se convierta en una tormenta de reconexiones.
  • Cancelar: una desconexión no cancela, porque la promesa es reanudar. El botón "Detener" llama a un endpoint explícito que aborta la generación en el motor. Las respuestas abandonadas se generan igual hasta el final, y ese costo se mide.
  • Errores: los errores después del 200 viajan como eventos. El cliente conserva el texto parcial, muestra el error y ofrece reintentar; distingue los 429 con Retry-After, que espera, del tope de gasto, que no reintenta, y de la sobrecarga, que reintenta con backoff o pasa a otro modelo.
  • Métricas: TTFT medido en el teléfono, porcentaje de streams completos, reconexiones y su tasa de éxito, tiempo del botón "Detener" hasta el abort y streams abiertos por instancia.
