El producto ChatGPT

El modelo es una parte del producto. Alrededor hay una base de datos que guarda conversaciones con ramas, un turno que tiene que sobrevivir a una conexión que se corta, archivos que se convierten en índices, código ajeno que corre aislado y un pipeline que revisa lo que entra y lo que sale.

20.1Qué hay alrededor del modelo

Los módulos anteriores construyeron la parte que genera tokens: el motor (M15), la API con streaming (M17), las cuotas (M18) y la flota (M19). Un producto de chat agrega lo que el usuario ve: conversaciones que se guardan, se retoman y se comparten, archivos, herramientas y memoria. Casi todo eso es backend clásico; lo nuevo es la forma de los datos.

Diseño de referencia Esos números piden particionar desde el primer día, y la clave natural es la conversación: casi toda lectura y escritura toca una sola.

20.2El esquema de datos

Usuarios y organizaciones son tablas chicas y relacionales: cambian poco y se leen con caché. Las conversaciones y los mensajes son el volumen grande. Una conversación guarda su dueño, su título (que genera un modelo chico después del primer turno) y el current_node: el último mensaje de la rama que el usuario está viendo.

Trade-off

El historial lateral ("mis conversaciones") se consulta por usuario, pero las conversaciones se particionan por id. Un índice global por user_id obliga a consultar todas las particiones; la salida habitual es una tabla aparte, particionada por usuario, que guarda solo id, título y fecha, y se actualiza con cada turno. Es una desnormalización: dos escrituras por turno a cambio de una lectura que toca una sola partición.

20.3Los mensajes son un árbol

Una conversación parece una lista, pero no lo es. Si el usuario pide "regenerar", el producto no borra la respuesta anterior: agrega otra respuesta al mismo mensaje, y las flechas "2 / 2" permiten volver a la primera. Si edita un mensaje viejo, el original queda y la edición es un hermano con su propia continuación. Por eso cada mensaje guarda su padre, y la conversación es un árbol de mensajes.

El formato con el que ChatGPT exporta los datos del usuario lo muestra: cada conversación trae un mapping de nodos con parent y children, y un current_node. Documentado

Armar el contexto desde la rama

Para cada turno, la API camina desde el padre del mensaje nuevo hasta la raíz y da vuelta la lista. Como todos los mensajes de la conversación están en la misma partición, alcanza con traerlos todos (unas decenas de filas) y caminar en memoria; una consulta recursiva hace lo mismo en la base:

WITH RECURSIVE rama AS (
  SELECT * FROM messages
   WHERE conversation_id = $1 AND id = $2          -- el padre del mensaje nuevo
  UNION ALL
  SELECT m.* FROM messages m
    JOIN rama r ON m.conversation_id = r.conversation_id AND m.id = r.parent_id
)
SELECT role, content FROM rama ORDER BY created_at;
def armar_contexto(mensajes, hoja_id, max_tokens):
    por_id = {m.id: m for m in mensajes}
    rama, nodo = [], por_id[hoja_id]
    while nodo is not None:
        rama.append(nodo)
        nodo = por_id.get(nodo.parent_id)
    rama.reverse()                       # de la raíz a la hoja
    return recortar(rama, max_tokens)    # M16: resumir o descartar lo más viejo

El árbol tiene una consecuencia para el prefix caching: dos ramas hermanas comparten todo el prefijo hasta el punto donde se separan. Regenerar una respuesta reutiliza el KV cache del prompt completo si la request cae en la misma réplica (M19).

20.4Un turno de punta a punta

  1. Guardar el mensaje con el id del clienteEl navegador genera el id del mensaje. Si la red falla y reintenta, el INSERT choca con la PK y la API devuelve el turno que ya está en curso, sin generar dos respuestas. Es la idempotency key del M02 sin tabla aparte.
  2. Crear la respuesta vacíaUn mensaje assistant con status = in_progress. Si el servidor muere a mitad, queda una marca visible en lugar de un hueco.
  3. Armar el contexto y llamar a inferenciaLa rama, los archivos relevantes (20.5), la memoria (20.7) y las herramientas disponibles.
  4. Reenviar y copiar cada eventoCada evento SSE lleva un id creciente y se agrega a un stream de Redis con la clave del mensaje (XADD), con un TTL de minutos.
  5. Cerrar el turnoAl terminar, una sola escritura guarda el contenido, status = complete y mueve current_node. Si el usuario canceló, se guarda lo generado con status = interrupted.

Qué pasa si falla

Un teléfono que cambia de antena corta el SSE a mitad de una respuesta de 40 segundos. Sin buffer, hay dos opciones malas: cancelar la generación (y cobrar los tokens igual) o seguir generando sin nadie que escuche. Con el buffer, el cliente reconecta con Last-Event-ID y recibe lo que se perdió; la generación nunca se enteró. Por eso la generación no depende de la conexión del cliente: corre hasta terminar o hasta que el usuario la cancele de forma explícita.

20.5Archivos y RAG

Un usuario sube un PDF de 200 páginas y pregunta por la cláusula de rescisión. El archivo no entra entero en cada turno: se convierte en un índice y en cada pregunta se buscan los fragmentos relevantes. Es el RAG del M16, ahora como pipeline.

  1. Subir directo al almacenamientoLa API devuelve una signed URL y el navegador sube el archivo a S3 sin pasar por los servidores de la API (M09). ChatGPT acepta archivos de hasta 512 MB. Documentado
  2. ParsearUn worker toma el evento de "archivo subido" de una cola y extrae el texto: PDF, Word, planillas. Las páginas escaneadas necesitan OCR. Es CPU, no GPU, y puede tardar minutos: va asíncrono, con el estado visible en la interfaz.
  3. Partir en fragmentosEl chunking corta el texto en fragmentos solapados. El file search de la API de OpenAI usa por defecto fragmentos de 800 tokens con 400 de solapamiento. Documentado
  4. Calcular embeddingsCada fragmento pasa por un modelo de embeddings: solo prefill, en lotes grandes. File search usa text-embedding-3-large con 256 dimensiones. Documentado
  5. IndexarLos vectores van a una base de datos vectorial, con un índice aproximado (HNSW o IVF) y el filtro por dueño: una búsqueda nunca tiene que devolver fragmentos de otro usuario.

Los números del ejemplo: 200 páginas a unos 500 tokens por página son 100 000 tokens. Con fragmentos de 800 que avanzan de a 400, salen unos 250 fragmentos y 200 000 tokens embebidos; a 0.13 dólares por millón con text-embedding-3-large, 2.6 centavos. Cada vector de 256 dimensiones en float32 ocupa 1 KB: 250 KB de vectores para todo el documento. El costo real está en el parsing y en lo que se agrega al prompt de cada pregunta: 10 fragmentos son 8 000 tokens de entrada por turno.

En producción real

La búsqueda por embeddings falla con nombres propios, códigos y números ("cláusula 14.3"). Los sistemas reales combinan la búsqueda vectorial con búsqueda por palabras (BM25) y reordenan los candidatos con un modelo chico (reranking) antes de meterlos en el prompt. File search de OpenAI hace las dos búsquedas y reordena. Documentado

20.6Herramientas y código en sandbox

Con herramientas, un turno deja de ser una sola llamada al modelo. El modelo pide una herramienta (el tool calling del M17), la API la ejecuta, agrega el resultado como un mensaje tool y vuelve a llamar al modelo. Un turno con búsqueda web y análisis de datos puede hacer cinco o seis vueltas, y cada vuelta es un mensaje más en el árbol.

La herramienta más delicada corre código que escribió el modelo, con archivos del usuario. Ese código no es confiable: puede intentar leer otros archivos, abrir conexiones o quedarse en un bucle. Un sandbox de código lo aísla:

  • Aislamiento del kernel: una microVM (Firecracker) o un kernel en espacio de usuario (gVisor), no un contenedor común, que comparte el kernel con el host. Diseño de referencia
  • Sin red o con una lista cerrada de destinos, para que el código no saque datos.
  • Límites de CPU, memoria, disco y tiempo por ejecución.
  • Una sesión por conversación, con los archivos subidos montados, que se destruye tras un rato sin uso. En la API de OpenAI, el code interpreter cobra 0.03 dólares por sesión y cada sesión dura una hora. Documentado

Trade-off

Arrancar una microVM tarda del orden de cien milisegundos; instalar pandas en ella, segundos. Por eso se usa una imagen con las librerías ya instaladas y un pool de sandboxes precalentados, como el pool de réplicas del M19. Mantener una sesión viva entre turnos guarda las variables del usuario, pero ocupa memoria mientras el usuario lee.

20.7Memoria entre conversaciones

ChatGPT puede recordar datos del usuario entre conversaciones: memorias guardadas que el usuario ve y borra, y referencias al historial de chats. Documentado Para el sistema, la memoria es otra fuente de contexto, como los archivos:

  • Memorias explícitas: frases cortas ("prefiere respuestas en español") en una tabla por usuario. Son pocas y se agregan enteras al prompt de sistema, al principio, donde el prefix caching las aprovecha.
  • Historial: resúmenes o embeddings de conversaciones anteriores, buscados como en el RAG, con el mismo filtro por dueño.

Lo difícil no es guardar sino borrar. Si el usuario borra una memoria o una conversación, tiene que desaparecer también de los índices derivados: el vector de su resumen, los caches. Un borrado que llega a la tabla pero no al índice vectorial sigue apareciendo en las respuestas. Diseño de referencia

20.8Moderación y feedback

La moderación revisa lo que entra y lo que sale. OpenAI ofrece un endpoint de moderación gratuito, con el modelo omni-moderation-latest, que clasifica texto e imágenes por categoría. Documentado El problema de sistemas es dónde ubicarlo sin sumar latencia:

  • Entrada: se clasifica el mensaje en paralelo con el armado del contexto. Un clasificador chico tarda decenas de milisegundos, mucho menos que el prefill.
  • Salida: el stream no puede esperar a la respuesta completa. Se clasifica por tramos mientras se genera; si un tramo se marca, se corta el stream y se reemplaza lo mostrado. Es un trade-off explícito entre latencia y lo que alcanza a verse.
  • Asíncrona: los casos dudosos van a una cola para revisión posterior, sin bloquear al usuario.

El feedback (el pulgar arriba o abajo y la comparación entre dos respuestas) es una tabla más, con el id del mensaje, el modelo que contestó y el voto. Su valor está en lo que se puede reconstruir: el contexto exacto que vio el modelo. Por eso los mensajes guardan qué modelo contestó y el árbol no se pisa.

En producción real

Las organizaciones que pagan exigen que sus conversaciones no se usen para entrenar y que se borren en un plazo. Eso se resuelve en el esquema, no en un filtro posterior: la política de retención vive en la organización (20.2) y el job de borrado recorre mensajes, archivos, vectores, memorias y feedback.

Ejercicio de diseño: "compartir conversación"

Hay que agregar un botón que genera un enlace público de solo lectura a una conversación. La conversación tiene un árbol de 40 mensajes con tres ramas, dos archivos subidos y una ejecución de código con un gráfico. El dueño puede seguir escribiendo después de compartir, y puede borrar el enlace. Decide qué se comparte, cómo se guarda y qué pasa cuando el dueño borra la conversación.

Ver la solución de referencia
  • Qué se comparte: la rama visible en el momento de compartir (de la raíz a current_node), no el árbol entero: las otras ramas pueden tener versiones que el usuario descartó.
  • Una copia, no una referencia: una tabla shared_links con un id aleatorio largo y una copia de esa rama. Si el dueño sigue escribiendo, el enlace no cambia; si quiere actualizarlo, genera otra copia.
  • Archivos: el enlace muestra los nombres pero no da acceso a los archivos subidos; el gráfico generado se copia como imagen a un bucket público con el id del enlace.
  • Lecturas: la página compartida es contenido estático: se sirve desde una CDN con caché, sin tocar la base de conversaciones.
  • Borrado: borrar el enlace o la conversación borra la copia y purga la CDN. El job de retención de 20.8 incluye shared_links.
