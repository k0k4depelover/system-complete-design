Protocolos y diseño de APIs

Una API es un contrato que otros van a usar durante años, con reintentos, redes que se cortan y versiones viejas del cliente. Este módulo compara los protocolos de comunicación, abre cada uno para ver qué viaja por el cable (frames de HTTP/2, bytes de Protobuf, sobres de SOAP firmados, frames de WebSocket) y baja al detalle que separa una API que aguanta producción de una que no: semántica de métodos, errores, paginación con la tabla en movimiento, versionado e idempotencia.

  • Diseñar el envío y la recepción de webhooks que sobreviven a reintentos y desorden.

2.1Estilos de comunicación

Antes de elegir un protocolo hay que responder tres preguntas: ¿quién inicia? (el cliente pide, o el servidor avisa), ¿el que pide espera la respuesta? (síncrono o asíncrono) y ¿quién consume? (un navegador, otro servicio tuyo o el sistema de un cliente). La tabla cubre los protocolos que verás en todo el curso:

El mismo caso de uso, "enviar un mensaje a un chat y recibir la respuesta", se ve así en cada estilo:

Un recurso, un método, un código de estado. Simple, cacheable y fácil de depurar con curl.

El contrato vive en un archivo .proto del que se genera código tipado para cliente y servidor. Aquí la respuesta llega como stream del servidor.

syntax = "proto3";
package chat.v1;

service ChatService {
  rpc SendMessage(SendMessageRequest) returns (stream MessageDelta);
}

message SendMessageRequest {
  string conversation_id = 1;
  string parent_message_id = 2;
  string content = 3;
  string idempotency_key = 4;
}

message MessageDelta {
  string message_id = 1;
  string text = 2;        // fragmento de texto
  bool done = 3;
}

Los números de campo (= 1, = 2) son el contrato real en el cable: puedes renombrar campos, pero nunca reutilizar un número.

Una mutación que devuelve exactamente los campos que la pantalla necesita, incluidos datos relacionados, en una sola request.

Tras un GET con Upgrade: websocket, la conexión queda como un canal de mensajes en ambos sentidos. El protocolo de mensajes lo defines tú.

// cliente → servidor
{"type": "message.send", "request_id": "r-5510", "conversation_id": "conv_42", "content": "Hola"}

// servidor → cliente (confirma)

// servidor → cliente (otro usuario escribió en la misma conversación)
{"type": "message.new", "conversation_id": "conv_42", "message_id": "msg_20", "from": "u_77"}

// cada 25 s, en ambos sentidos
{"type": "ping"}

De dónde sale cada uno

Los protocolos no aparecieron todos juntos: cada uno respondió a los problemas del anterior, y entender esa historia explica por qué conviven hoy.

  • 1984, la idea de RPC. Andrew Birrell y Bruce Nelson, en Xerox PARC, publicaron cómo hacer que llamar a una función de otra máquina se viera igual que llamar a una local. Documentado Casi todo lo que vino después es una variante de esa idea.
  • Años noventa, RPC atado a un ecosistema. ONC RPC (Sun, la base de NFS), CORBA y Java RMI funcionaban, pero cada uno exigía su propio runtime, se llevaba mal con los firewalls y, en el caso de RMI, solo hablaba Java.
  • 1998 a 2004, RPC por HTTP y XML. XML-RPC y después SOAP usaron HTTP como transporte para pasar los firewalls, y XML para que cualquier lenguaje pudiera leer el mensaje. SOAP sumó contratos formales (WSDL) y la familia WS-*, con seguridad a nivel de mensaje (WS-Security, 2004). Documentado
  • 2000, REST. Roy Fielding, uno de los autores de HTTP, describió en su tesis el estilo de arquitectura que había hecho escalar la web. Con JSON y los navegadores, se volvió la forma por defecto de las APIs públicas. Documentado
  • 2015, vuelta al RPC binario. Google publicó gRPC, derivado de Stubby, el RPC que usaba internamente, porque entre servicios propios importan más el rendimiento y los contratos tipados que leer el mensaje a ojo. El mismo año, Facebook publicó GraphQL, que usaba desde 2012 en su app móvil. Documentado

2.2REST bien hecho: métodos y códigos de estado

Qué es REST, según quien lo definió

REST no es "JSON por HTTP". Es un estilo de arquitectura: un conjunto de restricciones que Roy Fielding describió en su tesis doctoral del año 2000 para explicar por qué la web había escalado tanto. Documentado Cada restricción tiene una consecuencia práctica:

RestricciónQué exigeQué te da en producción
Cliente-servidorLa interfaz y los datos evolucionan por separadoUna app móvil y una web sobre la misma API
Sin estadoCada request trae todo lo necesario: credencial, cursor, versiónCualquier instancia atiende cualquier request: el balanceo es trivial y escalar es agregar instancias (M03)
CacheableCada respuesta dice si se puede guardar y cuánto (Cache-Control, ETag)CDNs, proxies y navegadores te ahorran requests (M04)
Interfaz uniformeRecursos con URL, representaciones (JSON, HTML), mensajes que se describen solos (método, headers, tipo de contenido) e hipermediaUn proxy que no conoce tu API igual sabe que un GET se puede reintentar y cachear
Sistema en capasEl cliente no sabe si habla con el servidor o con un intermediarioPuedes meter una CDN, un gateway o un balanceador sin cambiar al cliente
Código bajo demanda (opcional)El servidor puede enviar código que el cliente ejecutaEl JavaScript de una página web

En 2008, Leonard Richardson propuso una escala para medir qué tan "REST" es una API, que Martin Fowler popularizó con el nombre de modelo de madurez de Richardson. Documentado

El nivel 3, HATEOAS (hipermedia como motor del estado de la aplicación), es el que Fielding considera obligatorio y el que casi nadie implementa por completo: la respuesta trae enlaces a lo que se puede hacer a continuación, y el cliente navega por ellos en lugar de armar URLs. Lo que sí se ve a menudo es una versión parcial, útil y barata: la API de GitHub incluye en sus respuestas las URLs de los recursos relacionados (url, html_url, comments_url), y la paginación devuelve el enlace a la página siguiente en el header Link. Documentado La sección siguiente se queda en el nivel 2, que es donde están las decisiones que más pesan.

Lo que promete cada método

Los métodos HTTP no son sinónimos con distinto nombre: cada uno promete propiedades que la infraestructura aprovecha. Un proxy puede reintentar un GET porque es seguro e idempotente; una CDN puede cachearlo; un navegador puede precargarlo. Si usas GET para algo que modifica datos, tarde o temprano alguien lo va a repetir por ti.

El request_id no es decorativo: es lo que el cliente te manda en el ticket de soporte, y con él encuentras la request exacta en tus logs y traces (M11).

2.3Paginación: offset o cursor

La paginación por offset es la primera que todos escriben y la primera que falla en producción, por dos razones. El costo: OFFSET 100000 obliga a la base a leer y descartar 100 000 filas. Y la consistencia: si se insertan o borran filas entre página y página, los elementos se repiten o se pierden.

La paginación por cursor (o keyset) pide "los siguientes después de este", usando un índice:

-- Página siguiente: posts anteriores al último que vio el cliente
SELECT id, author_id, body, created_at
FROM posts
WHERE feed_id = $1
  AND (created_at, id) < ($2, $3)      -- el cursor: (created_at, id) del último elemento
ORDER BY created_at DESC, id DESC
LIMIT 21;                                -- uno de más para saber si hay otra página

-- Índice que hace esto barato a cualquier profundidad
CREATE INDEX posts_feed_cursor ON posts (feed_id, created_at DESC, id DESC);
GET/v1/feeds/{feed_id}/posts?limit=20&cursor={cursor}Diseño de referencia

El cursor es opaco para el cliente: un base64 de (created_at, id), firmado si no quieres que lo manipulen.

{
  "data": [ { "id": "post_981", "body": "…", "created_at": "2026-09-27T13:59:02Z" } ],
  "next_cursor": "eyJ0IjoiMjAyNi0wOS0yN1QxMzo1OTowMloiLCJpZCI6InBvc3RfOTgxIn0",
  "has_more": true
}

El id va en el cursor como desempate: dos filas pueden tener el mismo created_at y, sin desempate, una de ellas se perdería entre páginas. Lo que el cursor no permite es "saltar a la página 37". Casi nunca hace falta; cuando sí (paneles de administración), se acepta el offset con un límite máximo de profundidad.

Cuánto cuesta cada una, y por qué

La documentación de PostgreSQL lo dice sin rodeos: "las filas que se saltea un OFFSET igual se tienen que calcular dentro del servidor; por eso un OFFSET grande puede ser ineficiente". Documentado La razón está en cómo es un índice. Un B-tree está ordenado y sabe buscar por valor: desde la raíz, en cada nivel elige la rama que contiene el valor, hasta llegar a una hoja. Lo que no sabe es buscar por posición: ningún nodo guarda cuántas filas hay debajo de cada rama, así que "la fila número 100 000" solo se encuentra contando desde la primera. Y en PostgreSQL, además, cada fila contada puede exigir visitar la tabla para comprobar si es visible para tu transacción (por MVCC: cada versión de una fila guarda qué transacciones la pueden ver, M05).

Es habitual leer que el cursor es O(1). Casi: es O(log n + k), donde n es el tamaño del índice y k el tamaño de la página. Bajar por el árbol cuesta un nivel por cada factor de crecimiento, y ese factor es enorme. La cuenta a mano, con páginas de 8 KB y entradas de unos 40 bytes (tres columnas de 8 bytes más la cabecera y el puntero de cada entrada), da unas 200 entradas por página:

Filas en el índiceNiveles del árbolPor qué
1 millón3200³ = 8 000 000 entradas caben en 3 niveles
100 millones4200⁴ = 1 600 000 000
10 000 millones5200⁵ = 320 000 000 000

Multiplicar la tabla por 100 suma un nivel. Y la raíz y los niveles internos se consultan en cada búsqueda, así que casi siempre están en memoria: lo que de verdad se lee del disco es una hoja y las k filas. Por eso, en la práctica, el cursor se comporta como si fuera constante, mientras el OFFSET crece en línea recta con la página.

Slack describe lo mismo desde su experiencia: endpoints que se diseñaron para devolver cientos de registros terminaron devolviendo cientos de miles, y con OFFSET "la base igual tiene que leer del disco hasta offset + count filas". Por eso migraron a cursores. Documentado

Qué pasa cuando llegan inserts mientras alguien pagina

Un OFFSET es una posición: "sáltate las primeras 4". Un cursor es un valor: "dame lo que esté por debajo de (10:00:12, post_88)". Esa diferencia decide qué pasa cuando la tabla cambia entre una página y la siguiente:

  1. Un insert arribaLlega un post nuevo. Con OFFSET, todo se corre un lugar y la página 2 vuelve a traer D. Con cursor, el post nuevo tiene un created_at mayor que la marca, así que queda fuera del rango < (marca): la página 2 sale bien, y el post nuevo aparece cuando el usuario pida lo nuevo, arriba.
  2. Un borrado de algo ya leídoCon OFFSET, todo sube un lugar y E no aparece nunca. Con cursor no pasa nada: la condición compara valores, así que funciona aunque la fila de la marca ya no exista.
  3. Una fila que aparece detrás de la marcaEste es el caso que el cursor no resuelve solo, y el que más sorprende. Pasa cuando una fila se vuelve visible con un valor de orden que el lector ya pasó.
  4. Una fila que cambia de lugarSi ordenas por algo que cambia (updated_at, un puntaje), una fila editada salta a otra posición: puede salir dos veces o ninguna, con offset o con cursor. Ordena por algo inmutable o usa un snapshot.

¿Cómo aparece una fila "en el pasado"? Más fácil de lo que parece:

  • Commits tardíos. En PostgreSQL, now() devuelve la hora de inicio de la transacción, no la del commit. Documentado Una transacción que empieza a las 10:00:00, tarda 3 segundos y confirma a las 10:00:03 deja una fila con created_at = 10:00:00 que nadie pudo ver hasta las 10:00:03. Si en ese intervalo un lector leyó posts de las 10:00:01 y 10:00:02, la fila nueva quedó detrás de su marca.
  • Secuencias. Los ids de una secuencia se reparten al insertar, no al confirmar: la transacción que recibió el 1001 puede confirmar después que la del 1002. Un cursor sobre el id tiene el mismo problema.
  • Relojes de varias máquinas. Si cada servidor de aplicación pone el created_at con su propio reloj, un desfase de 200 ms basta para que una fila nueva quede "antes" de otra que ya se leyó (M06).
  • Réplicas con retraso. Si la página 1 sale del primario y la 2 de una réplica atrasada (M05), el lector puede ver huecos que después se llenan.

En un feed que se lee scrolleando, perderse un post de vez en cuando es aceptable. En una sincronización, no: un cliente contable que cada 5 minutos pide "los movimientos posteriores al último que tengo" se pierde esa fila para siempre, porque nunca vuelve a pedir ese rango. Las soluciones, de la más simple a la más robusta:

TécnicaCómo funcionaCosto
Ventana de solapePedir created_at > marca − 10 s y descartar por id lo que ya tienesRelees un poco cada vez; la ventana tiene que ser mayor que la transacción más larga (un statement_timeout la acota)
Marca de aguaDevolver solo filas con created_at < now() − 5 s: lo más reciente todavía puede estar en vueloLo nuevo aparece con 5 s de demora

Bajar y subir: before y after

Un feed se recorre en dos direcciones: hacia abajo (más viejo) al scrollear, y hacia arriba (más nuevo) al tirar para refrescar. Cada dirección usa su propia marca:

-- Hacia abajo: lo anterior a la marca de abajo
SELECT … WHERE feed_id = $1 AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC LIMIT 21;

-- Hacia arriba: lo posterior a la marca de arriba, en orden ASCENDENTE
SELECT … WHERE feed_id = $1 AND (created_at, id) > ($4, $5)
ORDER BY created_at ASC, id ASC LIMIT 21;     -- la app invierte la lista antes de mostrarla

¿Por qué ascendente al subir? Si el usuario estuvo tres horas sin abrir la app y llegaron 500 posts, pedir "los 20 más nuevos" trae los últimos 20 y deja un hueco de 480 entre esos y lo que ya tenía. Con orden ascendente desde la marca, la página trae los 20 que siguen inmediatamente, sin hueco, y se repite hasta alcanzar el presente. La alternativa, que usan muchas apps, es traer los 20 más nuevos y mostrar un separador "cargar más" en el hueco, que se llena paginando hacia abajo desde ahí.

Las APIs públicas exponen las dos marcas: Twitter usó since_id y max_id en sus timelines, y Stripe usa starting_after y ending_before con limit y has_more. Documentado

El cursor por dentro

  • Qué guarda. Los valores de las columnas de orden de la última fila (created_at e id), la dirección, y una huella de los filtros: un cursor de "mis posts con la etiqueta X" no debería servir para otra consulta.
  • Por qué opaco. Si el cliente no puede leerlo, puedes cambiar lo que guarda sin romper a nadie. Slack lo aprovechó: su cursor es un base64 (dXNlcjpXMDdRQ1JQQTQ= es user:W07QCRPA4), y en endpoints viejos podía esconder un offset por dentro mientras migraba. Documentado
  • Firmado. Con un HMAC, nadie fabrica un cursor que lea fuera de lo permitido.
  • El índice tiene que coincidir. Las columnas y las direcciones del ORDER BY tienen que ser las del índice. La comparación de filas (a, b) < (x, y) funciona solo si las dos columnas van en la misma dirección; si mezclas (created_at DESC, id ASC), se escribe a mano: created_at < $t OR (created_at = $t AND id > $id).
  • Sin nulos en la clave de orden. Un NULL no es menor ni mayor que nada: esas filas desaparecen de la paginación. Usa columnas NOT NULL.
import base64, hashlib, hmac, json

SECRETO = b"rotar-cada-90-dias"

def encode_cursor(created_at: str, id: str, filtros: dict) -> str:
    datos = {"t": created_at, "id": id, "f": hashlib.sha256(json.dumps(filtros, sort_keys=True).encode()).hexdigest()[:16]}
    crudo = json.dumps(datos, separators=(",", ":")).encode()
    firma = hmac.new(SECRETO, crudo, hashlib.sha256).digest()[:16]
    return base64.urlsafe_b64encode(crudo + firma).decode().rstrip("=")

def decode_cursor(cursor: str, filtros: dict) -> dict:
    bruto = base64.urlsafe_b64decode(cursor + "=" * (-len(cursor) % 4))
    crudo, firma = bruto[:-16], bruto[-16:]
    if not hmac.compare_digest(firma, hmac.new(SECRETO, crudo, hashlib.sha256).digest()[:16]):
        raise ValueError("cursor inválido")            # la API responde 400
    datos = json.loads(crudo)
    if datos["f"] != hashlib.sha256(json.dumps(filtros, sort_keys=True).encode()).hexdigest()[:16]:
        raise ValueError("el cursor es de otra consulta")
    return datos

Contar el total, saltar páginas y exportar

  • Saltar a una página. Si hace falta, se permite offset con un tope. Elasticsearch lo trae de fábrica: from + size no puede pasar de 10 000 por defecto (index.max_result_window), y para ir más lejos recomienda search_after, que es un cursor. Documentado
  • Exportar todo, consistente. Para una foto exacta de millones de filas, el cursor no alcanza: hace falta un snapshot. En PostgreSQL, una transacción REPEATABLE READ con un DECLARE CURSOR; en Elasticsearch, un point in time con search_after. 2.4Versionado y evolución sin romper clientes

Una API pública tiene clientes que no controlas y que no se actualizan: apps móviles de hace dos años, integraciones que nadie mantiene. La regla es separar cambios compatibles de cambios que rompen:

  • Compatibles: agregar endpoints, agregar campos opcionales a la respuesta, aceptar parámetros opcionales nuevos, agregar valores a un enum (si los clientes toleran valores desconocidos).
  • Rompen: quitar o renombrar campos, cambiar tipos o formatos, volver obligatorio algo opcional, cambiar el significado de un código de estado.

Los cambios compatibles solo funcionan si los clientes son tolerant readers: ignoran campos que no conocen. Los que rompen necesitan una versión nueva. Hay tres formas comunes de expresarla:

EstrategiaEjemploVentajaCosto
En la URL/v1/pagos, /v2/pagosVisible, fácil de enrutar y cachearVersiones gruesas: todo cambia de golpe
En un headerAccept: application/vnd.ejemplo.v2+jsonURLs establesInvisible en logs y difícil de probar a mano
Por fecha, fijada por cuentaStripe-Version: 2024-06-20Cada cliente queda fijo en la versión con la que se integró; los cambios se aplican con capas de compatibilidadExige mantener transformaciones entre versiones durante años

Stripe usa la tercera: cada cuenta queda fijada en la versión del día en que se integró, y el servidor transforma las respuestas hacia atrás versión por versión. Documentado Para retirar algo, anuncia la fecha con los headers Deprecation y Sunset (RFC 8594) y mide quién sigue usándolo antes de apagarlo.

2.5Idempotencia en la API

En M00 viste el problema: si la respuesta se pierde, el cliente no sabe si su operación se ejecutó. Con GET, PUT y DELETE puede reintentar tranquilo. Con un POST que cobra dinero, no. La solución estándar es una idempotency key que el cliente genera una vez por operación lógica y reenvía en cada reintento:

El algoritmo, en orden:

  1. Reservar la claveINSERT … ON CONFLICT DO NOTHING. Si insertó una fila, esta request es la primera: sigue.
  2. Si ya existía, compararSi el hash difiere, responde 422: la clave se reutilizó con otra request. Si está completed, devuelve la respuesta guardada. Si está in_progress, responde 409: la primera request todavía se está procesando.
  3. Ejecutar la operaciónY en la misma transacción que sus efectos locales (crear el pago en tu base), guardar la respuesta y marcar la clave como completed.
  4. PurgarUn job borra claves de más de 24 h. Un reintento después de eso se trata como una request nueva.

Qué pasa si el proceso muere a mitad de la operación

La clave queda en in_progress para siempre y los reintentos reciben 409 eternamente. Por eso existe locked_until: vencido el lock, otro proceso puede retomar la clave. Pero retomar exige saber si el efecto externo (el cobro) llegó a ocurrir: se consulta al procesador de pagos con la misma clave, que también debe ser idempotente de su lado. Este es el caso más difícil del sistema de pagos y se resuelve por completo en M27.

Concurrencia optimista con ETag

Otro problema de las APIs con escrituras: dos clientes leen el mismo recurso, lo modifican y guardan; el segundo pisa al primero sin enterarse (lost update). Un ETag resuelve el caso sin bloquear a nadie:

GET /v1/documentos/doc_9           →  200 OK   ETag: "v17"

PUT /v1/documentos/doc_9
If-Match: "v17"
{ …cambios… }                       →  200 OK   ETag: "v18"     (nadie lo había cambiado)
                                    →  412 Precondition Failed  (otro guardó v18 antes: recarga y decide)

Del lado de la base es un UPDATE … SET version = version + 1 WHERE id = $1 AND version = $2: si actualizó 0 filas, alguien ganó la carrera.

2.6RPC: llamar a una función en otra máquina

REST piensa en recursos: hay cosas con URL y se les aplican verbos. RPC (Remote Procedure Call) piensa en acciones: hay funciones, y las llamas con argumentos. La idea, publicada por Birrell y Nelson en 1984, es que el programador escriba cobrar(42, 2500) y no se entere de que la función corre en otra máquina. Documentado Para lograrlo, un generador de código lee el contrato, escrito en un IDL (lenguaje de definición de interfaces), y produce dos piezas: un stub en el cliente, con la misma firma que la función real, y otro en el servidor que la invoca.

Una llamada remota no es una llamada local

El atractivo de RPC, que la red sea invisible, es también su trampa. En 1994, cuatro ingenieros de Sun Microsystems publicaron "A Note on Distributed Computing", que explica por qué esconder la red por completo es un error: una llamada remota difiere de una local en latencia, en que no comparte memoria (no hay punteros), en la concurrencia y, sobre todo, en las fallas parciales. Documentado Una función local termina o lanza una excepción. Una remota puede quedar sin respuesta, y entonces no sabes si se ejecutó. Por eso todo RPC serio expone lo que la red agrega en lugar de esconderlo:

  • Plazos. Toda llamada tiene un deadline. Sin él, un servidor colgado retiene hilos del cliente hasta agotarlos (M08).
  • Semántica de entrega. Si el cliente reintenta, la función puede ejecutarse dos veces: "al menos una vez". Si no reintenta, "como mucho una vez". Para efectos que no se pueden duplicar, hace falta idempotencia (2.5), igual que en REST. ONC RPC, por ejemplo, pone un identificador de transacción (xid) en cada llamada para emparejar respuestas, y los servidores lo usan para detectar retransmisiones. Documentado
  • Versiones mezcladas. Durante un deploy, clientes viejos llaman a servidores nuevos y al revés. El formato tiene que tolerar campos que uno de los dos no conoce.

gRPC por dentro

gRPC nació de Stubby, el RPC que Google usaba internamente, y se publicó como código abierto en 2015. Documentado Dentro de tu sistema, los servicios se llaman millones de veces por segundo y los contratos cambian a menudo. gRPC aporta lo que ahí importa:

  • Contratos tipados en Protocol Buffers, con código generado para cada lenguaje: un cambio incompatible falla al compilar, no en producción.
  • Binario y compacto sobre HTTP/2 con conexiones persistentes y multiplexadas.
  • Cuatro modos: unario, streaming del servidor, del cliente y bidireccional.
  • Deadlines que se propagan: si el usuario tiene 2 s de presupuesto y ya se gastaron 1.5 s, el servicio de más abajo recibe 0.5 s y no trabaja en vano.

Cada llamada es un stream de HTTP/2. El cliente abre el stream con un frame HEADERS y manda los mensajes en frames DATA; el servidor contesta igual y cierra con un segundo HEADERS, los trailers, donde va el resultado:

  • La ruta es el método. :path es /paquete.Servicio/Método, siempre con POST. Un balanceador L7 puede enrutar por servicio leyendo solo la ruta.
  • te: trailers sirve para detectar proxies que no soportan trailers: sin ellos, el cliente nunca sabría si la llamada salió bien.
  • grpc-timeout lleva el deadline como duración, con unidades H, M, S, m, u y n: 1500m son 1.5 s. Cada servidor le resta lo que ya gastó antes de llamar al siguiente.
  • Cada mensaje lleva un prefijo de 5 bytes: 1 de compresión y 4 con el largo, en big endian. Así el receptor sabe dónde termina un mensaje y empieza otro dentro del stream.
  • El estado va al final. El :status 200 de HTTP se envía antes de saber cómo termina la llamada; el resultado real es grpc-status en los trailers. Una llamada que falla de inmediato puede mandar solo trailers (Trailers-Only). Para un monitor que solo mira códigos HTTP, gRPC siempre "anda bien": mide grpc-status.

Protocol Buffers, byte por byte

Protobuf no manda nombres de campos: manda números. Cada campo empieza con un tag que junta el número de campo y el tipo de dato en el cable: tag = (número << 3) | tipo. Documentado

TipoNombreParaCómo se escribe
0VARINTint32, int64, uint, bool, enumGrupos de 7 bits; el bit más alto de cada byte dice si sigue otro
1I64fixed64, double8 bytes
2LENstring, bytes, mensajes anidados, listas empaquetadasUn varint con el largo y después los bytes

El ejemplo de la documentación oficial: el campo 1 con el valor 150 se escribe 08 96 01. El 08 es (1 << 3) | 0. El 150 en binario es 10010110: no entra en 7 bits, así que se parte en 0010110 (los 7 bajos, con un 1 adelante porque sigue otro byte: 96) y 0000001 (01). Documentado Tres consecuencias de diseño salen de aquí:

  • Los campos 1 a 15 ocupan un byte de tag; del 16 al 2047, dos. Los campos que más se envían van con números chicos.
  • Los negativos en int32 son caros: se extienden a 64 bits y ocupan 10 bytes. Para valores que suelen ser negativos, sint32 usa ZigZag (−1 → 1, 1 → 2, −2 → 3…) y quedan cortos.
  • La compatibilidad está en los números. Un receptor que encuentra un número desconocido lo saltea (el tipo le dice cuántos bytes saltar) y lo conserva. Por eso puedes agregar campos y renombrarlos, pero nunca reutilizar un número: márcalo con reserved 4; cuando borres el campo. En proto3, los valores por defecto (0, "", false) ni siquiera se envían.

Con los valores iniciales del simulador, el mensaje ocupa 20 bytes en Protobuf y 77 en JSON sin espacios: un 26 %. Con gzip la distancia se achica en mensajes largos y repetitivos; lo que no se achica es el trabajo de parsear texto, ni la ventaja de tener un esquema que el compilador verifica.

Balancear y exponer gRPC

Una conexión HTTP/2 vive mucho y lleva miles de llamadas. Con un balanceador L4 (M03), el balanceo se decide por conexión: si el cliente abre una sola, todas sus llamadas caen en la misma instancia, y las réplicas nuevas que agrega el autoescalado no reciben nada. Tres salidas:

  • Proxy L7 (Envoy, un service mesh): termina HTTP/2 y reparte cada stream por separado.
  • Balanceo en el cliente: el resolver de nombres devuelve todas las instancias y el cliente reparte con una política. La de por defecto, pick_first, usa una sola; round_robin abre una conexión a cada una. Documentado Con xDS, un plano de control le envía al cliente la lista y los pesos: un service mesh sin proxy.
  • Edad máxima de conexión en el servidor (MAX_CONNECTION_AGE): obliga a los clientes a reconectar cada tanto, y las conexiones nuevas se reparten entre las instancias nuevas. Documentado

Hacia los navegadores, gRPC no funciona tal cual: JavaScript no puede leer trailers ni controlar frames de HTTP/2. gRPC-Web cambia el formato para que los trailers viajen dentro del cuerpo, y necesita un proxy que traduzca. Por eso, hacia afuera, gRPC suele quedarse detrás de un gateway que expone REST.

2.7SOAP: contratos formales y seguridad en el mensaje

SOAP es un protocolo de mensajes en XML. Nació como RPC por HTTP (SOAP 1.1, una nota del W3C de mayo de 2000) y se estandarizó como SOAP 1.2, recomendación del W3C desde el 24 de junio de 2003. Documentado Ya casi nadie lo elige para una API nueva, pero sigue en el corazón de muchas integraciones entre bancos, aseguradoras, gobiernos y sistemas empresariales, y es probable que te toque integrarte con uno. Salesforce, por ejemplo, sigue publicando su SOAP API junto a la REST. Documentado

El sobre: Envelope, Header, Body y Fault

Todo mensaje SOAP es un Envelope con dos partes. El Body lleva la operación y sus datos. El Header, opcional, lleva bloques que no son de la operación sino del viaje: seguridad, ruteo, transacciones. Un bloque marcado con mustUnderstand="true" obliga al receptor a procesarlo o a rechazar el mensaje: así se agregan capacidades sin que un servidor viejo las ignore en silencio. Si algo falla, el Body trae un Fault:

HTTP/1.1 400 Bad Request
Content-Type: application/soap+xml; charset=utf-8

<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Body>
    <soap:Fault>
      <soap:Code>
        <soap:Value>soap:Sender</soap:Value>            <!-- la culpa es de quien envió -->
        <soap:Subcode><soap:Value>c:MontoInvalido</soap:Value></soap:Subcode>
      </soap:Code>
      <soap:Reason><soap:Text xml:lang="es">El monto debe ser positivo</soap:Text></soap:Reason>
    </soap:Fault>
  </soap:Body>
</soap:Envelope>

Sender equivale a un 4xx y Receiver a un 5xx: dice si reintentar tiene sentido. En el binding HTTP de SOAP 1.2, un fault de tipo Sender viaja con 400 y los demás con 500. Documentado Las dos versiones conviven, y se confunden a menudo:

WSDL: el contrato primero

Un WSDL (Web Services Description Language) es el IDL de SOAP: un XML que describe los tipos (con XML Schema), las operaciones con sus mensajes de entrada, salida y error, cómo se codifican, y la URL del servicio. Las herramientas leen el WSDL y generan los stubs, igual que protoc con un .proto: en Java, wsimport; en .NET, svcutil. Integrarse con un banco suele empezar así: te mandan un WSDL, generas el cliente y llamas métodos tipados.

<wsdl:portType name="Pagos">

    <wsdl:output message="tns:CobrarResponse"/>

¿Por qué se dice que SOAP es más seguro?

La respuesta corta: SOAP en sí no trae seguridad. Lo que la trae es WS-Security, un estándar de OASIS de abril de 2004 que define cómo firmar y cifrar partes de un mensaje SOAP. Documentado La diferencia de fondo está en qué se protege. TLS protege la conexión: cada salto entre dos máquinas. WS-Security protege el mensaje: la protección viaja con él, sin importar por cuántas manos pase.

En una arquitectura con un ESB (un bus de servicios que enruta y transforma mensajes), colas y sistemas de terceros en el medio, eso importa. Un mensaje firmado con WS-Security se ve así:

Lo que WS-Security agrega, y que TLS solo no da:

  • Integridad de punta a punta. Si un intermediario cambia el monto, el hash del Body no coincide y la firma falla, aunque cada salto haya usado TLS.
  • Confidencialidad selectiva. Con XML Encryption se cifra solo el Body, o solo el número de tarjeta: el ESB puede leer los headers de ruteo sin ver los datos.
  • No repudio. La firma se hace con la clave privada de un certificado X.509 de la empresa que envía. Guardado el mensaje firmado, esa empresa no puede negar después que lo envió: la prueba es criptográfica y sobrevive al mensaje. Para bancos y gobiernos, eso vale más que todo lo demás. Con TLS, la prueba muere al cerrar la conexión.
  • Protección contra replay. El Timestamp firmado, con vencimiento, impide reenviar un mensaje capturado horas después.
  • Política en el contrato. Con WS-Policy, el WSDL declara qué hay que firmar y cifrar, y las herramientas lo aplican solas al generar el cliente. La familia WS-* suma entrega confiable (WS-ReliableMessaging) y transacciones distribuidas con commit en dos fases (WS-AtomicTransaction, el 2PC del M06).

Nada de esto es exclusivo de SOAP. En el mundo JSON, la firma y el cifrado de mensajes existen como JWS y JWE (RFC 7515 y 7516), HTTP Message Signatures (RFC 9421) firma requests HTTP, y las firmas HMAC de los webhooks (2.10) son seguridad a nivel de mensaje. Documentado La diferencia es que en SOAP vienen estandarizadas, integradas al contrato y soportadas por herramientas desde hace veinte años. "SOAP es más seguro" quiere decir eso: trae seguridad de mensaje de fábrica, no que una API REST bien hecha no pueda tenerla.

Qué pasa si falla: la seguridad de XML tiene sus propios ataques

La flexibilidad de la firma por partes abrió una familia entera de ataques. En el XML Signature Wrapping, el atacante mueve la parte firmada a otro lugar del documento y pone la suya donde la aplicación la va a leer. El verificador busca el id firmado, lo encuentra y aprueba; la aplicación procesa otra cosa. En 2011, un grupo de la Universidad del Ruhr en Bochum mostró que con un solo mensaje SOAP firmado y capturado se podían ejecutar operaciones arbitrarias en la interfaz SOAP de Amazon EC2 con la identidad de la víctima. Documentado

Otros dos ataques vienen con cualquier parser de XML, SOAP o no:

  • XXE (XML External Entity): una entidad que apunta a file:///etc/passwd o a una URL interna hace que el parser la lea y la meta en el documento. Se apaga desactivando las DTD y las entidades externas.
  • Billion laughs: diez entidades anidadas, cada una con diez copias de la anterior, expanden a 10⁹ copias de un texto de 3 bytes: unos 3 GB de memoria a partir de un mensaje de menos de 1 KB. Se evita igual, y con límites de expansión.

Trade-off

Elige SOAP cuando la otra parte lo exige, que es lo más común, o cuando necesitas no repudio y mensajes que atraviesan intermediarios con herramientas que ya lo resuelven. Para una API nueva, REST con mTLS (M10) y firmas de mensaje donde hagan falta da las mismas garantías con mucho menos peso. Y si te integras con un servicio SOAP, usa una biblioteca de WS-Security mantenida y con los parsers endurecidos: escribir la verificación de firmas a mano es justo cómo nacen los ataques de wrapping.

2.8GraphQL: flexibilidad con costo

GraphQL resuelve un problema real de los frontends: una pantalla necesita datos de cinco recursos y con REST eso son cinco requests, o un endpoint a medida. Con GraphQL el cliente pide exactamente el árbol de datos que necesita. Facebook lo creó en 2012 para el News Feed de su app móvil, lo publicó en 2015 y desde 2018 lo mantiene la GraphQL Foundation, dentro de la Linux Foundation. Documentado A cambio de esa flexibilidad, el servidor acepta consultas arbitrarias, y eso trae tres problemas que hay que diseñar desde el principio:

  • El problema N+1. Cada campo se resuelve por separado; una lista de 50 posts con su autor dispara 51 consultas. Se agrupan con DataLoader.
  • Consultas carísimas. Nada impide pedir amigos de amigos de amigos. Se limita profundidad y costo calculado de cada consulta, y en APIs propias se aceptan solo persisted queries (consultas registradas de antemano, identificadas por hash).
  • Caché HTTP inútil. Todo es POST /graphql. Las persisted queries por GET recuperan la caché de CDN; si no, se cachea por entidad en el servidor.

El esquema es el contrato

Todo empieza en un esquema tipado, escrito en SDL (Schema Definition Language). Tiene tres puntos de entrada: Query para leer, Mutation para escribir y Subscription para recibir eventos. El ! marca un campo que nunca es nulo:

type Query {
  post(id: ID!): Post
  posts(first: Int!, after: String): PostConnection!
}
type Mutation  { sendMessage(input: SendInput!): Message! }
type Subscription { messageAdded(conversationId: ID!): Message! }

type Post { id: ID!  title: String!  author: User!  comments(first: Int!): CommentConnection! }
type User { id: ID!  name: String! }

# Paginación por cursor, al estilo Relay: la misma idea de 2.3
type PostConnection { edges: [PostEdge!]!  pageInfo: PageInfo! }
type PostEdge { node: Post!  cursor: String! }
type PageInfo { hasNextPage: Boolean!  endCursor: String }

La convención de connections (de Relay, el cliente de Facebook) es la paginación por cursor de la sección 2.3 con otro nombre: first y after son el limit y el cursor, y endCursor es la marca. GitHub la usa en toda su API de GraphQL. Documentado

Cómo se ejecuta una consulta

El servidor procesa cada consulta en tres pasos. Parsea el texto. La valida contra el esquema: un campo que no existe o un argumento del tipo equivocado se rechaza antes de tocar la base. Y la ejecuta: recorre el árbol de la consulta de arriba abajo y, para cada campo, llama a su resolver, una función que recibe el objeto padre y devuelve el valor del campo. Un resolver de lista devuelve N objetos, y los resolvers de sus campos se ejecutan N veces.

def resolve_posts(parent, info, first):
    return db.fetch("SELECT * FROM posts ORDER BY id DESC LIMIT %s", first)

def resolve_author(post, info):
    # Sin loader: un SELECT por post. Con loader: se junta con los demás autores del mismo nivel.
    return info.context.loaders.user.load(post.author_id)

N+1 y DataLoader

DataLoader, la biblioteca que publicó Facebook, hace dos cosas: agrupa todas las llamadas a load(id) que ocurren en el mismo turno del event loop y las convierte en una sola llamada con la lista de ids, y cachea cada resultado durante la request, así que el mismo autor pedido diez veces se busca una. Documentado Con 50 posts de 12 autores distintos: sin loader, 1 + 50 = 51 consultas; con loader, 1 + 1 = 2, y la segunda pide 12 ids, no 50. Con anidamiento, el número de consultas pasa a ser uno por nivel del árbol: posts, autores y comentarios de los posts son 3, no 1 + 50 + 50.

El loader se crea por request, nunca global: su caché no sabe de permisos, y un loader compartido le mostraría a un usuario lo que cargó otro.

Errores: 200 con datos a medias

Una consulta GraphQL puede salir bien en parte. La respuesta trae lo que se pudo resolver en data y los fallos en errors, cada uno con el path del campo que falló:

{
  "data": { "posts": [ { "title": "Viaje", "author": { "name": "Ana" } },
                       { "title": "Receta", "author": null } ] },
  "errors": [ { "message": "No tienes permiso para ver este usuario",
                "path": ["posts", 1, "author"],
                "extensions": { "code": "FORBIDDEN" } } ]
}

Dos consecuencias. La primera, para operar: casi todo vuelve con HTTP 200, así que un tablero que mide errores por código de estado ve el 100 % de éxito mientras la mitad de los campos falla. Hay que contar errors, por operación y por código. La segunda, para diseñar: la nulabilidad decide hasta dónde se propaga un error. Si author fuera User! (no nulo) y fallara, el null subiría hasta el primer padre que sí admita null y se llevaría el post entero. Documentado Marca como no nulo solo lo que de verdad nunca puede fallar.

Limitar lo que cuesta una consulta

Contar requests no sirve: una sola consulta puede pedir un millón de objetos. Las APIs públicas cobran por costo calculado. GitHub lo documenta así: cada usuario tiene 5 000 puntos por hora; el costo de una consulta es el número de requests que haría falta para resolver cada conexión, suponiendo que cada first se llena, dividido por 100 y redondeado; first y last van de 1 a 100; ninguna consulta puede pedir más de 500 000 nodos; y una consulta que tarda más de 10 s se corta. Documentado Un ejemplo resuelto:

query {
  viewer {
    repositories(first: 100) {        # 1 request
      nodes {
        issues(first: 50) {           # 100 requests, una por repositorio
          nodes {
            labels(first: 10) {       # 100 × 50 = 5 000 requests, una por issue
              nodes { name }
}}}}}}}

costo  = (1 + 100 + 5 000) / 100 = 51.01  →  51 puntos
nodos  = 100 + 100 × 50 + 100 × 50 × 10 = 55 100   (dentro del límite de 500 000)

Además de costo y profundidad, hay dos abusos propios de GraphQL. Los alias permiten pedir el mismo campo muchas veces en una consulta (a1: login(…) a2: login(…)…): mil intentos de contraseña en una sola request HTTP, que un límite por request no ve. Y la introspección le entrega el esquema completo a cualquiera; en una API privada se apaga en producción.

Caché, persisted queries, suscripciones y federación

  • Persisted queries. El cliente manda el hash SHA-256 de la consulta en lugar del texto. Si el servidor no la conoce, responde con un error y el cliente reenvía el texto completo una sola vez. Como el hash es corto, la consulta puede ir por GET y una CDN puede cachearla. Es el protocolo de Automatic Persisted Queries de Apollo. Documentado En una API propia, lo más seguro es una lista cerrada: el servidor solo ejecuta los hashes que registró tu build, y cualquier otra consulta se rechaza.
  • Caché normalizada en el cliente. Apollo Client y Relay guardan cada objeto una sola vez, por __typename e id. Si una mutación devuelve el usuario 7 con otro nombre, todas las pantallas que lo muestran se actualizan.
  • Suscripciones. Para eventos en vivo, el cliente abre una suscripción que viaja casi siempre sobre un WebSocket (2.9), con un subprotocolo como graphql-transport-ws.
  • Federación. En una empresa grande, cada equipo publica su parte del esquema (un subgrafo) y un router los compone en un solo grafo: planifica cada consulta, pregunta a cada subgrafo lo suyo y junta el resultado. Netflix contó en 2020 cómo migró su API de estudio a este modelo. Documentado El precio es que el router se vuelve una pieza crítica y que una consulta puede pagar varios saltos de red.

2.9Tiempo real: polling, SSE y WebSockets

HTTP nació para que el cliente pregunte y el servidor conteste. Para que el servidor avise algo apenas pasa, hay cuatro formas, de la más simple a la más capaz.

Polling y long polling, con números

Polling es preguntar cada tanto. Su costo se calcula a mano: un millón de clientes que preguntan cada 5 segundos son 1 000 000 ÷ 5 = 200 000 requests por segundo, y si hay novedades para el 1 % de ellos, el 99 % de ese tráfico vuelve vacío. Bajar el intervalo mejora la latencia y multiplica el costo en la misma proporción.

Con long polling, el servidor retiene la request hasta que hay algo nuevo o vence un plazo (25 o 30 s, por debajo del timeout de los proxies del camino). Al recibir la respuesta, el cliente vuelve a preguntar enseguida. Entre una respuesta y la request siguiente queda un hueco: lo que pase ahí se perdería, así que cada request lleva un cursor ("lo posterior al evento 812") y el servidor contesta desde ahí. Es la paginación de 2.3 aplicada al tiempo.

SSE por dentro

SSE es una respuesta HTTP que no termina. El servidor responde con Content-Type: text/event-stream y va escribiendo eventos de texto separados por una línea en blanco, con cuatro campos posibles: event (el tipo), data (el contenido; varias líneas se juntan), id (lo que el navegador devuelve en Last-Event-ID al reconectar) y retry (cuántos milisegundos esperar antes de reconectar). Una línea que empieza con : es un comentario y sirve de latido para que ningún proxy cierre la conexión por inactividad. Documentado

retry: 3000

: latido cada 15 s para que los proxies no corten

event: precio
id: 812
data: {"simbolo": "ACME", "precio": 101.25}

Dos límites prácticos. Con HTTP/1.1, el navegador abre como mucho 6 conexiones por dominio, y cada pestaña con SSE gasta una; con HTTP/2, los streams se multiplexan sobre una conexión y el límite pasa a ser el que negocian las partes, típicamente 100. Documentado Y los proxies que acumulan la respuesta antes de reenviarla (buffering) rompen el streaming: en nginx se desactiva por respuesta con el header X-Accel-Buffering: no. Documentado El M17 lo usa para el streaming de los LLMs.

WebSocket por dentro

Un WebSocket empieza como un GET de HTTP/1.1 que pide cambiar de protocolo. Si el servidor acepta, responde 101 Switching Protocols y desde ese momento la conexión TCP deja de hablar HTTP: lleva frames en los dos sentidos, en cualquier momento.

  • La clave no es seguridad. Sec-WebSocket-Key es un valor al azar, y el servidor responde con el base64 del SHA-1 de la clave más un GUID fijo. No autentica a nadie: solo evita que una caché o un servidor que no habla WebSocket acepte la conexión por error. La autenticación va aparte, con una cookie o un token en el primer mensaje.
  • Los frames del cliente van enmascarados. Cada frame del cliente al servidor lleva una clave de 32 bits nueva y el payload pasa por un XOR con ella. No es cifrado (la clave viaja al lado): impide que una página maliciosa elija los bytes exactos que aparecen en el cable y engañe a un proxy intermedio para envenenar su caché. Los frames del servidor no se enmascaran. Documentado
  • Mensajes de control. Ping y pong mantienen viva la conexión y detectan una que murió sin avisar. El cierre lleva un código: 1000 es normal, 1001 es que el servidor se va (un deploy), y 1006 lo reporta el navegador cuando la conexión se cortó sin frame de cierre. Documentado
  • Lo que no trae. No hay correlación entre pedido y respuesta, ni reintentos, ni control de flujo por mensaje: si el servidor envía más rápido de lo que el cliente procesa, los mensajes se acumulan en memoria. El protocolo de mensajes de tu aplicación tiene que agregar ids, acks y un límite de mensajes en vuelo, como hace WhatsApp en el M29.

2.10Webhooks: tu sistema llamando al de otros

Un webhook invierte la dirección: cuando pasa algo (un pago se confirma), tu sistema envía un POST a la URL que registró el cliente. Eso significa depender de un servidor ajeno, que puede estar caído, lento o mal programado. Las reglas, de los dos lados:

Si envías webhooks

Firma cada envío con HMAC y un secreto por cliente, incluyendo un timestamp.

Reintenta con backoff exponencial durante horas o días, y desactiva el endpoint si falla siempre.

Envía desde una cola, nunca dentro de la transacción del evento.

Da una forma de consultar el estado actual (GET /eventos), porque algún webhook se va a perder.

Si los recibes

Verifica la firma y rechaza timestamps de más de 5 minutos (evita que reenvíen un evento viejo capturado).

Deduplica por id de evento: la entrega es al menos una vez.

Responde 2xx en menos de un par de segundos y procesa en segundo plano.

No confíes en el orden: si llega pago.reembolsado antes que pago.aprobado, consulta el estado actual al proveedor.

La verificación de la firma, del lado del receptor (el esquema que usa Stripe es de este tipo: timestamp + cuerpo firmados con HMAC-SHA256):

// Header recibido:  Firma: t=1790546400,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
function verificar(cuerpoCrudo, header, secreto, ahora) {
  const { t, v1 } = parsear(header);
  if (Math.abs(ahora - t) > 300) throw new Error('timestamp fuera de ventana');   // anti-replay
  const esperado = hmacSha256(secreto, `${t}.${cuerpoCrudo}`);                    // cuerpo SIN parsear
  if (!compararEnTiempoConstante(esperado, v1)) throw new Error('firma inválida');
}

Dos detalles que causan bugs reales: la firma se calcula sobre el cuerpo crudo (si tu framework lo parsea y lo vuelve a serializar, cambia un espacio y la firma no coincide), y la comparación debe ser en tiempo constante para no filtrar información por el tiempo de respuesta.

Ejercicio de diseño: API de reservas de salas

Diseña la API de un sistema para reservar salas de reunión: listar salas con disponibilidad, crear una reserva, cancelarla y listar "mis reservas". Las apps móviles tienen mala conectividad y reintentan. Dos personas pueden intentar reservar la misma sala al mismo tiempo. Un calendario externo debe enterarse de cada reserva.

Define endpoints con método, códigos de respuesta, paginación, cómo evitas reservas duplicadas por reintentos, cómo resuelves la carrera por la misma sala y cómo avisas al calendario.
