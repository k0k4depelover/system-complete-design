Protocolos y diseño de APIs

Una API es un contrato que otros van a usar durante años, con reintentos, redes que se cortan y versiones viejas del cliente. Este módulo compara los protocolos de comunicación y baja al detalle que separa una API que aguanta producción de una que no: semántica de métodos, errores, paginación, versionado e idempotencia.

2.1Estilos de comunicación

Antes de elegir un protocolo hay que responder tres preguntas: ¿quién inicia? (el cliente pide, o el servidor avisa), ¿el que pide espera la respuesta? (síncrono o asíncrono) y ¿quién consume? (un navegador, otro servicio tuyo o el sistema de un cliente). La tabla cubre los protocolos que verás en todo el curso:

ProtocoloDirecciónFormatoÚsalo paraCuidado con

gRPCCliente pide; streaming en ambos sentidosProtobuf (binario)Tráfico entre servicios internosNo es nativo en navegadores; cachés HTTP no lo entienden
GraphQLCliente pideJSONFrontends que combinan muchos recursosCosto de queries arbitrarias, caché difícil, N+1
SSEServidor empujaTexto (eventos)Notificaciones, tokens de un LLM, preciosSolo servidor → cliente
WebSocketAmbos, en cualquier momentoMensajes (texto o binario)Chat, colaboración, juegosConexiones con estado: escalar y balancear es más difícil

El mismo caso de uso, "enviar un mensaje a un chat y recibir la respuesta", se ve así en cada estilo:

Un recurso, un método, un código de estado. Simple, cacheable y fácil de depurar con curl.

POST /v1/conversations/conv_42/messages HTTP/1.1
Content-Type: application/json
Idempotency-Key: 3c9e0a7f-1b2d-4c55-9e8a-51f0c2d7a6b4

{"content": "Hola", "parent_message_id": "msg_17"}

HTTP/1.1 201 Created
Location: /v1/conversations/conv_42/messages/msg_18

{"id": "msg_18", "role": "user", "content": "Hola", "created_at": "2026-09-27T14:03:11Z"}

El contrato vive en un archivo .proto del que se genera código tipado para cliente y servidor. Aquí la respuesta llega como stream del servidor.

syntax = "proto3";
package chat.v1;

service ChatService {
  rpc SendMessage(SendMessageRequest) returns (stream MessageDelta);
}

message SendMessageRequest {
  string conversation_id = 1;
  string parent_message_id = 2;
  string content = 3;
  string idempotency_key = 4;
}

message MessageDelta {
  string message_id = 1;
  string text = 2;        // fragmento de texto
  bool done = 3;
}

Los números de campo (= 1, = 2) son el contrato real en el cable: puedes renombrar campos, pero nunca reutilizar un número.

Una mutación que devuelve exactamente los campos que la pantalla necesita, incluidos datos relacionados, en una sola request.

// POST /graphql
{
  "query": "mutation Send($input: SendInput!) { sendMessage(input: $input) { id content conversation { title unreadCount } } }",
  "variables": { "input": { "conversationId": "conv_42", "content": "Hola" } }
}

// 200 OK (incluso si hubo errores parciales)
{ "data": { "sendMessage": { "id": "msg_18", "content": "Hola", "conversation": { "title": "Viaje", "unreadCount": 0 } } } }

La request es un POST normal; la respuesta queda abierta y trae eventos a medida que ocurren. Es el formato de los LLMs (M17).

event: message.created
id: 1
data: {"message_id": "msg_19", "role": "assistant"}

event: delta
id: 2
data: {"text": "¡Hola! "}

event: delta
id: 3
data: {"text": "¿En qué te ayudo?"}

event: message.completed
id: 4
data: {"finish_reason": "stop"}

Si la conexión se corta, el cliente reconecta enviando Last-Event-ID: 3 y el servidor puede continuar desde ahí.

Tras un GET con Upgrade: websocket, la conexión queda como un canal de mensajes en ambos sentidos. El protocolo de mensajes lo defines tú.

// cliente → servidor
{"type": "message.send", "request_id": "r-5510", "conversation_id": "conv_42", "content": "Hola"}

// servidor → cliente (confirma)
{"type": "message.ack", "request_id": "r-5510", "message_id": "msg_18"}

// servidor → cliente (otro usuario escribió en la misma conversación)
{"type": "message.new", "conversation_id": "conv_42", "message_id": "msg_20", "from": "u_77"}

// cada 25 s, en ambos sentidos
{"type": "ping"}

Como no hay semántica HTTP por mensaje, tienes que reinventar lo que HTTP te daba: correlación (request_id), errores, reintentos e idempotencia.

2.2REST bien hecho: métodos y códigos de estado

Los métodos HTTP no son sinónimos con distinto nombre: cada uno promete propiedades que la infraestructura aprovecha. Un proxy puede reintentar un GET porque es seguro e idempotente; una CDN puede cachearlo; un navegador puede precargarlo. Si usas GET para algo que modifica datos, tarde o temprano alguien lo va a repetir por ti.

MétodoSeguroIdempotenteCacheableUso típico
GETSíSíSíLeer un recurso o una colección
HEADSíSíSíSolo headers (¿existe?, ¿cambió?)
PUTNoSíNoReemplazar un recurso completo en una URL conocida
DELETENoSíNoBorrar
POSTNoNoCasi nuncaCrear, ejecutar acciones
PATCHNoDependeNoModificar parte de un recurso

Errores que ayudan

Un error útil dice qué pasó, qué campo falló y cómo arreglarlo, en un formato que las máquinas pueden leer. El estándar es Problem Details (RFC 9457):

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.ejemplo.com/errores/monto-invalido",
  "title": "El monto no es válido",
  "status": 422,
  "detail": "amount debe ser un entero positivo en la unidad mínima de la moneda (centavos).",
  "instance": "/v1/pagos",
  "request_id": "req_01J9ZC4Q8T",
  "errors": [{ "field": "amount", "code": "must_be_positive_integer" }]
}

El request_id no es decorativo: es lo que el cliente te manda en el ticket de soporte, y con él encuentras la request exacta en tus logs y traces (M11).

2.3Paginación: offset o cursor

La paginación por offset es la primera que todos escriben y la primera que falla en producción, por dos razones. El costo: OFFSET 100000 obliga a la base a leer y descartar 100 000 filas. Y la consistencia: si se insertan o borran filas entre página y página, los elementos se repiten o se pierden.

La paginación por cursor (o keyset) pide "los siguientes después de este", usando un índice:

-- Página siguiente: posts anteriores al último que vio el cliente
SELECT id, author_id, body, created_at
FROM posts
WHERE feed_id = $1
  AND (created_at, id) < ($2, $3)      -- el cursor: (created_at, id) del último elemento
ORDER BY created_at DESC, id DESC
LIMIT 21;                                -- uno de más para saber si hay otra página

-- Índice que hace esto barato a cualquier profundidad
CREATE INDEX posts_feed_cursor ON posts (feed_id, created_at DESC, id DESC);
GET/v1/feeds/{feed_id}/posts?limit=20&cursor={cursor}Diseño de referencia

El cursor es opaco para el cliente: un base64 de (created_at, id), firmado si no quieres que lo manipulen.

{
  "data": [ { "id": "post_981", "body": "…", "created_at": "2026-09-27T13:59:02Z" } ],
  "next_cursor": "eyJ0IjoiMjAyNi0wOS0yN1QxMzo1OTowMloiLCJpZCI6InBvc3RfOTgxIn0",
  "has_more": true
}

El id va en el cursor como desempate: dos filas pueden tener el mismo created_at y, sin desempate, una de ellas se perdería entre páginas. Lo que el cursor no permite es "saltar a la página 37". Casi nunca hace falta; cuando sí (paneles de administración), se acepta el offset con un límite máximo de profundidad.

2.4Versionado y evolución sin romper clientes

Una API pública tiene clientes que no controlas y que no se actualizan: apps móviles de hace dos años, integraciones que nadie mantiene. La regla es separar cambios compatibles de cambios que rompen:

  • Compatibles: agregar endpoints, agregar campos opcionales a la respuesta, aceptar parámetros opcionales nuevos, agregar valores a un enum (si los clientes toleran valores desconocidos).
  • Rompen: quitar o renombrar campos, cambiar tipos o formatos, volver obligatorio algo opcional, cambiar el significado de un código de estado.

Los cambios compatibles solo funcionan si los clientes son tolerant readers: ignoran campos que no conocen. Los que rompen necesitan una versión nueva. Hay tres formas comunes de expresarla:

EstrategiaEjemploVentajaCosto
En la URL/v1/pagos, /v2/pagosVisible, fácil de enrutar y cachearVersiones gruesas: todo cambia de golpe
En un headerAccept: application/vnd.ejemplo.v2+jsonURLs establesInvisible en logs y difícil de probar a mano
Por fecha, fijada por cuentaStripe-Version: 2024-06-20Cada cliente queda fijo en la versión con la que se integró; los cambios se aplican con capas de compatibilidadExige mantener transformaciones entre versiones durante años

Stripe usa la tercera: cada cuenta queda fijada en la versión del día en que se integró, y el servidor transforma las respuestas hacia atrás versión por versión. Documentado Para retirar algo, anuncia la fecha con los headers Deprecation y Sunset (RFC 8594) y mide quién sigue usándolo antes de apagarlo.

2.5Idempotencia en la API

En M00 viste el problema: si la respuesta se pierde, el cliente no sabe si su operación se ejecutó. Con GET, PUT y DELETE puede reintentar tranquilo. Con un POST que cobra dinero, no. La solución estándar es una idempotency key que el cliente genera una vez por operación lógica y reenvía en cada reintento:

El algoritmo, en orden:

  1. Reservar la claveINSERT … ON CONFLICT DO NOTHING. Si insertó una fila, esta request es la primera: sigue.
  2. Si ya existía, compararSi el hash difiere, responde 422: la clave se reutilizó con otra request. Si está completed, devuelve la respuesta guardada. Si está in_progress, responde 409: la primera request todavía se está procesando.
  3. Ejecutar la operaciónY en la misma transacción que sus efectos locales (crear el pago en tu base), guardar la respuesta y marcar la clave como completed.
  4. PurgarUn job borra claves de más de 24 h. Un reintento después de eso se trata como una request nueva.

Qué pasa si el proceso muere a mitad de la operación

La clave queda en in_progress para siempre y los reintentos reciben 409 eternamente. Por eso existe locked_until: vencido el lock, otro proceso puede retomar la clave. Pero retomar exige saber si el efecto externo (el cobro) llegó a ocurrir: se consulta al procesador de pagos con la misma clave, que también debe ser idempotente de su lado. Este es el caso más difícil del sistema de pagos y se resuelve por completo en M27.

Concurrencia optimista con ETag

Otro problema de las APIs con escrituras: dos clientes leen el mismo recurso, lo modifican y guardan; el segundo pisa al primero sin enterarse (lost update). Un ETag resuelve el caso sin bloquear a nadie:

GET /v1/documentos/doc_9           →  200 OK   ETag: "v17"

PUT /v1/documentos/doc_9
If-Match: "v17"
{ …cambios… }                       →  200 OK   ETag: "v18"     (nadie lo había cambiado)
                                    →  412 Precondition Failed  (otro guardó v18 antes: recarga y decide)

Del lado de la base es un UPDATE … SET version = version + 1 WHERE id = $1 AND version = $2: si actualizó 0 filas, alguien ganó la carrera.

2.6gRPC entre servicios

Dentro de tu sistema, los servicios se llaman millones de veces por segundo y los contratos cambian a menudo. gRPC aporta lo que ahí importa:

  • Contratos tipados en Protocol Buffers, con código generado para cada lenguaje: un cambio incompatible falla al compilar, no en producción.
  • Binario y compacto sobre HTTP/2 con conexiones persistentes y multiplexadas.
  • Cuatro modos: unario, streaming del servidor, del cliente y bidireccional.
  • Deadlines que se propagan: si el usuario tiene 2 s de presupuesto y ya se gastaron 1.5 s, el servicio de más abajo recibe 0.5 s y no trabaja en vano.

Lo que cuesta: no es legible con curl, los navegadores necesitan gRPC-Web con un proxy, y el balanceo necesita un balanceador L7 que entienda HTTP/2 (con uno L4, todas las requests de una conexión larga caen en la misma instancia, M03).

2.7GraphQL: flexibilidad con costo

GraphQL resuelve un problema real de los frontends: una pantalla necesita datos de cinco recursos y con REST eso son cinco requests, o un endpoint a medida. Con GraphQL el cliente pide exactamente el árbol de datos que necesita. A cambio, el servidor acepta consultas arbitrarias, y eso trae tres problemas que hay que diseñar desde el principio:

  • El problema N+1. Cada campo se resuelve por separado; una lista de 50 posts con su autor dispara 51 consultas. Se agrupan con DataLoader.
  • Consultas carísimas. Nada impide pedir amigos de amigos de amigos. Se limita profundidad y costo calculado de cada consulta, y en APIs propias se aceptan solo persisted queries (consultas registradas de antemano, identificadas por hash).
  • Caché HTTP inútil. Todo es POST /graphql. Las persisted queries por GET recuperan la caché de CDN; si no, se cachea por entidad en el servidor.

Las conexiones persistentes cambian la escala del problema: ya no importan tanto las requests por segundo como las conexiones abiertas y la memoria que ocupa cada una. Y aparecen problemas nuevos: un deploy que reinicia servidores desconecta a cientos de miles de clientes a la vez, que reconectan todos juntos (se mitiga con reconexión con jitter y drenaje gradual), y enviar un mensaje a un usuario exige saber en qué servidor está su conexión (un registro de presencia o pub/sub, que verás en WhatsApp, M29).

2.9Webhooks: tu sistema llamando al de otros

Un webhook invierte la dirección: cuando pasa algo (un pago se confirma), tu sistema envía un POST a la URL que registró el cliente. Eso significa depender de un servidor ajeno, que puede estar caído, lento o mal programado. Las reglas, de los dos lados:

Si envías webhooks

Firma cada envío con HMAC y un secreto por cliente, incluyendo un timestamp.

Reintenta con backoff exponencial durante horas o días, y desactiva el endpoint si falla siempre.

Envía desde una cola, nunca dentro de la transacción del evento.

Da una forma de consultar el estado actual (GET /eventos), porque algún webhook se va a perder.

Si los recibes

Verifica la firma y rechaza timestamps de más de 5 minutos (evita que reenvíen un evento viejo capturado).

Deduplica por id de evento: la entrega es al menos una vez.

Responde 2xx en menos de un par de segundos y procesa en segundo plano.

No confíes en el orden: si llega pago.reembolsado antes que pago.aprobado, consulta el estado actual al proveedor.

La verificación de la firma, del lado del receptor (el esquema que usa Stripe es de este tipo: timestamp + cuerpo firmados con HMAC-SHA256):

// Header recibido:  Firma: t=1790546400,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
function verificar(cuerpoCrudo, header, secreto, ahora) {
  const { t, v1 } = parsear(header);
  if (Math.abs(ahora - t) > 300) throw new Error('timestamp fuera de ventana');   // anti-replay
  const esperado = hmacSha256(secreto, `${t}.${cuerpoCrudo}`);                    // cuerpo SIN parsear
  if (!compararEnTiempoConstante(esperado, v1)) throw new Error('firma inválida');
}

Dos detalles que causan bugs reales: la firma se calcula sobre el cuerpo crudo (si tu framework lo parsea y lo vuelve a serializar, cambia un espacio y la firma no coincide), y la comparación debe ser en tiempo constante para no filtrar información por el tiempo de respuesta.

Ejercicio de diseño: API de reservas de salas

Diseña la API de un sistema para reservar salas de reunión: listar salas con disponibilidad, crear una reserva, cancelarla y listar "mis reservas". Las apps móviles tienen mala conectividad y reintentan. Dos personas pueden intentar reservar la misma sala al mismo tiempo. Un calendario externo debe enterarse de cada reserva.

Define endpoints con método, códigos de respuesta, paginación, cómo evitas reservas duplicadas por reintentos, cómo resuelves la carrera por la misma sala y cómo avisas al calendario.

Ver la solución de referencia
EndpointDetalles clave
GET /v1/salas?desde=…&hasta=…&cursor=…Paginación por cursor; cacheable unos segundos (max-age=5).
POST /v1/reservas + Idempotency-Key201 con Location. Reintento con la misma clave: la misma respuesta. Sala ocupada: 409 con Problem Details.
DELETE /v1/reservas/{id}Idempotente por naturaleza: borrar una reserva ya cancelada devuelve 204 (o 404, pero sin efecto).
GET /v1/me/reservas?cursor=…Cursor sobre (inicio, id).
Webhook reserva.creada / reserva.canceladaFirmado con HMAC, con id de evento, enviado desde una cola con reintentos. El calendario deduplica.

La carrera por la sala no se resuelve en la API sino en la base: una restricción que impida reservas superpuestas. En PostgreSQL, una restricción de exclusión sobre el rango de tiempo por sala (EXCLUDE USING gist (sala_id WITH =, periodo WITH &&)). La segunda inserción falla y la API la traduce a 409. Cualquier chequeo previo del tipo "¿está libre?" seguido de un insert tiene una ventana de carrera (M05).

El webhook se publica con el patrón outbox: el evento se guarda en la misma transacción que la reserva y un proceso aparte lo envía (M07). Así no hay reservas sin evento ni eventos sin reserva.
