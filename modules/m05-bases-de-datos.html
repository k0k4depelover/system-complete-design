Bases de datos

La base de datos es la pieza más difícil de cambiar de todo el sistema: se elige una vez y se vive con ella años. Este módulo recorre cómo guarda los datos, qué garantiza cuando dos transacciones chocan, cómo se replica y cómo se reparte entre máquinas, con widgets para ver cada trade-off.

Un sistema real combina varios. El patrón habitual es una fuente de verdad transaccional y vistas derivadas (búsqueda, caché, analítica) alimentadas desde su log de cambios: si una vista se corrompe, se reconstruye desde la fuente.

5.2Cómo guarda los datos: B-tree y LSM

Toda base empieza escribiendo cada cambio en el WAL antes de aplicarlo: si se corta la luz, al arrancar reproduce el log. Lo que cambia es cómo organiza los datos después:

El trade-off se mide en amplificaciones: cuántos bytes se escriben en disco por cada byte que escribió la aplicación, y cuántos lugares hay que mirar por cada lectura. El B-tree amplifica escrituras (reescribe una página de 8 kB por una fila de 100 bytes); el LSM amplifica lecturas (una clave puede estar en varios niveles; los filtros de Bloom evitan leer la mayoría) y consume disco y CPU en compactaciones que, si se atrasan, degradan todo.

5.3Índices

Un índice es una copia ordenada de algunas columnas con un puntero a la fila. Las reglas que más importan en producción:

  • Prefijo izquierdo: un índice (tenant_id, created_at) sirve para filtrar por tenant_id, o por tenant_id y un rango de created_at, pero no por created_at solo.
  • Igualdad primero, rango después: en (estado, fecha), WHERE estado = 'pendiente' AND fecha > X recorre un tramo contiguo del índice.
  • Índice que cubre: si el índice incluye todas las columnas que pide la consulta (INCLUDE en PostgreSQL), la base no necesita tocar la tabla.
  • Cada índice cuesta en escrituras: una tabla con 8 índices hace 9 escrituras por cada INSERT. Los índices que nadie usa se borran.
EXPLAIN ANALYZE
SELECT id, total FROM pedidos
WHERE tenant_id = 42 AND created_at > now() - interval '7 days'
ORDER BY created_at DESC LIMIT 50;

-- Bien:  Index Scan Backward using pedidos_tenant_created on pedidos  (rows=50, time=0.3 ms)
-- Mal:   Seq Scan on pedidos  Filter: …  Rows Removed by Filter: 48 000 000  (time=9 800 ms)

5.4Transacciones y niveles de aislamiento

Una transacción ACID promete que sus cambios se aplican todos o ninguno y que, una vez confirmados, sobreviven. Lo delicado es la "I": qué ve cada transacción de las otras mientras corren a la vez. Aislar por completo (como si fueran de a una) es caro, así que las bases ofrecen niveles de aislamiento que permiten ciertas anomalías a cambio de rendimiento. Elige un nivel y una anomalía para ver una ejecución intercalada:

La anomalía más traicionera es el write skew, porque el nivel por defecto de casi todas las bases la permite y no produce ningún error: solo datos que violan una regla del negocio. Tres formas de protegerse, de más a menos general:

  1. SerializableLa base detecta el conflicto y aborta una transacción. La aplicación tiene que estar preparada para reintentar (error 40001 en PostgreSQL).
  2. Bloquear lo que leesSELECT … FOR UPDATE sobre las filas en las que basas la decisión.
  3. Llevar la regla a una restricciónUn UNIQUE, un CHECK o una restricción de exclusión hacen que la base haga cumplir la regla sin importar el aislamiento. Siempre que puedas, esta es la mejor.

5.5Replicación

Se replica por tres razones: sobrevivir a la caída de una máquina, repartir lecturas y acercar datos a los usuarios. Hay tres arquitecturas:

Un líderVarios líderesSin líder
Quién acepta escriturasSolo el líderUn líder por región o datacenterCualquier réplica
ConflictosNo haySí: dos regiones cambian lo mismoSí: se resuelven con versiones o último que escribe
Si cae el líderFailover: segundos a minutos sin escriturasLas otras regiones siguenNo hay líder que perder
EjemplosPostgreSQL, MySQL, MongoDBReplicación activa-activa entre regionesCassandra, DynamoDB (estilo Dynamo)

Con un líder, la decisión central es síncrona o asíncrona. Síncrona: el commit espera a que la réplica confirme, así que un failover no pierde nada, pero cada escritura paga la ida y vuelta a la réplica y, si la réplica cae, el líder se frena. Asíncrona: escrituras rápidas, pero el failover puede perder las últimas transacciones y las réplicas van detrás. Es exactamente el trade-off de latencia contra consistencia de PACELC (M06). Lo habitual es una réplica síncrona en otra zona y el resto asíncronas.

Qué pasa con el retraso de replicación

El retraso de replicación suele ser de milisegundos, pero bajo carga o durante un vacuum largo puede llegar a minutos. Síntomas: un usuario guarda algo y no lo ve al recargar (falta read-your-writes); una lista muestra un elemento y en la siguiente recarga desaparece (falta de lecturas monótonas, porque la segunda lectura fue a una réplica más atrasada).

Mitigación: leer del líder durante unos segundos después de que el usuario escribe; o guardar la posición del log (LSN) de su última escritura y leer solo de réplicas que ya la aplicaron; y fijar a cada usuario a la misma réplica para lecturas monótonas. Y alertar sobre el retraso: una réplica una hora atrasada es un incidente.

Quórums

En la replicación sin líder, el cliente escribe en N réplicas y espera W confirmaciones; lee de R y se queda con la versión más nueva. Si W + R > N, todo conjunto de lectura se solapa con todo conjunto de escritura: al menos una de las réplicas leídas tiene el último valor.

Configuraciones típicas: N = 3, W = 2, R = 2 (equilibrado); W = 3, R = 1 (lecturas rápidas, escrituras frágiles); W = 1, R = 1 (máxima velocidad, consistencia eventual). Para que las réplicas converjan aunque nadie las lea, estos sistemas usan read repair (al leer, se corrigen las réplicas atrasadas) y anti-entropía con árboles de Merkle (comparan resúmenes de rangos de claves y sincronizan solo lo que difiere).

5.6Particionado (sharding)

Cuando los datos o las escrituras no caben en una máquina, se reparten con sharding. Todo depende de la partition key, que decide en qué shard vive cada fila:

EstrategiaCómoGanasPagas
Por rangoA–F al shard 1, G–M al 2…Consultas por rango eficientesClaves monótonas (fechas, IDs secuenciales) concentran las escrituras en un shard
Por hashhash(clave) decide el shardCarga parejaLos rangos tocan todos los shards
Por directorioUna tabla dice qué shard tiene cada tenantMover un cliente grande a su propio shardOtro componente crítico que consultar y mantener

La clave correcta hace que las consultas frecuentes toquen un solo shard. En un chat, conversation_id: todo el historial de una conversación vive junto (M00). En un SaaS, tenant_id: cada cliente vive en un shard, con un plan para los clientes gigantes. Las consultas que cruzan shards (un índice secundario global, un reporte de todo) se resuelven aparte: consultando todos los shards en paralelo (scatter-gather) o manteniendo una vista derivada.

Rebalancear sin mover todo

El día que agregas un shard hay que mover datos. Con hash(clave) mod N, cambiar N cambia el destino de casi todas las claves. Dos soluciones:

  • Muchas particiones fijas: se crean, por ejemplo, 1 024 particiones desde el principio y se asignan a los nodos; agregar un nodo es mover algunas particiones enteras. Lo usan Elasticsearch, Kafka y Riak.
  • Hashing consistente: nodos y claves en un anillo de hashes; cada clave pertenece al siguiente nodo en sentido horario. Con nodos virtuales, cada nodo ocupa muchas posiciones y la carga se empareja. Lo usan Cassandra, DynamoDB y muchas cachés distribuidas.

5.7Cómo elegir

Tres preguntas resuelven la mayoría de los casos, en este orden:

  1. ¿Qué no puedo perder ni duplicar?Dinero, pedidos, inventario: base transaccional con aislamiento fuerte y replicación síncrona. No se negocia.
  2. ¿Cómo se accede?Por clave, por rango, por texto, por similitud, por agregación temporal. Cada patrón tiene su almacén.
  3. ¿Cuánto y qué tan rápido crece?Si cabe en un PostgreSQL grande con réplicas (y cabe mucho más de lo que se suele creer: terabytes y decenas de miles de transacciones por segundo), empieza por ahí.

En producción real

Muchas empresas grandes corren sobre bases relacionales mucho más allá de lo que parecería razonable: Figma documentó cómo escaló PostgreSQL particionando verticalmente (tablas en distintas bases) antes de hacer sharding horizontal, y Notion hizo sharding de su PostgreSQL por espacio de trabajo. Documentado Cambiar de base de datos es de los proyectos más caros que existen; elegir la aburrida al principio rara vez es un error.

Ejercicio de diseño: datos de un marketplace

Un marketplace tiene 50 millones de productos de 2 millones de vendedores, 20 000 pedidos por minuto en pico, búsqueda por texto con filtros, reseñas y un inventario que no puede venderse por debajo de cero.

Elige los almacenes, define las claves de partición, escribe el esquema de pedidos e inventario, y explica cómo evitas vender más stock del que hay.

Ver la solución de referencia
  • Pedidos e inventario: PostgreSQL. 20 000 pedidos por minuto son ~330 por segundo: un solo clúster con réplica síncrona basta durante mucho tiempo. Si hiciera falta particionar, por vendedor_id para el inventario y por comprador_id para los pedidos.
  • Catálogo y búsqueda: los productos en PostgreSQL como fuente de verdad; OpenSearch como vista derivada alimentada por CDC.
  • Reseñas: tabla en PostgreSQL particionada por producto_id, con el promedio precalculado en el producto.
  • Stock que nunca baja de cero: se lleva a la base, no a la aplicación:
CREATE TABLE inventario (
  sku        text PRIMARY KEY,
  vendedor_id uuid NOT NULL,
  disponible integer NOT NULL CHECK (disponible >= 0),
  version    bigint NOT NULL DEFAULT 1
);

-- Reservar 2 unidades: atómico, sin leer antes. Si no alcanza, el CHECK falla y no se vende.
UPDATE inventario SET disponible = disponible - 2, version = version + 1
WHERE sku = $1 AND disponible >= 2
RETURNING disponible;      -- 0 filas afectadas = sin stock

CREATE TABLE pedidos (
  id            uuid PRIMARY KEY,           -- UUIDv7
  comprador_id  uuid NOT NULL,
  estado        text NOT NULL CHECK (estado IN ('creado', 'pagado', 'enviado', 'cancelado')),
  total_centavos bigint NOT NULL,
  moneda        char(3) NOT NULL,
  idempotency_key text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (comprador_id, idempotency_key)    -- un reintento no crea otro pedido
);

El UPDATE … WHERE disponible >= 2 evita la actualización perdida sin bloqueos explícitos, y el CHECK es la red de seguridad. La reserva de stock y la creación del pedido van en la misma transacción; el pago, que es externo, se coordina con una saga (M27).
